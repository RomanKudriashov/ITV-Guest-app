# Inclusions API — контракт (кросс-ссылки, overlay, разъезд заказа)

Сервис может **включить** контент другого сервиса **по ссылке** (не копия) и
наложить overlay. Заказ-агрегатор с позициями от разных исполнителей
**разъезжается** (fan-out). **R2 — модель + API + резолв + посев.** Управляющий
UI включений — R4; типизированные трекеры — R3.

## Модель

`ServiceInclusion` (тенант, RLS): `including_service` ⊃ `source_service`.
- `scope`: `all` (весь источник) | `categories` (выбранные `ServiceInclusionCategory`).
- overlay: `markup_kind` (`none|percent|amount`) + `markup_value` (percent в
  б.п. `1500=15%`, amount в мин. ед.); `schedule` (своё расписание блока,
  null = доступность источника); `executor` (`source` — точка источника,
  по умолчанию | `own` — своя точка включающего).
- скрытие: `ServiceInclusionHidden` — позиции источника, скрытые в этом включении.
- инварианты: unique пары `(including, source)`; нет самовключения (CheckConstraint);
  **нет циклов** (A↔B и длиннее — отклоняется при записи, `409 inclusion_cycle`).

## Резолв (на чтении)

- **Эффективный каталог** сервиса = свои категории + заимствованные (с overlay);
  позиции — те же строки источника: правка в источнике видна заёмщику **без
  копии** (цена, стоп-лист).
- **Цена** заимствованной = `источник + наценка overlay`.
- **Доступность** заимствованной = **пересечение** доступности источника и
  расписания блока (overlay/венью включающего): источник закрыт → закрыто;
  блок закрыт → закрыто.
- **Эффективный исполнитель** позиции: своя → точка сервиса; заимствованная →
  точка по overlay (`source`/`own`). Один выбор решает маршрут и расписание.

## Разъезд заказа (fan-out)

Заказ оформляется на **сервис-корзину** (`OrderIn.service_code`). Позиции
группируются по эффективному исполнителю:
- **один исполнитель** → обычный (плоский) заказ — как раньше, байт-в-байт;
- **несколько** → `Order.parent` (гостевой агрегат) + по одному `child` на
  исполнителя. Каждый child — на своей доске трекера (существующий механизм),
  со своими позициями и эскалацией.

Гостю — **один заказ**: `serialize_order(parent)` агрегирует позиции children,
статус — свод (наименее продвинутый; terminal когда все). **Снимок сумм — один,
на parent**, над всеми позициями, коммерция **включающего** сервиса (сбор/
доставка/минимум — его). Цена заимствованной строки в снимке — с наценкой.
Отмена гостем каскадит на не-терминальные children.

`quote_cart` с `service_code` считает так же (наценка + коммерция агрегатора) —
предпросчёт сходится со снимком заказа.

## API (CMS, StaffAuth) — данные, без полного UI (R4)

| Метод | Путь | Назначение |
|---|---|---|
| GET | `/api/v1/cms/services/{service_id}/inclusions` | включения сервиса |
| POST | `/api/v1/cms/services/{service_id}/inclusions` | создать (source/scope/markup/schedule/executor/category_ids/hidden_item_ids) |
| PATCH | `/api/v1/cms/inclusions/{id}` | править overlay/scope/выборки |
| DELETE | `/api/v1/cms/inclusions/{id}` | удалить |

Объект: `{id, including_service_id, source_service_id, scope, markup_kind,
markup_value, schedule_id, executor, is_active, sort_order, category_ids,
hidden_item_ids}`. Цикл при создании → `409 {code: "inclusion_cycle"}`.

## Аналитика

Единица фанного заказа — **parent** (несёт деньги + агрегат позиций с
исполнителями children); children в аналитику не идут (иначе двойной счёт).
Пересчёт из заказов и лента дашборда считают parent + обычные, не children.

## Границы (не в R2)
Управляющий UI включений — R4. Типизированные трекеры (доска на тип) — R3;
здесь маршрутизация только доставляет в существующий механизм исполнения.
