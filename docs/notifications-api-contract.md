# Контракт уведомлений и эскалации

Фиксируется **до** реализации. Префикс CMS-эндпоинтов: `/api/v1/cms`.
Аутентификация и тенант — как у остальной CMS (`docs/cms-api-contract.md`).

## Зачем это

Заявка бесполезна, если её никто не увидел. Отдел получает уведомление в свой
канал; если за отведённое время заявку не взяли в работу — она поднимается
выше по ступеням: старший смены, затем руководитель. Взяли в работу —
эскалация гаснет.

## Гарантии движка

Три свойства, ради которых он вообще написан:

1. **Ступень заново проверяет состояние заказа в момент исполнения.**
   Отмена запланированной задачи — оптимизация, а не гарантия: задача может
   сработать ровно в ту секунду, когда официант жмёт «Принять». Поэтому перед
   отправкой ступень перечитывает заказ и молча гасит себя, если он уже принят,
   завершён или отменён. Это та же дисциплина реконсиляции, что у WebSocket.
2. **Идемпотентность.** У каждой отправки есть ключ дедупликации
   (`hotel + заказ + ступень + канал`) с уникальным индексом. Повтор задачи —
   обычное дело для Celery — не приводит ко второму сообщению гостю или
   сотруднику.
3. **Недоступность канала не задевает заказ.** Отправка идёт отдельной задачей
   с ретраями и экспоненциальным backoff. Упавший Telegram делает запись
   `failed` в журнале и ничего больше.

## 1. Модель

### NotificationChannel — куда слать

```jsonc
{
  "id": "...", "type": "telegram",          // telegram | email | log
  "title": "Чат кухни",
  "is_active": true,
  "execution_point_id": "..." | null,       // канал отдела
  "user_id": "..." | null,                  // персональный канал сотрудника
  "config": {"chat_id": "-100123"},         // секреты не отдаются наружу
  "config_public": {"chat_id": "-100123"},  // то же без секретов — для CMS
  "templates": {
    "ru": {"subject": "Новая заявка №{{number}}", "body": "..."},
    "en": {"subject": "...", "body": "..."}
  }
}
```

`config` по типам:

| Тип | Поля | Секретные |
|---|---|---|
| `telegram` | `bot_token`, `chat_id` | `bot_token` |
| `email` | `to` (список), `from_email` | — |
| `log` | — | — |

`log` — адаптер для разработки и CI: пишет сообщение в лог приложения и всегда
успешен. Без него тесты и демо требовали бы настоящих кредов.

**Секреты наружу не отдаются.** В ответах вместо `config` приходит
`config_public` с замаскированными значениями (`bot_token: "••••1234"`).
Записать секрет можно, прочитать — нет.

### EscalationRule + EscalationStep — когда и кому

```jsonc
{
  "id": "...", "name": "Кухня: подъём по смене",
  "execution_point_id": "...",   // null — правило по умолчанию для отеля
  "is_active": true,
  "steps": [
    {"id": "...", "sort_order": 0, "delay_minutes": 0,
     "target_kind": "point",   "channel_id": null,  "title": "Сразу — в чат кухни"},
    {"id": "...", "sort_order": 1, "delay_minutes": 5,
     "target_kind": "lead",    "channel_id": null,  "title": "Через 5 мин — старшему"},
    {"id": "...", "sort_order": 2, "delay_minutes": 15,
     "target_kind": "manager", "channel_id": null,  "title": "Через 15 мин — руководителю"}
  ]
}
```

`delay_minutes` считается **от создания заказа**, а не от предыдущей ступени:
так «через 15 минут» означает ровно то, что написано, и перенастройка одной
ступени не сдвигает остальные.

`target_kind`:

| Значение | Кому уходит |
|---|---|
| `point` | все активные каналы точки исполнения |
| `lead` | персональные каналы старших смены этой точки |
| `manager` | персональные каналы руководителей этой точки |
| `channel` | конкретный канал из `channel_id` |

Если цель не разрешилась ни в один канал, ступень пишет в журнал `skipped` с
причиной — молчаливое «никому не ушло» недопустимо.

### NotificationLog — журнал и состояние

```jsonc
{
  "id": "...", "order_id": "...", "order_number": 42,
  "rule_id": "...", "step_id": "...", "step_index": 1,
  "channel_id": "..." | null, "channel_type": "telegram",
  "target_kind": "lead",
  "status": "sent",            // scheduled | sent | failed | skipped | cancelled
  "scheduled_for": "2026-07-22T18:05:00+03:00",
  "sent_at": "2026-07-22T18:05:01+03:00",
  "attempts": 1,
  "error": "",
  "subject": "Новая заявка №42",
  "body": "Комната 305 · Такси · Аэропорт Пулково",
  "accepted_at_send": false     // был ли заказ уже принят в момент срабатывания
}
```

Записи двух уровней: у ступени есть **родительская** запись (`channel_id: null`
— «ступень сработала») и **дочерние** по одной на канал («сообщение ушло»).
Так видно и то, что ступень отработала, и куда именно она разошлась.

Статусы:

* `scheduled` — запланирована, ждёт своего времени;
* `sent` — отправлено;
* `failed` — канал не принял после всех ретраев;
* `skipped` — ступень сработала, но слать было некому/незачем;
* `cancelled` — заказ приняли раньше, ступень погашена.

## 2. Жизненный цикл

```
order.created ─→ plan_escalation_task (Celery)
                   ├─ ступень, чей срок пришёл (delay 0) → выполняется сразу
                   └─ ступени 1..N → ScheduledJob(kind="notification.escalation_step",
                                                  run_at=created_at + delay)
служба расписания (круг раз в минуту) → run_step_job → execute_step

каждая ступень при исполнении:
   перечитать заказ ──→ принят / завершён / отменён ? ──→ cancelled, выход
                    └─→ нет ──→ разрешить цели ──→ отправки (по задаче на канал)

order.accepted / order.status_changed(терминальный) / order.cancelled
   └─→ cancel_pending(order): scheduled → cancelled, задания службы → cancelled
       (без записи в журнал действий), revoke старых задач Celery (best-effort)
```

**Когда — служба расписания, отправка — Celery.** Ступень только записывает
доставки; в очередь `deliver_notification` они уходят **после коммита**: служба
держит блокировку строки задания, и ждать под ней канал нельзя, а воркер,
получивший задачу раньше коммита, не нашёл бы доставку. Точность ступени —
круг службы, до минуты.

**Повторы.** До 5 повторов с нарастающей паузой: 15 с, 30 с, 1 мин, 2 мин,
4 мин (не больше 10 мин) плюс разброс до 5 с. Исчерпаны — доставка `failed` и
событие `notification.undelivered` (см. §3а).

**Выключенная просрочка** (`order.overdue`, §3а) — новые ступени не
планируются, уже запланированные гаснут при срабатывании (`cancelled`,
«Отель выключил уведомления о просрочке»).

`order.accepted` — новое событие шины: раньше принятие заказа было неотличимо
от любой другой смены статуса, а для эскалации это ключевой момент.

## 3. CMS API

### Каналы

| Метод | Путь |
|---|---|
| GET | `/api/v1/cms/notification-channels` |
| POST | `/api/v1/cms/notification-channels` |
| PATCH / DELETE | `/api/v1/cms/notification-channels/{id}` |
| POST | `/api/v1/cms/notification-channels/{id}/test` |

`test` отправляет пробное сообщение и возвращает результат — настраивать канал
вслепую и ждать первой настоящей заявки, чтобы узнать про опечатку в токене,
нельзя.

Валидация конфигурации по типу: `422 channel_config_invalid` с `field`.

### Правила эскалации

| Метод | Путь |
|---|---|
| GET | `/api/v1/cms/escalation-rules` |
| POST | `/api/v1/cms/escalation-rules` (вместе со ступенями) |
| PATCH | `/api/v1/cms/escalation-rules/{id}` (`steps` заменяют набор целиком) |
| DELETE | `/api/v1/cms/escalation-rules/{id}` |

Правила:
* `delay_minutes` неотрицательный, ступени упорядочены по возрастанию задержки —
  иначе `422 steps_out_of_order`;
* две ступени с одинаковой задержкой — `422 duplicate_delay`;
* `target_kind=channel` без `channel_id` — `422 channel_required`;
* правило без ступеней — `422 rule_without_steps`;
* на одну точку исполнения — не больше одного активного правила
  (`409 rule_already_exists`).

### Журнал

`GET /api/v1/cms/notification-log?order_id=&status=&limit=` — новые сверху.

## 3а. События без заказа

Эскалация — журнал доставок **по заказу**, заказ в нём обязателен. Всё
остальное, что уходит человеку (сообщение гостя, низкая оценка, события
оформления), идёт через одну дверь `services/events.notify` и пишется в свой
журнал.

### Справочник событий

Код, не таблица: `apps/notifications/events.py`. Событие заводим мы, отель его
не создаёт. В справочнике только то, что система порождает сегодня:

| Код | Адресат по умолчанию | Включено по умолчанию |
|---|---|---|
| `order.overdue` | по ступеням правил эскалации | да |
| `order.cancelled` | `point` | да |
| `review.low` | `manager` | да |
| `notification.undelivered` | `hotel` | да |
| `chat.guest_message` | `point` | нет |
| `brand.published_on_schedule` | `hotel` | нет |
| `brand.published_late` | `hotel` | нет |
| `brand.schedule_failed` | `hotel` | нет |

По умолчанию включено только то, после чего нужно действовать. Остальное
отель включает сам.

* `order.cancelled` — отделу заявки. Не шлётся, если отменил сотрудник этого
  же отдела (он знает), и для агрегата (о себе сообщает каждая его часть).
* `notification.undelivered` — доставка события или эскалации не прошла
  после всех повторов. Уходит в общие каналы отеля, **кроме** канала, который
  не принял сообщение; о недоставленном «не доставлено» не сообщается.

У каждого события — название, тема и текст на `ru`/`en`/`ar`/`zh` и список
подстановок `{{имя}}`. Незаполненная подстановка — прочерк; пустая строка
остаётся пустой, а строка текста, ставшая пустой, убирается. Подстановка,
зависящая от языка (отдел, состав, причина), лежит в данных события словарём
`{язык: текст}` и выбирается на языке получателя.

Адресаты: `point` — все активные каналы отдела; `lead` / `manager` — только
**личные** каналы сотрудников этого уровня на этой точке; `hotel` — **общие**
каналы: без отдела **и** без сотрудника. Личный канал общим не считается.
Событие отдела без отдела адресовать некому — это видно в журнале.

### Журнал событий

Две таблицы: факт (`notifications_event`) и доставки
(`notifications_event_delivery`). Факт пишется **до** попытки отправки и
остаётся, даже если слать было некому.

```jsonc
{
  "id": "...", "code": "review.low",
  "execution_point_id": "..." | null,
  "payload": {"rating": 2, "number": 42, "comment": ""},
  "outcome": "partial",   // pending | sent | partial | failed | no_recipients
  "created_at": "...",
  "deliveries": [
    {"id": "...", "channel_id": "...", "recipient_id": "..." | null,
     "channel_type": "telegram", "channel_title": "Пётр",
     "language": "en", "subject": "...", "body": "...",
     "status": "failed", "attempts": 1, "sent_at": null,
     "error": "Unauthorized"}
  ]
}
```

Список — `{items, total, …}`, новые сверху. Повтор события шины не даёт
второй записи: уникальный `(hotel, dedupe_key)`.
Отказ канала не отменяет события и не роняет вызывающего. Выключенное
отелем событие не пишется вовсе.

Доставки ставятся в Celery (`deliver_event`) **после коммита**, с теми же
повторами, что у эскалации. Пока не закончены все — итог `pending`.

| Метод | Путь |
|---|---|
| GET | `/api/v1/cms/notification-events?code=&outcome=&limit=&offset=` |
| GET | `/api/v1/cms/notification-events/catalog` |

Управляющий видит события своих отделов; события уровня отеля (без отдела)
видит только администратор. Справочник отдаётся на языке интерфейса.

### Язык текста — язык получателя

* личный канал — язык владельца (`User.language`, `en-US` → `en`);
* общий канал отдела или отеля — язык отеля;
* язык, на котором справочник не говорит, — язык отеля, затем `ru`.

Текст события, заданный отелем (ниже), стоит в том же порядке, что шаблон
канала: свой текст на языке получателя → справочник на нём же → свой текст на
языке отеля → справочник.

Для эскалации язык выбирается на каждую доставку. Порядок текста: шаблон
канала на языке получателя → текст справочника на языке получателя → шаблон
канала на языке отеля → справочник по запасному языку. Текст события,
заданный отелем, идёт сразу после шаблона канала на том же языке. Готовые слова
(«Номер 305») тоже собираются на языке получателя. Язык записывается в
доставку журнала.

### Настройки событий

Решение отеля по каждому событию справочника. Строки нет — действует
справочник; сохранение значений справочника строку удаляет.

```jsonc
{
  "code": "review.low", "title": "Низкая оценка",
  "audience": "manager", "placeholders": ["rating", "number", "comment", "room_number"],
  "enabled_by_default": true,
  "audience_from_rules": false,        // true — кому, решают правила эскалации
  "defaults": {"ru": {"subject": "...", "body": "..."}, "en": {...}},
  "setting": {
    "enabled": true,
    "audience": "manager",             // point | lead | manager | hotel | channel
    "channel_id": null,                // при audience=channel
    "channel_types": [],               // пусто — любые виды
    "templates": {"ru": {"subject": "...", "body": "..."}},
    "customized": false
  }
}
```

| Метод | Путь |
|---|---|
| GET | `/api/v1/cms/notification-events/settings` |
| PUT | `/api/v1/cms/notification-events/settings/{code}` (не переданное поле не меняется) |
| POST | `/api/v1/cms/notification-events/settings/{code}/preview` (+ `language`) |

`GET` отдаёт весь справочник одним конвертом списка `{items, total, limit,
truncated, offset}`, как остальные списки CMS; так же отдаётся и
`/notification-events/catalog`.

Меняет и смотрит превью **администратор отеля** (`403` управляющему).
Изменение пишется в журнал действий: `notification.event_settings_changed`.

Проверки (`422`, одни и те же для сохранения и превью):
`invalid_audience`, `channel_required`, `channel_not_found`,
`invalid_channel_type`, `audience_from_rules` (адресат просрочки),
`invalid_language`, `unknown_placeholder`, `template_incomplete` (тема без
сообщения или наоборот), `too_long` (тема 255, сообщение 4000).
Неизвестное событие — `404`.

### Превью: «вот так придёт»

Черновик прикладывается к **последнему настоящему случаю** отеля и
собирается тем же путём, что отправка. Ничего не сохраняет и не отправляет.

| Событие | Пример |
|---|---|
| `order.overdue` | последняя заявка (не агрегат) |
| `order.cancelled` | последняя отменённая заявка |
| `chat.guest_message` | последнее сообщение гостя |
| `review.low` | последний отзыв с оценкой не выше порога отеля |
| `brand.*` | последнее такое событие в журнале действий; иначе последняя опубликованная версия с пометкой `brand_version` (задержки нет) |
| `notification.undelivered` | последняя недоставленная доставка |

```jsonc
{
  "enabled": true,
  "example": {"source": {"kind": "review", "number": 412, "rating": 2,
                         "at": "...", "point": "Кухня"}},
  "message": {"language": "ru", "subject": "...", "body": "..."},
  "recipients": [
    {"channel_id": "...", "channel_title": "...", "channel_type": "log",
     "recipient": "Пётр", "language": "en", "subject": "...", "body": "...",
     "step": null}              // у просрочки — {"title", "delay_minutes"}
  ],
  "rule": null                  // у просрочки — {"id", "name"}
}
```

Случая нет — `example`, `message` и `recipients` равны `null`: пример не
выдумывается. `recipients: []` — пример есть, но сейчас это не придёт никому.

### Служба расписания в консоли

`GET /api/v1/platform/scheduler` и сигнал здоровья в сводке платформы несут,
кроме пульса, `pending` (ждут срока после круга) и `by_kind`:
`{"notification.escalation_step": {"pending": 12, "due": 0, "overdue": 0},
"brand.publish": {...}}`. Сигналы `scheduler_ok|overdue|down` несут ту же
разбивку в `kinds`: сотня ступеней эскалации не заслоняет одну просроченную
публикацию.

## 4. Настройки

| Переменная | Смысл |
|---|---|
| `NOTIFICATIONS_ENABLED` | глобальный выключатель (в тестах `0`) |
| `NOTIFICATIONS_FALLBACK_ADAPTER` | чем слать, если у канала нет кредов (`log`) |
| `TELEGRAM_API_URL` | база API бота — подменяется в тестах |
| `DEFAULT_FROM_EMAIL` | отправитель писем |

Задержки ступеней задаются данными (`delay_minutes`), а не настройками: в
тестах ступени вызываются напрямую, поэтому ждать реальных минут не нужно
никогда.
