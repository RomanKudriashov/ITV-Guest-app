# Контракт 2. Гостевой API управления номером

Префикс: `/api/v1/guest/room`. Живое состояние: `WS /ws/v1/guest/room`.
Реализация — G5. Общие правила (тенант по поддомену, `Authorization: Bearer`,
локализованные строки, формат ошибок) — как в
[`../../guest-api-contract.md`](../../guest-api-contract.md).

## Главное правило

Фронт знает про **`controlId` и значение**. И больше ни про что.

```jsonc
{ "controlId": "light.main", "value": 1 }
```

Номер комнаты, endpoint, имя устройства iRidi, `C_*`, `F_*`, диапазоны — всё
это backend выводит из гостевой сессии. Ни одно из этих полей не приходит с
фронта и ни одно не уходит на фронт (ТЗ §13).

Подмена `controlId` даёт максимум «такого элемента в вашем номере нет» — она не
может дотянуться до соседней комнаты, потому что комната берётся из сессии, а
не из запроса.

## 1. Резолв: QR → комната → тип → конфиг

QR номера кодирует уже существующий диплинк `/r/{room}` (см. `apps/hotels/qr.py`).
Отдельного «GRMS-QR» не заводим — гость сканирует один код на весь сервис.

Цепочка на входе:

```
токен сессии → GuestSession.room → RoomTypeRoom → RoomType
             → PublishedConfig (текущая опубликованная версия)
             → OnPremNode отеля + endpoint "iridi"
```

Если любое звено отсутствует — модуль недоступен, и это **не ошибка**, а
легальное состояние `unavailable`:

* у отеля выключен модуль `room_control` (реестр модулей, R1/R6);
* комната не привязана к типу;
* у типа нет опубликованной версии конфигурации;
* узел офлайн или endpoint `iridi` недоступен.

## 2. Уровни доверия и step-up по PIN заезда

Опираемся на существующую лестницу `TrustLevel`
(`anonymous` 0 < `room_scanned` 10 < `pms_verified` 20 < `staff_verified` 30).

| Действие | Нужный уровень |
|---|---|
| Увидеть, что модуль есть | `anonymous` |
| Читать состояние номера (снапшот) | `room_scanned` (**weak**) |
| Отправлять команды | `pms_verified` (**strong**) |

Почему чтение и запись разведены: QR висит на стене в номере и его может
отсканировать кто угодно, кто в номер зашёл, — горничная, сосед, гость
предыдущего заезда со старым скриншотом. Смотреть на состояние — приемлемо,
менять климат и открывать шторы — нет.

Повышение `room_scanned → pms_verified` — **PIN заезда**: последние 4 цифры
брони/фамилия, что даст PMS. Точный фактор фиксируется в G6, когда будет
интеграция PMS; контракт фиксирует только форму.

### `POST /api/v1/guest/room/verify`

```jsonc
// запрос
{ "pin": "4821" }

// 200 — доверие повышено
{ "trust": "pms_verified" }

// 401 — не подошло
{ "detail": "Код не подошёл", "code": "PIN_INVALID", "attempts_left": 3 }

// 429 — перебор
{ "detail": "Слишком много попыток. Попробуйте через 15 минут",
  "code": "PIN_THROTTLED", "retry_after_s": 900 }
```

Защита от перебора — обязательная часть контракта, а не деталь реализации:

* счётчик попыток на **сессию И на комнату** (иначе перебор с новых сессий
  обнуляет счётчик бесплатно);
* 5 попыток → блокировка на 15 минут, дальше окно растёт;
* ответ на неверный PIN — константного времени, без подсказок «такой брони нет»
  против «PIN не тот»;
* каждая попытка — в `AuditLog` (`grms.pin_attempt`), успешная и неуспешная;
* PIN не попадает ни в журнал, ни в `payload` аудита, ни в метрики.

При смене гостя в номере (выезд по PMS) сессии комнаты со `pms_verified`
обязаны терять уровень — иначе выехавший гость продолжит управлять номером.

## 3. Снапшот состояния

### `GET /api/v1/guest/room/state`

Единственная форма ответа — **полный снапшот**. Частичных апдейтов в контракте
нет: гость может открыть страницу в любой момент, и склеивать дельты на клиенте,
который только что подключился, не из чего.

```jsonc
{
  "availability": "online",          // online | unavailable
  "message": null,                   // текст для гостя, когда unavailable
  "checked_at": "2026-08-02T12:00:00+03:00",
  "trust": "pms_verified",
  "can_command": true,
  "zones": [
    { "code": "bedroom", "title": "Спальня",
      "controls": [
        { "controlId": "dnd",
          "kind": "dnd", "title": "Не беспокоить",
          "capabilities": ["toggle"],
          "value": 0, "state": "confirmed", "readonly": false,
          "updated_at": "2026-08-02T11:59:58+03:00" },

        { "controlId": "light.main",
          "kind": "light_group", "title": "Основной свет",
          "capabilities": ["toggle"],
          "value": 1, "state": "confirmed", "readonly": false },

        { "controlId": "ac.1",
          "kind": "air_conditioner", "title": "Кондиционер",
          "capabilities": ["toggle", "fan_speed", "setpoint", "current_temp"],
          "value": { "on": 1, "fan_speed": 2, "setpoint": 22, "current_temp": 23 },
          "range": { "setpoint": { "min": 16, "max": 32, "step": 1 },
                     "fan_speed": { "min": 0, "max": 3, "step": 1 } },
          "state": "confirmed", "readonly": false },

        { "controlId": "scene.night",
          "kind": "scene", "title": "Ночь",
          "capabilities": ["trigger"],
          "value": null, "state": "confirmed", "readonly": false }
      ] }
  ]
}
```

Ключевое:

* `capabilities` — то, по чему фронт **ветвится**. Не по `controlId`, не по
  строковому имени. Реестр — [`control-elements.md`](./control-elements.md).
* составной элемент (кондиционер) — **один** `controlId` с объектом-значением,
  а не четыре независимых. Иначе фронт собирал бы фанкойл из четырёх кусков
  сам, а он не должен знать, что фанкойл вообще из чего-то состоит.
* `range` приходит с сервера, из диапазонов Excel (`16-32`, `0-3`). Фронт не
  зашивает ни 16, ни 32.
* `title` — уже локализованная строка.

### Состояния элемента

| `state` | Когда | Что делает фронт |
|---|---|---|
| `confirmed` | значение подтверждено feedback'ом | показывает значение |
| `pending` | команда ушла, подтверждения ещё нет | «в процессе», элемент заблокирован |
| `offline` | связи нет или значение не читается | «нет связи», элемент заблокирован |

`offline` **обязателен** отдельно от `unavailable` всего экрана: часть элементов
может читаться, часть нет.

Про `unavailable`: гостю показывается ровно текст ТЗ §6 — «Управление номером
временно недоступно. Пожалуйста, обратитесь на ресепшен». Техническая причина
(`CONNECTOR_OFFLINE`, `TIMEOUT`, …) гостю **не показывается** — она в журнале.

И отдельно: **устаревшие значения не показываются как актуальные**. Когда связи
нет, элементы уходят в `offline`, а не остаются с последним известным значением
в виде `confirmed`.

⚠️ На текущем стенде все feedback возвращают `false` (§7 прозвона), то есть
«свет выключен» и «GRMS не отвечает» неразличимы. Пока это не решено, комната с
поголовными `false` должна считаться `unavailable`, а не «всё выключено».
Вопрос открыт для ПНР.

## 4. Открытие экрана: чтение feedback'ов

При входе backend **читает feedback'и** доступных каналов (ТЗ §12) — не отдаёт
кэш. Постоянного опроса всех номеров нет: читаем для активных гостевых сессий
и после команд.

Порядок: проверить узел и endpoint → прочитать feedback'и пачкой → собрать
снапшот. Если проверка не прошла — `unavailable`, и чтение не делается.

## 5. Команда

### `POST /api/v1/guest/room/command`

```jsonc
// запрос — и это весь запрос
{ "controlId": "ac.1", "capability": "setpoint", "value": 22 }
```

`capability` нужен для составных элементов: у кондиционера четыре ручки под
одним `controlId`. Для простых элементов поле опускается.

```jsonc
// 202 — принято, подтверждения ещё нет
{ "commandId": "…", "controlId": "ac.1", "state": "pending" }
```

Ответ **202, а не 200**: `status:"true"` от iRidi означает лишь, что команда
принята, но не что оборудование в этом состоянии (ТЗ §12, §7 прозвона).
Подтверждение приходит отдельно — снапшотом.

Ошибки: `403 TRUST_REQUIRED` (нужен step-up), `404 CONTROL_UNKNOWN`,
`409 ROOM_UNAVAILABLE`, `422 VALUE_OUT_OF_RANGE`, `429 RATE_LIMITED`.

Валидация значения — на сервере, по диапазону из переменной типа номера. `26`
для `fan_speed` (диапазон `0-3`) отбивается на backend, а не «как-нибудь»
доезжает до Modbus.

## 6. Подтверждение: цикл перечтения с бэкоффом

**Одного немедленного перечтения недостаточно.** Между «iRidi принял SET» и
«GRMS доехал до оборудования и обновил регистр feedback» проходит время, и оно
не фиксировано. Читать сразу — почти гарантированно прочитать старое значение и
объявить исправную команду неподтверждённой.

Поэтому после успешного SET backend запускает **цикл перечтения в окне**:

```
попытки через:  200 мс → 500 мс → 1 с → 2 с   (окно ~4 с)
```

* feedback совпал с отправленным → `confirmed`, снапшот уходит в WS, цикл
  прекращается досрочно;
* окно вышло, значение не то → `unconfirmed`: элемент **возвращается к
  фактическому прочитанному состоянию**, гостю показывается сообщение о
  невозможности выполнить действие (ТЗ §12);
* всё время цикла элемент в `pending`.

Конкретные числа — предмет калибровки на живом стенде в G3; в контракте
фиксируется форма (несколько попыток с ростом паузы в ограниченном окне) и то,
что она **не** сводится к одному чтению.

Пока команда в `pending`, повторные команды на тот же `controlId`
отбрасываются (`409`), чтобы гость «дробью» не набил очередь.

### Сцены — исключение

У сцен feedback нет (подтверждено прозвоном §8.3: `F_Scene_*` не существует).
Для `capabilities: ["trigger"]` цикла перечтения нет: успешная отправка = успех.
Сцена не имеет состояния и никогда не показывается как «включённая».

### Текущая температура — read-only

`current_temp` приходит только по feedback, команды на неё не принимаются
(`422`). В реестре элементов помечена `readonly`.

## 7. Живое состояние: `WS /ws/v1/guest/room`

Группа — `room.{hotel_id}.{room_id}`, по образцу существующих консьюмеров
(`tracker.*`, `order.*`, `chat.*`).

Сообщение одно, и оно всегда полный снапшот:

```jsonc
{ "type": "room.snapshot", "event": "connected|updated|unavailable",
  "room": { …тело GET /state… } }
```

Снапшот уходит **во все сессии комнаты**, а не только автору команды: в номере
могут быть два телефона, и свет, включённый с одного, обязан появиться на
втором.

Обрыв WS — не повод считать номер недоступным: фронт переподключается и
перечитывает `GET /state`. Восстановление доступности после сбоя фронт
проверяет периодическим опросом `GET /state` (ТЗ §6).

---

## 8. Что фронт не получает никогда

`room_number`, `endpoint`, имя устройства iRidi, `subdevice`, `C_*`, `F_*`,
`requestID`, коды ошибок транспорта, адреса внутренней сети.

Проверяется тестом в G5: снапшот и ответы сериализуются без этих полей.
