# Контракт 4. Реестр элементов управления и capabilities

Фиксированный каталог предметных элементов. Интерфейс собирается из них, а не
из произвольных кнопок и слайдеров (ТЗ §11).

Каталог живёт **в коде** (`backend/apps/grms/catalog.py`), а не в таблице. Как
`MODULE_LABELS` и тарифная сетка: это часть продукта, а не данные отеля. Новый
вид элемента — это новый код на фронте и в адаптере, поэтому строкой в базе он
появиться не может.

## Почему capabilities, а не строки

Фронт и адаптер ветвятся **по capability**, никогда по `kind` и никогда по
`controlId`.

```ts
// так
if (control.capabilities.includes('setpoint')) renderThermostat(control)

// не так
if (control.kind === 'air_conditioner' || control.kind === 'heating') …
```

Причина прямая: ТЗ требует поддержать GRMS других производителей «без изменения
гостевого интерфейса». У другого вендора отопление может оказаться отдельным
элементом с той же ручкой уставки. Ветвление по `kind` заставит править фронт
на каждом новом объекте; ветвление по capability — нет.

Из того же следует: `controlId` (`light.main`, `ac.1`) — **идентификатор, а не
признак типа**. Разбирать его строкой на фронте запрещено.

## 1. Словарь capabilities

| Capability | Тип значения | Направление | Что рисует фронт |
|---|---|---|---|
| `toggle` | `binary` 0/1 | чтение+запись | большой переключатель |
| `trigger` | нет значения | только запись | кнопка-сцена |
| `fan_speed` | `enum` 0–3 | чтение+запись | сегменты Авто/1/2/3 |
| `setpoint` | `range` 16–32 | чтение+запись | кольцо термостата |
| `current_temp` | `range` | **только чтение** | число внутри кольца |
| `position` | `range` 0–100 | чтение+запись | вертикальный слайдер |
| `level` | `range` 0–100 | чтение+запись | кольцо-диммер |

`current_temp` — единственная read-only capability. Команда на неё отбивается
`422` (ТЗ §12).

`position` и `level` заложены в словарь, но на этом объекте не используются:
шторы у GRMS бинарные (`0-Curtain Close, 1-Curtain Open`), диммирование в Excel
отсутствует. Компоненты под них в ките уже есть (`PositionSlider`, `RingDimmer`)
— см. [`../reuse-map.md`](../reuse-map.md).

## 2. Каталог элементов

Колонка «переменные на стенде» — по итогам прозвона
([`../iridi-probe.md`](../iridi-probe.md) §6.3).

| `kind` | Заголовок | Capabilities | Показ | Переменные на стенде |
|---|---|---|---|---|
| `dnd` | Не беспокоить | `toggle` | переключатель | `C_DND` / `F_DND` |
| `mur` | Убрать номер | `toggle` | переключатель | `C_MUR` / `F_MUR` |
| `master_switch` | Мастер-выключатель | `trigger` | кнопка | — (сценой) |
| `light_group` | Группа света | `toggle` | плитка | `C_Light N` / `F_Light N` |
| `curtain` | Шторы | `toggle` (опц. `position`) | плитка | `C_Curtain N` / `F_Curtain N` |
| `curtain_blackout` | Блэкаут-шторы | `toggle` (опц. `position`) | плитка | — |
| `air_conditioner` | Кондиционер | `toggle`\*, `fan_speed`, `setpoint`, `current_temp` | термостат | `C_FCU_*` / `F_FCU_*` |
| `heating` | Отопление | `toggle`\*, `setpoint`, `current_temp` | термостат | — |
| `scene` | Сцена | `trigger` | кнопка | `C_Scene_N`, feedback нет |

\* — обязательная capability элемента; остальные необязательные.

**«—» значит: элемент есть в каталоге, но на этом объекте не включается.**
Тегов `F_Heating*`, `F_Blackout*`, `F_MasterSw` на стенде нет (§8.4 прозвона).
Мастер-выключатель, судя по старому примеру объекта, реализуется сценой
`MASTER_OFF`, а не отдельным каналом.

### Фиксировано у элемента

Вид, иконка, логика, тип значений, способ отображения состояния (ТЗ §11).
Администратор **не** может изменить ни одно из этого — он выбирает элемент,
кладёт в зону, задаёт порядок, связывает с переменными и, при необходимости,
переопределяет заголовок.

### Составные элементы

`air_conditioner` и `heating` — **один** элемент с несколькими capability, а не
набор независимых. Один `controlId`, объект-значение:

```jsonc
{ "controlId": "ac.1", "kind": "air_conditioner",
  "capabilities": ["toggle", "fan_speed", "setpoint", "current_temp"],
  "value": { "on": 1, "fan_speed": 2, "setpoint": 22, "current_temp": 23 } }
```

Иначе фронт собирал бы фанкойл из четырёх кусков, зная, что фанкойл вообще
из чего-то состоит, — а он не должен.

Однотипные элементы ставятся повторно: `ac.1`, `ac.2` (ТИП2 и ТИП3 на стенде
имеют по два фанкойла).

## 3. Правила для каждой capability

### `toggle`
Значение `0|1`. Подтверждение — перечтением feedback (цикл с бэкоффом,
[`guest-api.md`](./guest-api.md) §6).

### `trigger`
Значения нет, состояния нет. Сцена **никогда** не показывается «включённой»:
feedback'а у неё нет (§8.3 прозвона), и подтверждать нечего. Успешная отправка
= успех, цикла перечтения нет.

Отправляемое значение берётся из переменной (`values_on`), обычно `1`; у части
сцен на старом объекте это `0` — значение хранится в маппинге, а не зашито.

### `fan_speed`
`0` — **Авто**, не «выключено» (Excel: `0 -Auto, 1 - Low, 2 - Med, 3 - High`).
Выключение фанкойла — это `toggle`, не `fan_speed: 0`. Путать нельзя: в
интерфейсе «Авто» и «Выкл» — разные вещи.

⚠️ В Excel у `C_FCU_Speed 2` (ТИП2 и ТИП3) описание начинается с `1 -Auto`
вместо `0 -Auto` — вероятная опечатка ПНР. Уточнить в G4 при импорте;
расхождение описаний одной и той же переменной между типами импорт обязан
показать предупреждением.

### `setpoint`
Диапазон из переменной (`16-32`), не зашит на фронте. Значение вне диапазона
отбивается на backend.

### `current_temp`
Только чтение. Показывается внутри кольца термостата. Если переменная не
связана — блок текущей температуры не рисуется вовсе (а не «—» или `0`).

⚠️ На стенде `F_FCU_Temperature 1` возвращает `false`, а не число (§7 прозвона).
Формат живого значения (`"23"`, `"23.5"`, `23`) не подтверждён — вопрос ПНР.

### `position` / `level`
`0–100`. Для штор `0` — закрыто, `100` — открыто. На этом объекте не
используются.

## 4. Совместимость элемента и переменной

Проверяется до публикации (ТЗ §11):

| Capability | Требует `value_kind` | Требует команду | Требует feedback |
|---|---|---|---|
| `toggle` | `binary` | да | да |
| `trigger` | `binary` | да | **нет** |
| `fan_speed` | `enum` | да | да |
| `setpoint` | `range` | да | да |
| `current_temp` | `range` | **нет** | да |
| `position` / `level` | `range` | да | да |

Плюс: диапазон переменной покрывает диапазон capability; одна переменная не
используется дважды; у элемента связаны все обязательные capability.

---

## 5. Что каталог даёт гостевому фронту

Фронт получает на элемент: `controlId`, `kind`, `title`, `capabilities`,
`value`, `range`, `state`, `readonly`. Ничего технического
([`guest-api.md`](./guest-api.md) §8).

`kind` отдаётся **только для иконки и заголовка по умолчанию**. Логика — по
`capabilities`. Это правило проверяется ревью фронта в G5: `kind` не должен
встречаться в условиях, влияющих на поведение.
