# Контракт 3. Конфигурация типа номера

Что хранит тип номера, как имя устройства iRidi выводится для конкретной
комнаты, как конфигурация версионируется и откатывается.
Импорт Excel — G4, конструктор — G4/G6. Здесь только модель данных и правила.

## Зачем тип

Номера с одинаковым составом оборудования собираются в **тип**. Все номера типа
получают один и тот же интерфейс, но обращаются к **разным устройствам iRidi**
(ТЗ §10). Настраивается тип один раз, а не 200 раз по числу комнат.

Прозвон это подтверждает: у ТИП2 (708) и ТИП3 (706) наборы тегов различаются
(2 шторы против 3), а внутри типа — одинаковы.

---

## 1. Состав типа

| Что | Зачем |
|---|---|
| комнаты типа | к какому типу относится физическая комната |
| эталонная комната | на ней тестируют до публикации (ТЗ §11) |
| шаблон имени устройства | как из номера комнаты получить `device` |
| переменные | импортированные `C_*` / `F_*` с диапазонами |
| зоны | спальня, гостиная, ванная |
| элементы интерфейса | что и в каком порядке видит гость |
| маппинг | элемент ↔ переменная |
| опубликованная версия | что реально отдаётся гостю |

Скелет моделей под это — `backend/apps/grms/models.py` (см.
[`../reuse-map.md`](../reuse-map.md), §«Скелет»).

---

## 2. Имя устройства: шаблон + переопределение

Имена устройств на боевом сервере (прозвон §6.2):

```
Modbus TCP Server (Slave mode) 701
Modbus TCP Server (Slave mode) 708
```

Отсюда шаблон типа:

```
Modbus TCP Server (Slave mode) {room}
```

`{room}` подставляется из `Room.number`. Единственная поддерживаемая
подстановка — номер комнаты; выражений и функций в шаблоне нет.

**Переопределение на комнату** обязательно (ТЗ §10): реальные объекты не бывают
идеально регулярными — одна комната после переделки может называться иначе.
Переопределение хранится на связи «комната ↔ тип» и, если задано, полностью
заменяет результат шаблона.

Правила:

* шаблон предлагается системой, но **подтверждается администратором** при
  настройке объекта (ТЗ §10) — не применяется молча;
* перед публикацией имя каждой комнаты **проверяется живым чтением** одного
  безопасного feedback'а. Прозвон показал, что несуществующее устройство
  отвечает `status:"false"` — то есть опечатка в шаблоне ловится до гостя, а не
  после;
* имя устройства собирает **только backend**. С фронта оно не приходит никогда:
  `IR.GetDevice` отдаёт любое устройство проекта, включая служебный `HttpServer`
  (§6.2 прозвона).

---

## 3. Переменные

Переменная — строка из Excel, техническая карта, **не** элемент интерфейса
(ТЗ §8).

```jsonc
{
  "key": "light_1",
  "command": "C_Light 1",          // может отсутствовать (только чтение)
  "feedback": "F_Light 1",         // может отсутствовать (сцены)
  "value_kind": "binary",          // binary | range | enum
  "min": 0, "max": 1,
  "raw_range": "0/1",              // как было в Excel, для разбора спорных случаев
  "description": "0-Lights OFF, 1-Lights ON",
  "subdevice": ""                  // на этом объекте всегда пусто
}
```

`subdevice` хранится, но по умолчанию пуст: `"Custom"` из примеров ТЗ и Postman
на боевом сервере ломает чтение (§8.1 прозвона). Поле оставлено на случай
другого объекта.

Обязательно допускаются оба вырожденных случая:

* **команда без feedback** — сцены (`C_Scene_1`, feedback'а нет — §8.3 прозвона);
* **feedback без команды** — текущая температура (`F_FCU_Temperature 1`).

Из диапазонов Excel:

| `raw_range` | `value_kind` | min–max |
|---|---|---|
| `0/1`, `0-1` | `binary` | 0–1 |
| `0-3` | `enum` | 0–3 (скорость вентилятора) |
| `16-32` | `range` | 16–32 (уставка) |

Разбор полуструктурированный, поэтому `raw_range` хранится как есть, а результат
разбора **подтверждает администратор** (ТЗ §9).

---

## 4. Зоны

Зона — группировка внутри номера: спальня, гостиная, ванная. Создаётся при
необходимости; в простом номере зона одна и в интерфейсе не показывается.

У зоны есть код, локализуемый заголовок и порядок. Элемент принадлежит ровно
одной зоне.

---

## 5. Элементы и маппинг

Элемент интерфейса — экземпляр из фиксированного каталога
([`control-elements.md`](./control-elements.md)), поставленный в тип номера:
вид элемента, зона, порядок, заголовок.

Маппинг связывает **не элемент с переменной**, а **capability элемента с
переменной**. Это принципиально: кондиционер — один элемент, но за ним четыре
переменные.

```jsonc
{
  "element": { "kind": "air_conditioner", "zone": "bedroom", "order": 30 },
  "bindings": {
    "toggle":       "C_FCU_MainSw 1 / F_FCU_MainSw 1",
    "fan_speed":    "C_FCU_Speed 1 / F_FCU_Speed 1",
    "setpoint":     "C_FCU_Setpoint 1 / F_FCU_Setpoint 1",
    "current_temp": "— / F_FCU_Temperature 1"
  }
}
```

Однотипные элементы ставятся повторно (два фанкойла, несколько групп штор) —
ТЗ §11. Различаются `controlId` (`ac.1`, `ac.2`).

### Проверки совместимости (ТЗ §11)

Перед публикацией:

* тип значения capability совпадает с `value_kind` переменной
  (`setpoint` требует `range`, `toggle` требует `binary`);
* диапазон переменной покрывает диапазон capability;
* обязательные capability элемента связаны, необязательные — по желанию;
* `current_temp` связан с переменной **без команды** (иначе read-only нарушен);
* одна переменная не использована в двух элементах;
* элементы с `trigger` (сцены) не требуют feedback.

---

## 6. Версии и публикация

Гость видит **только опубликованную версию**. Правки в конструкторе на живой
номер не влияют, пока не нажата публикация.

```
черновик типа  ──публикация──▶  PublishedConfig v3  ◀── читает гость
                                 PublishedConfig v2  (откат сюда)
                                 PublishedConfig v1
```

Опубликованная версия — **самодостаточный снимок**: зоны, элементы, порядок,
маппинг, диапазоны, шаблон устройства, имена команд/feedback. Она не ссылается
на текущие переменные и элементы, а содержит их копию.

Причина: иначе удаление переменной в черновике молча сломало бы работающую
опубликованную конфигурацию. Снимок делает откат настоящим — вернуться к v2
значит вернуться к тому, что реально работало, а не к «v2 плюс сегодняшние
правки справочников».

Правила:

* публикация делает новую версию, номер растёт, предыдущие сохраняются;
* текущая версия ровно одна на тип;
* откат — публикация копии старой версии новым номером, а не удаление новых;
  история не переписывается;
* публикация и откат пишутся в `AuditLog` (кто, когда, с какой на какую);
* публикация **блокируется**, если не прошли проверки §5 или не пройден тест на
  эталонной комнате.

### Тест на эталонной комнате

До публикации администратор прогоняет конфигурацию на эталонной комнате
(ТЗ §11): каждый элемент читается, при желании — переключается, результат
виден в диагностике. Это единственный момент, когда команда уходит в номер не
от гостя.

⚠️ На текущем стенде такой тест **не пройдёт по подтверждению**: feedback'и не
отдают живых значений (§7 прозвона). До решения вопроса с ПНР тест проверяет
доставку команды (`status:"true"`) и существование тегов, но не подтверждение
состояния.
