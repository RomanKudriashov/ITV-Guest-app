# Контракт 1. Backend ↔ Local Connector

Фиксируется **до** кода: коннектор — отдельный сервис за сетью объекта,
и переписать его «по ходу» нельзя. Реализация — G1.

Опора на прозвон: [`../iridi-probe.md`](../iridi-probe.md). Всё, что там
помечено ⛔, здесь уже учтено.

## Роль коннектора

Коннектор — **транспорт и ничего больше**. Он не знает ни про комнаты, ни про
типы номеров, ни про DND, ни про формат iRidi. Он умеет: держать соединение,
принять готовое задание, проверить его по локальному конфигу, выполнить HTTP
во внутренней сети, вернуть сырой ответ.

Вся специфика iRidi (`request`/`device`/`channel`/`feedback`, нормализация
`status`/`value`, дискриминатор `"undefined"`) живёт в адаптере на backend.
Смена протокола iRidi меняет адаптер, а не коннектор.

Обратное тоже верно: backend **не передаёт IP или полный URL**. Он называет
endpoint по идентификатору (`"iridi"`), а адрес знает только объект.

## Направление связи

Коннектор ходит наружу сам, backend до него дозвониться не может — коробка за
NAT. Поэтому:

* коннектор устанавливает **исходящее WSS** к backend и держит его;
* backend пушит задания в этот сокет;
* коннектор отвечает в него же.

Это ложится на уже существующее: `OnPremNode` (реестр узлов, хэш ключа,
отзыв, `last_seen_at`) и Channels. Подробности переиспользования —
[`../reuse-map.md`](../reuse-map.md).

## 1. Аутентификация и жизнь соединения

### Подключение

```
WSS /ws/v1/onprem/connector
Authorization: Bearer <node_key>
```

Ключ выдаётся при регистрации узла в админке, хранится **хэшем**
(`OnPremNode.key_hash`, sha256), показывается один раз. По ключу backend
находит узел и его отель — узел не знает и не передаёт `hotel_id`.

Ответ на успешное подключение:

```jsonc
{ "type": "connector.hello",
  "node_id": "…", "hotel": "crystal",
  "heartbeat_interval_s": 60,
  "server_time": "2026-08-02T12:00:00+03:00" }
```

Отозванный (`is_revoked`) или неизвестный ключ → закрытие с `4401`.
Переподключение — с джиттером, чтобы после сетевого сбоя весь парк узлов не
пришёл одной волной.

### Heartbeat

Уже существует: `POST /api/v1/onprem/heartbeat` + `OnPremNode.touch()`,
порог `OFFLINE_AFTER_SECONDS = 180` (три пропуска подряд). Оставляем как есть,
добавляем то же самое сообщением в сокете, чтобы живость соединения и живость
процесса не расходились:

```jsonc
// коннектор → backend, раз в heartbeat_interval_s
{ "type": "connector.heartbeat",
  "version": "1.0.3",
  "endpoints": { "iridi": { "reachable": true, "checked_at": "…", "latency_ms": 12 } } }
```

`endpoints.*.reachable` — **результат локальной проверки коннектором**, а не
догадка backend. Именно на это опирается требование ТЗ §6 «доступен ли endpoint
iridi» до показа управления.

Узел считается офлайн, если `last_seen_at` старше 180 с. «Офлайн» здесь
означает ровно «перестал отмечаться» — дозвониться до него мы не можем в
принципе.

## 2. Задание вниз

```jsonc
// backend → коннектор
{
  "type": "connector.request",
  "requestID": "ce3ba8ef-a30b-4812-97c6-37e90ccb4d1c",
  "endpoint": "iridi",
  "method": "POST",
  "path": "/",
  "headers": { "Content-Type": "application/json" },
  "body": {
    "requestID": "ce3ba8ef-a30b-4812-97c6-37e90ccb4d1c",
    "request": "SET",
    "device": "Modbus TCP Server (Slave mode) 201",
    "subdevice": "",
    "channel": "C_Light 1",
    "value": 1
  },
  "timeout_ms": 3000,
  "ttl_ms": 5000
}
```

Замечания, вытекающие прямо из прозвона:

* `method` для чтения — **`POST`**, не `GET`. Сервер игнорирует HTTP-метод и
  смотрит только на `body.request` (§4 прозвона). Это снимает требование ТЗ §7
  «HTTP-клиент коннектора должен поддерживать GET с телом». Коннектор всё же
  **обязан уметь** GET с телом — на другом объекте может стоять другая сборка
  скрипта, — но по умолчанию мы им не пользуемся.
* `subdevice` — пустая строка. `"Custom"` из примеров ТЗ/Postman на боевом
  сервере ломает чтение (§8.1 прозвона).
* `requestID` дублируется на двух уровнях: внешний — корреляция
  backend↔коннектор, внутренний — корреляция внутри ответа iRidi. Значение
  одно и то же, и это осознанно: сквозная диагностика по одному идентификатору.
* `requestID` — строгий **UUIDv4**. Валидируется backend перед отправкой:
  iRidi возвращает его эхом без экранирования, и произвольная строка ломает
  JSON ответа или подмешивает в него поля (§3 прозвона).

## 3. Ответ вверх

Коннектор возвращает **сырой ответ, не разбирая его**:

```jsonc
{
  "type": "connector.response",
  "requestID": "ce3ba8ef-…",
  "ok": true,                       // транспорт отработал; НЕ «команда удалась»
  "status_code": 200,
  "headers": { "Content-Type": "text/json" },
  "raw_body": "{ \"requestID\" : \"ce3ba8ef-…\", \"status\" : \"true\" }",
  "duration_ms": 87
}
```

`raw_body` — **строка**, а не разобранный объект. Причина: iRidi собирает ответ
конкатенацией строк и при некоторых значениях `requestID` отдаёт невалидный
JSON. Разбор — задача адаптера, и он должен видеть исходный текст, чтобы
положить его в журнал как есть.

`ok: true` при `status_code: 200` не означает успеха команды: iRidi **всегда**
отвечает 200, а неуспех кладёт в тело (§2 прозвона).

## 4. Ошибки

Коннектор не выполнил запрос:

```jsonc
{ "type": "connector.response", "requestID": "…", "ok": false,
  "error": { "code": "ENDPOINT_UNREACHABLE", "message": "connection refused" },
  "duration_ms": 3002 }
```

Полный набор кодов — он же набор различаемых причин из ТЗ §6:

| Код | Кто ставит | Что видит инженер в админке |
|---|---|---|
| `CONNECTOR_OFFLINE` | backend (узла нет в сокете) | коннектор не подключён |
| `ENDPOINT_UNKNOWN` | коннектор | endpoint не зарегистрирован на объекте |
| `ENDPOINT_UNREACHABLE` | коннектор | iRidi недоступен |
| `TIMEOUT` | коннектор | превышен тайм-аут |
| `REQUEST_REJECTED` | коннектор | метод/путь/размер вне allowlist |
| `BAD_RESPONSE` | адаптер backend | iRidi вернул некорректный ответ |
| `DEVICE_NOT_FOUND` | адаптер backend | устройство не найдено |
| `CHANNEL_NOT_FOUND` | адаптер backend | канал не найден |
| `TTL_EXPIRED` | backend | ответ пришёл после истечения TTL |

Первые пять — транспортные, ставит коннектор. Следующие три ставит адаптер,
разбирая `raw_body`; коннектор про них не знает.

Разделение `DEVICE_NOT_FOUND` / `CHANNEL_NOT_FOUND` возможно **только на
чтении** (§6.1 прозвона): `status:"false"` → нет устройства,
`value:"undefined"` → нет тега. На записи iRidi отдаёт `status:"false"` в обоих
случаях — адаптер ставит `DEVICE_OR_CHANNEL_NOT_FOUND`. Это ограничение
протокола, а не недоделка.

Гостю ни один из этих кодов не показывается — только «Управление номером
временно недоступно» (ТЗ §6). Коды живут в журнале и админке.

## 5. TTL и «поздние» ответы

`ttl_ms` — от момента постановки задания. Ответ, пришедший позже, **отбрасывается
и не применяется к состоянию**, но в журнал пишется с пометкой `TTL_EXPIRED`.

Это прямое требование ТЗ §6: «старые команды после восстановления связи не
выполняются». Без TTL связь, вернувшаяся через минуту, вывалила бы в номер
очередь накопленных команд.

Правило: `ttl_ms > timeout_ms`. Задания в очереди на отключённый узел **не
копятся** — если узла нет в сокете, backend отвечает `CONNECTOR_OFFLINE` сразу,
не ожидая его возвращения.

## 6. Локальный конфиг коннектора

Живёт **на объекте**, backend его не редактирует и не читает:

```jsonc
{
  "backend_url": "wss://crystal.guest.example.com/ws/v1/onprem/connector",
  "node_key_file": "/etc/itv-connector/key",
  "heartbeat_interval_s": 60,
  "max_concurrent_requests": 8,
  "endpoints": {
    "iridi": {
      "baseUrl": "http://10.10.20.15:1085",
      "allowedMethods": ["GET", "POST"],
      "allowedPaths": ["/"],
      "timeoutMs": 3000,
      "maxRequestBytes": 8192,
      "maxResponseBytes": 65536,
      "followRedirects": false
    }
  }
}
```

* `max_concurrent_requests: 8` — скрипт iRidi поднимает сервер с
  `max_http_clients = 50` на **весь объект**. Восемь на узел оставляет запас.
* `allowedPaths: ["/"]` — сам iRidi путь игнорирует (§4 прозвона), но allowlist
  нужен: endpoint'ы универсального коннектора не ограничиваются iRidi, дальше
  через него пойдут замки и другие HTTP-API.
* `followRedirects: false` — по умолчанию запрещены (ТЗ §16). Редирект — способ
  увести запрос на адрес вне allowlist.
* Секреты (`node_key`, авторизация endpoint'ов) в журнал не пишутся.

Запрос к незарегистрированному endpoint отбивается на коннекторе
(`ENDPOINT_UNKNOWN`) — даже если backend его прислал. Коннектор не доверяет
backend в вопросе адресов: это последний рубеж между облаком и внутренней сетью
объекта.

## 7. Что коннектор НЕ делает

* не формирует команды iRidi и не знает их формата;
* не разбирает и не нормализует ответ;
* не кэширует состояния и не опрашивает оборудование по своей инициативе;
* не хранит соответствие «комната → устройство»;
* не ходит к endpoint'ам, которых нет в его локальном конфиге.
