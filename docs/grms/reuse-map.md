# Карта переиспользования: GRMS встраивается, а не пристраивается

Требование к модулю — «органично, не сбоку». Ниже по каждому куску: что уже
есть, что берём, что достраиваем и почему именно так.

Итог: **семь из восьми несущих механизмов уже built** — реестр модулей, реестр
он-прем узлов с heartbeat, комнаты с QR, WS-снапшоты, журнал, RLS, UI-кит.
Нового инфраструктурного кода в G0 нет вообще; в G1–G6 достраиваются адаптер,
конструктор и гостевой экран.

---

## 1. Комната и QR — `hotels.Room` + `apps/hotels/qr.py`

Есть: `Room` (тенантная, `hotel + number` уникальны, `floor`, `zone`,
`is_active`), генерация QR (`qr_svg`, `qr_png`, печатный лист `qr_sheet_html`),
диплинк `/r/{room}`, гостевая сессия с `GuestSession.room`.

**Берём как есть. Новых QR не заводим** — гость сканирует один код на весь
сервис, а не отдельный «GRMS-QR». Резолв `QR → комната → тип → конфиг` целиком
опирается на существующую цепочку `GuestSession.room`.

Достраиваем: связь «комната ↔ тип номера». Сделана **не** полем на `Room`, а
отдельной таблицей `RoomTypeRoom` в `apps.grms`:

* `hotels` не начинает зависеть от `grms` — направление зависимости остаётся
  `grms → hotels`, миграции не переплетаются;
* появляется естественное место для **переопределения имени устройства на
  комнату** (ТЗ §10) — оно принадлежит именно связи, а не комнате и не типу;
* модуль снимается целиком, не оставляя мёртвой колонки в `hotels_room`.

## 2. WS-снапшот — `apps/realtime/consumers.py`

Есть: `TrackerConsumer`, `GuestOrderConsumer`, `GuestChatConsumer`. У всех один
и тот же приём — группа на сущность (`tracker.{hotel}.{point}`,
`order.{hotel}.{order}`), **полный снапшот** на подключение и на каждое событие,
никаких дельт.

**Берём приём целиком.** `RoomStateConsumer`, группа `room.{hotel}.{room}`,
сообщение `room.snapshot` — ровно тот же контракт, что у `order.snapshot`.

Почему это точное попадание, а не натяжка: состояние номера **обязано** уходить
во все сессии комнаты. В номере два телефона, свет включили с одного — второй
должен показать это без перезагрузки. Полный снапшот здесь не «так уж вышло», а
единственный вариант: гость подключается в произвольный момент, и склеивать
дельты ему не из чего.

## 3. Журнал команд → диагностика инженера — `core.AuditLog`

Есть: `AuditLog` с `action`, `object_type`/`object_id`, `payload` (JSON),
`actor_type` (в т.ч. `guest`), `hotel` nullable, индекс `(hotel, -created_at)`,
метод `record()`.

**Берём как журнал команд.** Диагностика инженера из ТЗ §14 (комната, элемент,
устройство, command/feedback, отправленное значение, ответ, время, статус)
собирается выборкой по `action LIKE 'grms.%'` — отдельная таблица не нужна:

```python
AuditLog.record(
    "grms.command",
    actor_type=AuditLog.ActorType.GUEST,
    object_type="grms.control", object_id=element_id,
    payload={"requestID": …, "room": "701", "controlId": "light.main",
             "device": "Modbus TCP Server (Slave mode) 701",
             "command": "C_Light 1", "feedback": "F_Light 1",
             "sent": 1, "raw_response": "…", "duration_ms": 87,
             "result": "confirmed"},
)
```

`raw_response` кладём **строкой как есть** — iRidi собирает ответ конкатенацией
и умеет отдать невалидный JSON (§3 прозвона). Журнал обязан хранить то, что
реально пришло.

Действия: `grms.command`, `grms.read`, `grms.publish`, `grms.rollback`,
`grms.pin_attempt`. Секреты и PIN в `payload` не попадают (ТЗ §16).

Если по объёму записей это станет узким местом — выносим в свою таблицу в G3.
Заводить её заранее незачем: `AuditLog` уже тенантный, уже под RLS, уже
индексирован под «показать последние по отелю».

## 4. UI-кит управления номером — `frontend/src/kit/room.tsx`

Есть, из R1, готовые компоненты (355 строк):

| Компонент | Под какую capability |
|---|---|
| `Thermostat` | `setpoint` + `current_temp` |
| `RingDimmer` | `level` |
| `PositionSlider` | `position` |
| `LargeToggle` | `toggle` (DND, MUR, мастер) |
| `ActionButton` / `SceneButton` | `trigger` |
| `RunningIndicator` | состояние `pending` — «в процессе» |
| `OfflineIndicator` | состояние `offline` — «нет связи» |

**Кит покрывает весь словарь capabilities из
[`contracts/control-elements.md`](./contracts/control-elements.md).** Ни одного
нового компонента под этот объект не требуется: `RingDimmer` и `PositionSlider`
на стенде не понадобятся (шторы бинарные, диммирования нет), но лежат готовыми.

Отдельно ценно, что `RunningIndicator` и `OfflineIndicator` уже нарисованы: это
ровно два состояния из ТЗ §6/§12, которые обычно доделывают в последний момент,
и именно из-за них гостю показывают устаревшие значения как актуальные.

Гостевой экран собирается в G5 из этих компонентов, ветвясь **по
`capabilities`**, а не по `kind`.

## 5. Реестр модулей — `apps/hotels/module_registry.py`

Есть: `HotelModule.Code.ROOM_CONTROL = "room_control"` («Управление номером
(GRMS)»), заведён в тарифной сетке (`tariffs.py`), локализован в
`vocabularies.py` (ru/en/ar/zh), гейтит CMS-навигацию через
`enabled_module_codes()`.

**Ничего добавлять не нужно — код модуля уже существует.** GRMS гейтится им же:
модуль выключен → экрана в CMS нет, гостю управление не отдаётся.

Дизайн-карта это уже предусматривает: «GRMS → в номерной фонд», «Позже — плитка
"Мой номер" (климат, шторы, свет)». То есть место в интерфейсе для модуля
заложено заранее, и мы встаём в него, а не рядом.

## 6. Он-прем узел = Local Connector — `apps/hotels/onprem.py`

Есть, из R6, и это самое крупное попадание:

* модель `OnPremNode` с `Purpose.GRMS` — **назначение «Управление номером» уже
  заведено**;
* ключ хранится **хэшем** (sha256), показывается один раз;
* `register_node` / `revoke_key` / `reissue_key` / `touch`;
* heartbeat уже работает: `POST /api/v1/onprem/heartbeat` (`api/onprem.py`);
* `OFFLINE_AFTER_SECONDS = 180`, `seconds_since_seen`;
* админские экраны реестра узлов (`api/platform.py`);
* поиск узла по хэшу ключа поверх тенантов — узел не знает `hotel_id` и не
  должен.

Комментарий в самой модели уже описывает нужную нам архитектуру дословно:
«облако не может достучаться до коробки внутри сети отеля… направление связи
обратное». Требования ТЗ §15 (автозапуск, переподключение, heartbeat, отдельный
конфиг и журнал, сообщать доступность) ложатся на это без переделки.

**Достраиваем в G1 только транспорт заданий:** WSS-эндпоинт
`/ws/v1/onprem/connector` и доставку `endpoints.*.reachable` внутри heartbeat.
Регистрация, ключи, отзыв, «жив/не жив» — берутся готовыми.

## 7. Тенантная изоляция — `apps/core/rls.py` + `tenant_tables.py`

Есть: `enable_sql()` с `ENABLE` **и `FORCE ROW LEVEL SECURITY`**, политика
`tenant_isolation` по `app.current_hotel`, fail-closed (нет контекста → нет
строк), реестр `TENANT_TABLES`, тест-сторож `tests/test_rls_coverage.py`,
находящий любую модель с `hotel` без политики.

**Все новые таблицы GRMS закрыты RLS FORCE миграцией** —
`apps/core/migrations/0014_rls_grms.py`, по образцу `0013_rls_onprem_node.py`,
плюс семь имён в `TENANT_TABLES`.

Вариант «спрятать конфигурацию в `hotel.settings`» здесь не проходит, и это не
формальность: конфигурация типа номера — это карта того, какие команды в какое
физическое оборудование уходят. JSON-поле не даёт ни ссылочной целостности с
`Room`, ни версий с откатом, ни выборки для диагностики, ни — главное — строчной
изоляции. Ошибка в скоупе на JSON-поле означает управление чужим номером.

Сторож `test_rls_coverage` делает это самоподдерживающимся: забыть добавить
таблицу нельзя, тест упадёт.

## Скелет схемы (G0) — `backend/apps/grms/`

Только модели из контрактов, без логики.

| Модель | Таблица | Что держит |
|---|---|---|
| `RoomType` | `grms_room_type` | тип: код, название, шаблон имени устройства |
| `RoomTypeRoom` | `grms_room_type_room` | комната ↔ тип, эталонная, переопределение имени |
| `Zone` | `grms_zone` | зоны номера, порядок |
| `Variable` | `grms_variable` | `C_*`/`F_*`, `value_kind`, диапазон, `raw_range`, `subdevice` |
| `ControlElement` | `grms_control_element` | элемент каталога в типе: `kind`, зона, порядок, заголовок |
| `Binding` | `grms_binding` | **capability элемента** ↔ переменная |
| `PublishedConfig` | `grms_published_config` | версия, снимок конфигурации, текущая/откат |

Каталог видов элементов и capabilities — **в коде**, `apps/grms/catalog.py`, не
в таблице (обоснование — [`contracts/control-elements.md`](./contracts/control-elements.md)).

### Одно отступление от буквы задания — `Binding`

В задании `Binding` описан как «элемент ↔ переменная в типе + зона + порядок».
В скелете зона и порядок стоят на `ControlElement`, а `Binding` связывает
**capability элемента** с переменной.

Причина в данных, а не в стиле: кондиционер — один элемент интерфейса, но за ним
четыре переменные (`C_FCU_MainSw`, `C_FCU_Speed`, `C_FCU_Setpoint`,
`F_FCU_Temperature`). Связь «элемент ↔ одна переменная» такой элемент выразить
не может — пришлось бы либо резать фанкойл на четыре независимых элемента (и
тогда термостат собирает фронт, чего он делать не должен), либо складывать
несколько переменных в одно поле. Зона и порядок при этом — свойства
размещения элемента, и на связи с переменной им делать нечего.
