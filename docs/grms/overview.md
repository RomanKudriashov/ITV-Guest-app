# Управление номером: как это работает целиком

Собрано из отчётов прогонов, шапок файлов и прозвона. Каждое утверждение помечено, чем оно
доказано: **[тест]** — проверяется прогоном, **[прозвон]** — проверено на живом железе один раз,
**[допущение]** — не проверено ничем.

Подробный разбор доказательств — `docs/audit/evidence.md`.

---

## 1. Цепочка

```
Гость (браузер)
   │  POST /api/v1/guest/room/command  {"controlId": "light.main", "value": 1}
   │  Ни устройства, ни канала, ни адреса — только идентификатор элемента.   [тест]
   ▼
Backend
   │  сессия → отель → комната → тип номера → опубликованная конфигурация
   │  проверка допустимости → адаптер iRidi строит тело запроса
   │  конверт {requestID, endpoint, method, path, body}                      [тест]
   ▼
Local Connector (на объекте, соединение исходящее)
   │  по идентификатору endpoint находит локальный адрес
   │  проверяет метод и путь по своему списку, выполняет запрос             [тест]
   ▼
iRidi HTTP-сервер (внутренняя сеть)
   │  C_* — команда, F_* — обратная связь
   ▼
GRMS → оборудование
```

**Гость технических параметров не получает вообще** — ТЗ §13. Подмена `controlId` не даёт
управлять соседней комнатой: устройство определяется по сессии, а не по телу запроса. **[тест]**

## 2. Три состояния элемента

Ровно три, и они означают разное:

| Состояние | Когда | Что видит гость |
|---|---|---|
| `confirmed` | feedback прочитан, значение известно | фактическое положение |
| `pending` | команда в полёте: HTTP уже ответил, подтверждение ещё идёт | «в процессе», элемент заблокирован |
| `offline` | feedback не читается | значение не показывается вовсе |

Плюс состояние всего экрана: `availability: online | unavailable`. При `unavailable` управление не
показывается работающим, а гостю выводится текст про ресепшен (ТЗ §6). **[тест]**

`pending` живёт не в базе, а в Redis (`services/inflight.py`): это факт о нашем незавершённом
действии, а не о номере. Оттуда же дедуп повторного тапа и автопротухание — если воркер умер,
элемент вернётся к фактическому значению, а не застрянет. **[тест]**

**Важное различение.** «Все каналы вернули `false`» трактуется как **недоступность**, а не как
«всё выключено». Разница видна гостю: во втором случае он бы увидел выключенный свет там, где
связи просто нет. Это решение — см. `docs/decisions.md`. **[тест]**

## 3. Что подтверждено прозвоном живого iRidi

Прозвон 2026-08-02, стенд `80.64.105.68:1085`, детали — `docs/grms/iridi-probe.md`.

| Утверждение | Статус |
|---|---|
| HTTP-сервер жив, отвечает | **[прозвон]** |
| Пространство имён устройств и тегов совпадает с Excel почти полностью | **[прозвон]** |
| `subdevice` обязан быть пустым, а не «Custom» | **[прозвон]**, поправка G0 |
| Чтение идёт POST, а не GET с телом (вопреки ТЗ §7) | **[прозвон]**, поправка G0 |
| Неизвестный канал отличается от неизвестного устройства | **[прозвон]** |
| SET принимается сервером | **[прозвон]** |
| **Feedback НЕ отдаёт живых значений: все 120 прочитанных тегов вернули `false`** | **[прозвон]** |

Последняя строка — главная. **Цикл подтверждения командой на этом стенде проверить нельзя.**
Он проверяется на эмуляторе, который отдаёт живой feedback. Что реальное железо на объекте
поведёт себя так же — **[допущение]**.

Шесть тестов против боевого стенда лежат в `tests/grms/services/test_grms_real_server.py` и по
умолчанию пропускаются (`GRMS_REAL_SERVER=1`). Что именно они докажут при включении — разобрано в
`docs/audit/evidence.md` §4.

## 4. Эмулятор: зачем он и чем он врёт

Эмулятор в Docker повторяет протокол iRidi, **включая его странности**: строковые `status` и
`value`, конкатенированный ответ, дискриминатор `"undefined"`. Он врёт так же, как настоящий, —
иначе на нём нельзя было бы поймать ошибки разбора.

Одно отличие намеренное: **эмулятор отдаёт живой feedback, а боевой стенд — нет**. Без этого цикл
подтверждения (ТЗ §12) не проверялся бы вовсе.

## 5. Конфигурация номера

1. **Импорт Excel** от команды ПНР: типы номеров, эталонная комната, список комнат, путь к
   устройству, команды `C_*`, каналы `F_*`, диапазоны. Импорт не создаёт интерфейс — он даёт набор
   технических переменных. Предупреждения при неоднозначностях — ТЗ §9. **[тест]**
2. **Сборка интерфейса** из готовых предметных элементов (не из произвольных кнопок): каталог в
   `apps/grms/services/catalog.py` — 9 видов. **[тест]**
3. **Маппинг** элемента на команду и feedback; проверка совместимости с диапазоном. **[тест]**
4. **Публикация версии** с возможностью отката. Снимок самодостаточен: откат к v2 возвращает v2,
   а не «v2 плюс сегодняшние правки справочников». **[тест]**

Ветвление во фронте — **по capability, никогда по kind** (ТЗ §1: подключить другой GRMS без правки
интерфейса). Элемент объявляет, что умеет — `toggle`, `fan_speed`, `setpoint`, `current_temp`,
`position`, `trigger`.

### Каталог элементов

`dnd`, `mur`, `master_switch`, `light_group`, `curtain`, `curtain_blackout`, `air_conditioner`,
`heating`, `scene`.

Два замечания из кода, оба важны для приёмки:

- **`master_switch` на объектах реализуется сценой** (`MASTER_OFF`), а не отдельным каналом:
  тега `F_MasterSw` на стенде нет.
- **Шторы бинарные** (0 — закрыть, 1 — открыть). `position` — задел под приводы с
  позиционированием, на этом объекте не используется.

## 6. План номера

Геометрия зон хранится **в процентах и в конфигурации**, а не в коде: план — картинка комнаты,
и координаты зон принадлежат объекту, а не программе. Зоны прямоугольные со скруглением;
полигональных нет.

Ночной кадр (номер с выключенным светом) **считается из светлого**, а не рисуется отдельно:
второй кадр пришлось бы заказывать дизайнеру на каждый тип номера. Гашение источников света —
серверный проход по картинке с ограничениями, названными в `apps/grms/services/nightframe.py`.
На чужих рендерах (не наших демо) проход **[не проверен]**.

## 7. Чего в цепочке нет

| Чего нет | Следствие |
|---|---|
| Постоянного опроса всех номеров | состояния читаются для активных сессий и после команд — так и в ТЗ §12 |
| Живого feedback на боевом стенде | подтверждение команд на объекте непроверяемо до пусконаладки |
| Полигональных зон | сложную планировку приходится описывать прямоугольниками |
| Экрана диагностики инженера | журнал пишется (`AuditLog`, выборка `grms.%`), экрана нет — ТЗ §14 |
| PMS | уровень доверия `pms_verified` оставлен пустым слотом, см. `docs/audit/pms.md` |
