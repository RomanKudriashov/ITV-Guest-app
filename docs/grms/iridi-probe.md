# Прозвон боевого iRidi — 80.64.105.68:1085

Дата прозвона: **2026-08-02**. Стенд отвечал всё время прозвона.
Прозвон выполнен с рабочей машины через интернет (не из сети объекта), метод —
`curl` + скрипты на `http.client`. Все сырые запросы/ответы ниже приведены
дословно.

Итог одной строкой: **HTTP-сервер iRidi жив, пространство имён устройств и тегов
реально и совпадает с Excel почти полностью, НО ни один feedback не отдаёт живого
значения — все 120 прочитанных тегов вернули `false`.** Подтверждение команд по
feedback (ТЗ §12) на этом стенде проверить нельзя. Подробности — в §6 и §7.

---

## 1. Доступность и базовое поведение

```
$ nc -z -v -w 5 80.64.105.68 1085
Connection to 80.64.105.68 port 1085 succeeded!

$ curl -s -m 10 -o /dev/null -w "connect=%{time_connect} http=%{http_code}\n" http://80.64.105.68:1085/
connect=0.005349 http=200
```

Заголовки ответа (пустое тело, POST):

```
HTTP/1.1 200 OK
Content-Length: 34
Connection: Keep-Alive
Content-Type: text/json
Data: Mon, 26 Jun 2017 11:15:14 GMT
Server: iRidium Server.1.7
Charset: utf-8

{"requestID":null, "status":false}
```

Заголовок `Data:` с датой 2017 года — статическая строка из скрипта
(`Iridi HTTP server JS.txt`, строка 31), а не время ответа. На дату ответа
опираться нельзя. `Server: iRidium Server.1.7` — тоже из скрипта (там записано
`"iRidium Server\1.1.7"`, где `\1` съелся как управляющий символ).

Задержка с рабочей машины через интернет: **min/avg/max = 60 / 91 / 306 мс**
(30 запросов в одном keep-alive-соединении). Из сети объекта будет заметно
меньше, но 3 с тайм-аута из ТЗ §4 — запас достаточный.

## 2. Подтверждённые квирки

| Квирк | Статус | Доказательство |
|---|---|---|
| Всегда HTTP 200, ошибка только в теле | **подтверждён** | все запросы ниже, включая мусорное тело и несуществующее устройство |
| `status` и `value` — строки | **подтверждён** | `{ "requestID" : "...", "status" : "true", "value" : "false" }` |
| `requestID` возвращается эхом | **подтверждён** | см. §3 |
| Общий буфер ответа → нужна корреляция по `requestID` | **не воспроизвёлся**, но требование остаётся | см. §5 |

### Две РАЗНЫЕ формы ответа

Это важнее, чем «status строкой». Форм ответа две, и типы в них не совпадают:

```jsonc
// A. «плохой запрос» — тело не распарсилось / нет request|device / request не GET|SET
{"requestID":null, "status":false}          // status — BOOLEAN, requestID — null

// B. любой распознанный запрос
{ "requestID" : "abc", "status" : "false" }             // status — СТРОКА
{ "requestID" : "abc", "status" : "true", "value" : "false" }
```

Форма A собирается через `JSON.Stringify` (строка 16 скрипта), форма B —
конкатенацией строк (строки 22–26). Отсюда и разнотипность. Нормализатор в
адаптере обязан принимать обе.

## 3. `requestID` возвращается БЕЗ экранирования — JSON-инъекция

Скрипт клеит ответ строками: `'{ "requestID" : "' + id + '", "status" : "'`.
`id` не экранируется. Проверено:

```
$ curl -X GET -d '{"requestID":"a\" , \"injected\" : \"yes","request":"GET",
                   "device":"Modbus TCP Server (Slave mode) 701","subdevice":"","feedback":"F_DND"}'
{ "requestID" : "a" , "injected" : "yes", "status" : "true", "value" : "false" }
```

Лишнее поле `injected` уехало в ответ — тело ответа управляется содержимым
`requestID`. Кавычка/обратный слэш в `requestID` ломает JSON целиком.

**Требование к адаптеру:** `requestID` генерирует backend и он обязан быть
строгим UUIDv4 (`^[0-9a-f-]{36}$`), проверяться перед отправкой. Ничто
управляемое гостем не должно попадать в это поле никогда.

Смежный случай — `requestID` вообще не передан:

```
$ ... -d '{"request":"GET","device":"NoSuchDevice","feedback":"F_X"}'
{ "requestID" : "undefined", "status" : "false" }
```

Возвращается строка `"undefined"`, а не `null`. Адаптер обязан считать такой
ответ некоррелируемым и отбрасывать.

## 4. HTTP-метод и путь игнорируются полностью

Скрипт смотрит только на поле `request` в теле, а не на HTTP-метод
(`in_sRequestType` в колбэке не используется). Проверено:

```
POST + "request":"GET"    -> { "requestID" : "m1", "status" : "true", "value" : "false" }   ✅ работает
GET  + "request":"SET"    -> { "requestID" : "m2", "status" : "false" }                     обработан как SET
PUT  + "request":"GET"    -> { "requestID" : "m3", "status" : "true", "value" : "false" }   ✅ работает
lowercase "request":"get" -> {"requestID":null, "status":false}                             ❌ регистрозависимо
```

Путь тоже игнорируется — `/`, `/anything`, `/api/v1/x` дают одинаковый ответ.
`Content-Type` не обязателен: запрос без него обрабатывается нормально.

### Практическое следствие — можно отказаться от «GET с телом»

ТЗ §7 требует, чтобы HTTP-клиент коннектора умел GET с телом, и это
неудобное требование (часть клиентов и прокси такое режут). Прозвон показал,
что **сервер одинаково принимает чтение по POST**. Все инвентаризационные
прогоны в §6 сделаны именно POST'ом.

**Предлагаю в контракте зафиксировать POST для обеих операций**, а `GET с телом`
оставить как опциональную возможность коннектора для совместимости. Это снимает
требование к HTTP-клиенту и не меняет ничего на стороне iRidi. Решение требует
подтверждения — на другом объекте скрипт iRidi может быть иной версии.

## 5. Гонка на общем буфере ответа — не воспроизвелась

`l_oResponse` в скрипте — модульный синглтон: колбэк пишет в него и возвращает
его же. Теоретически два одновременных запроса могут разъехаться.

Проверка: 150 параллельных запросов, половина к существующему устройству
(ответ с `value`), половина к несуществующему (ответ без `value`) — то есть
структурно различимые ответы, у каждого свой `requestID`.

```
--- 150 requests: ok=150 id-crossed=0 shape-crossed=0 err=0
keep-alive 30 reqs on 1 conn: crossed=0
```

Расхождений нет: скриптовый движок iRidium однопоточный, колбэк отрабатывает
целиком до следующего.

**Вывод:** корреляцию строго по `requestID` из тела оставляем как обязательную
(защита в глубину — буфер общий, и поведение под нагрузкой на другой версии
прошивки не гарантировано), но известной активной гонки на этом стенде нет.

## 6. Реальные устройства и каналы на сервере

### 6.1 Как определяется существование

Найден надёжный дискриминатор, которого нет в документации:

| Ответ | Значит |
|---|---|
| `status:"false"` на GET | **устройства нет** (`IR.GetDevice` вернул falsy) |
| `status:"true"`, `value:"undefined"` | устройство есть, **тега нет** |
| `status:"true"`, `value:<иное>` | устройство и тег есть, значение — `value` |
| `status:"false"` на SET | нет устройства **или** нет командного канала |

То есть на чтении «нет устройства» и «нет канала» различимы, на записи — нет.
Это ровно те два случая, которые ТЗ §6 требует различать в админке
(«устройство или канал не найден»), поэтому:

**Требование к адаптеру:** строку `"undefined"` в `value` трактовать как
`CHANNEL_NOT_FOUND`, а не как значение. Иначе элемент интерфейса покажет
«undefined» как состояние.

### 6.2 Найденные устройства

Перебор по шаблону `Modbus TCP Server (Slave mode) <N>`:

**Есть (15):** `201, 202, 203, 301, 401, 415, 501, 601, 701, 702, 703, 704, 706, 708, 710`

**Нет:** `101, 705, 707, 709, 801, 901` — список не «всё подряд», а настоящий.

Дополнительно существует устройство **`HttpServer`** — это сам HTTP-сервер из
скрипта. `IR.GetDevice` отдаёт любое устройство проекта, включая служебные:

```
EXISTS: HttpServer => { "requestID" : "e16892", "status" : "true", "value" : "undefined" }
```

**Требование безопасности:** имя устройства формирует backend по шаблону типа
номера; произвольное имя от клиента до iRidi доходить не должно. Иначе гость
дотянется до служебных устройств проекта iRidi.

Имена из старых примеров **не существуют**: `Room 415`, `SHUN_1_2`,
`Modbus TCP Server (Slave mode) Network` — все дают `status:"false"`.
Файл `пример запроса к Iridi для комнаты.txt` описывает другой объект и как
справочник по именам на этом стенде неприменим.

### 6.3 Инвентаризация тегов по эталонным комнатам

Прочитаны все правдоподобные `F_*` (42 имени) на трёх эталонных комнатах из Excel.

**ТИП1 — `Modbus TCP Server (Slave mode) 701`, тегов 19:**
`F_DND`, `F_MUR`, `F_Light 1…12`, `F_Curtain 1`,
`F_FCU_MainSw 1`, `F_FCU_Speed 1`, `F_FCU_Setpoint 1`, `F_FCU_Temperature 1`

**ТИП2 — `Modbus TCP Server (Slave mode) 708`, тегов 24:**
`F_DND`, `F_MUR`, `F_Light 1…11`, `F_Curtain 1…3`,
`F_FCU_MainSw 1–2`, `F_FCU_Speed 1–2`, `F_FCU_Setpoint 1–2`, `F_FCU_Temperature 1–2`

**ТИП3 — `Modbus TCP Server (Slave mode) 706`, тегов 24:**
`F_DND`, `F_MUR`, `F_Light 1…12`, `F_Curtain 1…2`,
`F_FCU_MainSw 1–2`, `F_FCU_Speed 1–2`, `F_FCU_Setpoint 1–2`, `F_FCU_Temperature 1–2`

**Отсутствуют на всех трёх:** `F_Scene_1`, `F_Scene_2`, `F_Heating 1`,
`F_Blackout 1`, `F_MasterSw`, а также `F_FCU_* 3` и лишние `F_Light`/`F_Curtain`.

### 6.4 Командные каналы `C_*` — прозвонены выборочно, намеренно

Существование `C_*` определяется только реальной записью — «пробного» чтения
для команд у протокола нет. Поэтому сплошной перебор `C_*` означал бы
физическое дёрганье света, штор и DND в реальных номерах.

Прозвонен минимум, на устройстве `202` (не эталонная комната ни одного типа),
самым безобидным каналом — уставкой температуры:

```
SET C_FCU_Setpoint 1 = 24   -> { "status" : "true" }     канал существует
SET C_FCU_Setpoint 1 = 25   -> { "status" : "true" }
SET C_FCU_Setpoint 1 = "24" -> { "status" : "true" }     строка принимается как и число
SET C_NOPE 99      = 1      -> { "status" : "false" }    неизвестный канал отбивается
SET (без ключа channel)     -> { "status" : "false" }
SET на NoSuchDevice         -> { "status" : "false" }
```

Соглашение `C_`/`F_` подтверждено, отбой неизвестного канала подтверждён.
Записанное значение уставки на устройстве 202 — `"24"`; прежнее значение
прочитать было нельзя (см. §7), поэтому вернуть его точно не удалось. Учитывая
§7, запись физически никуда не доехала.

Полную инвентаризацию `C_*` предлагаю делать на объекте, вместе с ПНР, когда
можно смотреть на оборудование, — либо в G2 на эмуляторе.

## 7. ⛔ Главное расхождение: feedback не отдаёт живых значений

Каждый существующий тег на **каждом** устройстве возвращает `"false"`.
Сплошная проверка 15 устройств × 8 базовых тегов:

```
value distribution across 120 reads (15 devices x 8 tags):
   'false'      120

NON-false/undefined values: 0
```

Ни одного числа. В частности `F_FCU_Temperature 1` — текущая температура —
тоже `"false"` на всех 15 устройствах, хотя обязана быть числом 16–32.

Проверка «SET → перечтение» на устройстве 202:

```
GET F_FCU_Setpoint 1      -> value "false"
SET C_FCU_Setpoint 1 = 24 -> status "true"      команда принята
GET F_FCU_Setpoint 1      -> value "false"      НЕ ИЗМЕНИЛОСЬ
SET C_FCU_Setpoint 1 = 25 -> status "true"
GET F_FCU_Setpoint 1      -> value "false"      НЕ ИЗМЕНИЛОСЬ
```

**Толкование:** HTTP-слой iRidi и пространство имён тегов живы, но за ними нет
данных — Modbus-обмен с GRMS не идёт либо slave отдаёт нули/пусто. `status:"true"`
на SET означает ровно «скрипт вызвал `_device.Set()`», и ничего больше.

**Почему это стоп-фактор.** ТЗ §12 строит подтверждение на изменении feedback:
«если feedback не изменился — команда считается неподтверждённой, элемент
возвращается к фактическому состоянию, гостю показывается сообщение о
невозможности выполнить действие». На этом стенде feedback не изменится
**никогда**, поэтому:

* гостевой интерфейс показал бы «не удалось выполнить» на 100% команд;
* «текущая температура» не отобразилась бы вообще;
* приёмку G3–G5 на этом стенде провести нельзя.

**Что нужно от команды ПНР / iRidi (блокирует приёмку, не блокирует G0–G2):**

1. Поднять Modbus-обмен между iRidi и GRMS на стенде — или сказать, что стенд
   заведомо «пустой» и приёмка будет на объекте.
2. Подтвердить, что `false` — это «нет данных», а не легальное значение `0`.
   Сейчас они неразличимы: выключенный свет и мёртвая связь выглядят одинаково.
   Если различить на уровне iRidi нельзя, backend обязан считать номер
   недоступным по критерию §6 ТЗ («можно ли получить текущие состояния») —
   иначе гостю покажут «всё выключено» вместо «связи нет».
3. Дать эталон живого ответа с числом (например реальную температуру), чтобы
   зафиксировать формат: `"23"`, `"23.5"` или `23`.

Пункт 2 — самый важный: от него зависит, отличит ли система «свет выключен» от
«GRMS отвалился». Это и есть требование ТЗ §6 «не показывать устаревшие
значения как актуальные».

## 8. Расхождения с присланными материалами

### 8.1 ⛔ `subdevice` обязан быть ПУСТЫМ (ТЗ и Postman говорят иначе)

ТЗ §5/§7 и `postman_collection.json` показывают `"subdevice": "Custom"`.
На боевом сервере это ломает чтение:

```
sub=''       fb='F_DND' -> { "status" : "true", "value" : "false" }        ✅
sub='Custom' fb='F_DND' -> { "status" : "true", "value" : "undefined" }   ❌ тег не найден
sub='Feedback'          -> value "undefined"                              ❌
sub='Tags'              -> value "undefined"                              ❌
```

Причина видна в скрипте (строка 82): имя тега склеивается как
`subdevice + ":" + feedback`, то есть при `subdevice:"Custom"` ищется тег
`Custom:F_DND`, которого нет.

**Вывод:** на этом объекте `subdevice` всегда пустая строка. Адаптер обязан
хранить `subdevice` как настраиваемое поле (на другом объекте оно может
понадобиться), но по умолчанию отправлять пустое. Примеры из ТЗ и Postman в
этой части к стенду неприменимы.

### 8.2 ⛔ Excel по ТИП1 расходится с сервером: 10 групп света против 12

`240701_Переменные для ПНР.xlsx`, блок «ТИП1 (Номер 701)» перечисляет
`C_Light 1 … C_Light 10`. На сервере у устройства 701 реально существуют
`F_Light 1 … F_Light 12` — на две группы больше.

ТИП2 (708) и ТИП3 (706) с Excel совпадают полностью.

Нужно уточнение у ПНР: 11-я и 12-я группы в ТИП1 — это забытые в Excel
реальные группы или мусор в проекте iRidi. **Это прямое обоснование того,
почему импорт Excel в G4 обязан быть сверяемым с живым сервером, а не слепым.**

### 8.3 Сцены: feedback отсутствует — как и предполагает ТЗ

`F_Scene_1`/`F_Scene_2` не найдены ни на одной эталонной комнате. Excel в
колонке Feedback для `C_Scene_1/2` содержит не имя тега, а число `46`
(артефакт формата — не имя канала). Совпадает с ТЗ §12: «для сцен feedback
может отсутствовать, достаточно успешной отправки команды».

### 8.4 Каталог ТЗ шире, чем стенд

ТЗ §1/§11 перечисляют отопление/радиаторы, blackout-шторы, мастер-выключатель.
Тегов `F_Heating*`, `F_Blackout*`, `F_MasterSw` на стенде нет. Каталог элементов
(контракт «реестр элементов») их поддерживает, но на этом объекте они не
включаются. Мастер-выключатель, вероятно, реализуется сценой (`C_Scene_*`) —
как в `пример запроса к Iridi для комнаты.txt`, где `MASTER_OFF` описан именно
как сцена, а не отдельный канал.

### 8.5 Мелочи

* Порт: скрипт в `Test_MB_http.sirpz` слушает `80`, присланный
  `Iridi HTTP server JS.txt` — `1085`. Боевой — **1085**. Порт настраиваемый,
  зашивать нельзя.
* `Iridi HTTP server JS.txt` и `scripts/Script 1.js` внутри `.sirpz` идентичны,
  кроме порта.
* `request` регистрозависим: `"get"` → «плохой запрос».
* `max_http_clients = 50` в скрипте — потолок одновременных HTTP-клиентов.
  При 150 параллельных запросов ошибок не было (соединения переиспользуются),
  но лимит одновременных запросов в коннекторе нужен, и он должен быть заметно
  ниже 50 на объект.

## 9. Что зафиксировать в контрактах (итог для G1–G2)

1. Чтение и запись — **POST**; путь `/`; `Content-Type: application/json`.
2. `subdevice` — настраиваемое поле, по умолчанию **пустое**.
3. `requestID` — строгий UUIDv4, генерирует backend, валидируется до отправки.
4. Нормализация ответа: две формы (A/B), `status`/`value` — строки;
   `value == "undefined"` → `CHANNEL_NOT_FOUND`.
5. Корреляция строго по `requestID` из тела; ответ с `requestID:"undefined"`
   или `null` — не коррелируется, считается сбоем.
6. Имя устройства собирает backend по шаблону типа номера; произвольное имя
   от клиента не проходит (иначе доступен служебный `HttpServer`).
7. `status:"true"` на SET ≠ подтверждение состояния. Подтверждение — только
   перечтение feedback (цикл с бэкоффом), для сцен — не требуется.
8. Различать «нет данных» и «значение 0» на текущем стенде нельзя — см. §7,
   вопрос открыт для ПНР.
