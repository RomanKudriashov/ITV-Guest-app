## 2. Тема и токены (после R7)

### Три словаря

| Словарь | Файл | Про что |
|---|---|---|
| платформенный | `frontend/src/theme/tokens.ts` | палитра бренда, `MEDIA_OVERLAY` |
| витрина | `frontend/src/guest/storefrontTokens.ts` | стекло, скримы, золото, раскладка |
| админка | `frontend/src/admin/adminTokens.ts` | платформенная консоль |

### Как экран берёт цвет

Ровно два хука:

```tsx
const { tokens, mode } = useAppTheme();     // frontend/src/theme/ThemeProvider.tsx:178
const { glass, scrim, onMedia } = useStorefront();  // guest/useStorefront.ts:15
```

`useStorefront()` — это `useMemo(() => storefrontTokens(mode), [mode])`, то есть
**набор витрины является функцией режима**. Ключевое решение R7: раньше значения
были плоскими и описывали только тёмную витрину, из-за чего светлая тема
физически не доходила до гостя.

Пример из живого кода (`VenuePage`/`CatalogPage`):

```tsx
sx={(theme) => ({
  background: glass.panel.background,
  border: glass.panel.border,
  backdropFilter: glass.panel.backdropFilter,
  borderRadius: `${theme.palette.brand.radius.md}px`,
})}
```

### Правило `lint:colors`

`frontend/scripts/check-colors.mjs`, гоняется внутри `npm run build` — то есть
на том же рубеже, что и типы.

**Запрещено:** любой литерал цвета — `#rgb`/`#rrggbb`/`#rrggbbaa`, `rgb()`,
`rgba()`, `hsl()`, `hsla()` — во всех `.ts`/`.tsx` под `src/`.

**Разрешено только** в трёх словарях выше плюс три точечных исключения:
`cms/brand/BrandEditor.tsx`, `cms/brand/previewData.ts`, `kit/FlagIcon.tsx`.

**Что guard пропустит** (важно для G5):
* цвета в CSS-файлах и inline-стилях внутри строк, не совпавших с регуляркой;
* именованные CSS-цвета (`white`, `black`, `tomato`) — регулярка их не ловит;
* цвет, собранный конкатенацией (`'rgb(' + r + ...`);
* SVG-атрибуты `fill="white"` в разметке.

То есть guard ловит частый случай, а не все. На это опираться можно, но не
слепо.

### Плита плана: тёмное фото на светлом фоне

Прецеденты **есть**, и оба сделаны одинаково — тёмный медиа-блок остаётся
тёмным в обеих темах, а читаемость обеспечивается скримом, а не режимом:

1. **Обложка отеля и шапка заведения** — `scrim.hero` / `scrim.heroWide`.
   В светлом наборе они *ослаблены*, но остаются тёмными. Комментарий в словаре
   объясняет почему: «под ними всегда лежит кадр, а не фон страницы».
2. **Плитка витрины** — `tile.fallbackColor`, `tile.scrim`: заглушка **всегда
   тёмная в обеих темах**, потому что подпись на плитке белая.
3. **`onMedia.*`** — белый текст поверх кадра в обеих темах: «светлый текст
   здесь следствие скрима, а не режима».
4. `MEDIA_OVERLAY` в `theme/tokens.ts` — общий слой для карточек кита.

**Guard это не сломает**: цвета лежат в словарях, а экран берёт их по имени.
Плита плана обязана идти тем же путём — добавить в `storefrontTokens.ts` секцию
вида `roomPlan: { scrim, fallback, zoneFill, zoneActive }` для обоих режимов, а
в компоненте не писать ни одного литерала.

### Что в светлой теме сейчас слабо

Из отчёта R7 §4 — уже вылечено и повторять нельзя: имя отеля жёстко белым, чип
номера белым по белёсому, стекло из разных источников двумя слоями, нижнее меню
почти глухим (.94 вместо .6+blur), липкая строка категорий закрывала контент
фоном страницы, крестик карточки без стеклянного чипа, счётчики трекера за
границей вкладки.

Общий вывод для G5: **элементы поверх кадра — из `glass.*`, а не свои**, иначе
новый экран унаследует ровно ту болезнь, которую R7 лечил.

## 3. Гостевая сессия и вход

### Резолв номера

QR кодирует `/r/{room}` (`backend/apps/hotels/qr.py`), диплинк ведёт на
`EntryPage`. Сессия — `POST /api/v1/guest/session` с `room_number`; токен
непрозрачный, отзываемый, в базе только SHA-256 (`accounts.GuestSession`).

Клиент: `frontend/src/guest/session/GuestSessionProvider.tsx`.

### Уровни доверия

`accounts.TrustLevel` — `anonymous` (0) < `room_scanned` (10) <
`pms_verified` (20) < `staff_verified` (30). На клиенте тип
`GuestTrust` в `guest/api/types.ts:13`.

Единственная производная величина:

```ts
canOrder: alive && session?.trust !== 'anonymous'   // GuestSessionProvider.tsx:142
```

### Step-up PIN — НЕ РЕАЛИЗОВАН

Ни на бэкенде, ни на фронте. Контракт G0
(`contracts/guest-api.md` §2) описывает `POST /api/v1/guest/room/verify`,
`PIN_INVALID`, `PIN_THROTTLED`, `attempts_left`, `retry_after_s` — **в коде
этого нет**. Поиск по `backend/api/` даёт ноль совпадений; единственный `verify`
в проекте — `apps/accounts/totp.py`, это 2FA платформенных админов, к гостю
отношения не имеет.

**Защиты от перебора PIN, соответственно, тоже нет** — нечего защищать.

Точка входа, если делать: рядом с созданием сессии в `backend/api/guest.py`,
повышение `GuestSession.trust` до `pms_verified`.

### Режим «просто посмотреть»

Вход без номера — кнопка `guest-browse-only` на `EntryPage` (строка 352).
Отличается на клиенте одним: `trust === 'anonymous'` → `canOrder === false`.

Как это выглядит сейчас: `VenuePage` показывает `Alert` с
`guest.venue.viewOnly`, формы заказа/заявки/слота показывают
`guest.errors.trustRequired` и блокируют кнопку.

### Гостевая сторона — построчно

**Эндпоинт приёма `{controlId, value}` — не реализован.**
`grep grms backend/api/guest.py` → пусто. Все 14 маршрутов GRMS живут под
`/api/v1/cms/grms/*` и закрыты `CmsAuth` + модулем. Гостевой токен туда не
пускают в принципе.

**Снапшот состояния для гостя — не реализован.** Ни REST, ни WS. Есть
`publishing.build_snapshot()`, но это снимок **конфигурации** для публикации, а
не состояние номера: в нём лежат технические `command`/`feedback`, которые
гостю отдавать нельзя (контракт `guest-api.md` §8).

**pending / confirmed / unconfirmed / failed — есть, но не в гостевом API.**
Константы в `apps/grms/commands.py`: `RESULT_CONFIRMED`, `RESULT_UNCONFIRMED`,
`RESULT_ACCEPTED`, `RESULT_FAILED`. Возвращает их `send_command()` — доменная
функция. Гостевые состояния элемента из контракта (`confirmed`/`pending`/
`offline`) **нигде не выражены**: `pending` в текущем коде вообще не существует
как состояние, потому что `send_command()` синхронна и возвращает управление
уже после цикла подтверждения (до ~3.7 с).

**Признак оффлайна гостю не отдаётся.** На бэкенде всё для него есть:
`transport.node_is_online(hotel)` и `endpoints.*.reachable` из heartbeat
коннектора. Но `availability: online|unavailable` из контракта нигде не
собирается и никуда не отдаётся.

**Чтение начального состояния из feedback до взаимодействия — не реализовано
для гостя.** Функция `commands.read()` есть и работает (используется в сверке и
проверке на номере), но гостевого пути к ней нет.

### Что это значит для G5

Гостевая часть — это **не «прикрутить экран к готовому API»**, а построить весь
гостевой слой: эндпоинты, снапшот-сериализатор без технических полей, WS-канал
комнаты, состояние `pending`, признак доступности, резолв
`сессия → комната → тип → опубликованный конфиг`.

## 5. Конфиг типа номера

### Текущая схема

`grms_published_config`: `room_type` (FK), `version`, `payload` (JSONField),
`is_current`, `published_at`, `published_by`, `rolled_back_from`.

Ограничения: уникальность `(hotel, room_type, version)` и частичный уникальный
индекс «ровно одна текущая версия на тип».

`payload` — самодостаточный снимок:

```jsonc
{ "type": "...", "title": {...}, "device_name_template": "...", "subdevice": "",
  "zones": [ { "code", "title", "sort_order",
               "controls": [ { "controlId", "kind", "title",
                               "capabilities": ["toggle"],
                               "channels": { "toggle": {command, feedback, subdevice, trigger_value} },
                               "range":    { "toggle": {min, max, kind} } } ] } ] }
```

Версионирование: публикация делает новую версию и снимает `is_current` со
старой; откат публикует **копию** старой версии новым номером и заполняет
`rolled_back_from`. История не переписывается.

### Места под геометрию плана и ассет рендера — НЕТ

Ни в модели, ни в снимке. `payload` — свободный JSON, поэтому расширение
возможно без миграции.

**Минимальное расширение, не ломающее версионирование и откат:**

```jsonc
{
  "...": "как сейчас",
  "plan": {
    "asset_id": "<uuid MediaAsset>",        // рендер плана
    "aspect": 1.6,                           // чтобы верстать до загрузки
    "zones":  [ { "code": "bedroom", "x": 4, "y": 8, "w": 46, "h": 60 } ],
    "points": [ { "controlId": "ac.1", "x": 62, "y": 30 } ]
  }
}
```

Всё в **процентах** от кадра — иначе рендер и разметка разъедутся при смене
размера картинки.

Ключевое условие совместимости: `plan` кладётся **внутрь `payload`**, а не
отдельной таблицей. Тогда снимок остаётся самодостаточным и откат к v2 вернёт
и геометрию v2 — то самое свойство, ради которого снимок и делали. Отдельная
таблица это свойство бы сломала: откат конфигурации оставил бы новую геометрию.

`build_snapshot()` в `publishing.py` — единственное место, где это собирается.

### Как в проекте привязываются изображения

`apps/media`: `MediaAsset` (UUID, `kind`, `status`, alt), загрузка через
`upload_asset()`, нарезка вариантов Celery-задачей
`apps.media.tasks.process_media_asset` (`thumb`/`card`/`full`), хранилище MinIO,
отдача через `serialize_asset()`. Пока варианты не нарезаны, URL пустые и UI
показывает локальное превью — статус опрашивается.

`MediaAsset.Kind`: `item`, `category`, `brand`, `other`. **Вида под план нет** —
нужен либо новый `room_plan`, либо `other` (но тогда планы не отфильтровать в
медиатеке).

**Тем же путём план положить можно**: загрузить как `MediaAsset`, а в
`payload.plan.asset_id` хранить UUID. Резолвить URL обязан backend
(`serialize_asset`), как уже сделано с `cover_image` — фронт не должен собирать
адрес строкой.

⚠️ **Грабли, о которых просили напомнить:** ключи реестра — **через дефис**
(`room-plan`), коды сервисов — **через подчёркивание** (`room_service`).
`MediaCategoryPlaceholder.code` и `HotelModule.Code` живут по разным
соглашениям; перепутать легко, а последствие — молча не найденный плейсхолдер.

### Засеянного конфига НЕТ

Проверено на живом стенде:

| отель | тариф | room_control | типов GRMS | конфигов |
|---|---|---|---|---|
| crystal | `standard` | **выключен** | 0 | 0 |
| azure | — | выключен | 0 | 0 |
| lumen | — | выключен | 0 | 0 |

Тариф `standard` содержит `modules=[]`. `ROOM_CONTROL` входит в `business`,
`resort` и `trial`.

**Что надо засеять для G5:**
1. включить `room_control` демо-отелю (сменить тариф на `business`/`trial` либо
   точечным `HotelModule` c `source=override`);
2. один `RoomType` с шаблоном устройства;
3. переменные под элементы демо (свет, шторы, фанкойл, DND, сцена);
4. `RoomTypeRoom` для комнаты `305` — её использует весь E2E (`DEMO_ROOM`);
5. элементы + привязки;
6. опубликованный `PublishedConfig` v1;
7. геометрия плана + ассет рендера, если он входит в G5.

Без п.1–6 экран нечем наполнить, а E2E нечего проверять.

| `trigger` (сцены, мастер) | `SceneButton` | ничего — готов |
| `setpoint` (уставка 16–32) | `Thermostat` | **добавить `onChange`; `max` по умолчанию 30, наш диапазон до 32** |
| `current_temp` | `Thermostat.current` | готов (read-only и должен таким быть) |

## 7. Риски конфликта с работающим

### Наложения в шапке и подвале

Плавающая группа контролов (номер/язык/тема) и липкая строка категорий уже
однажды столкнулись: группа стояла на `top: 10`, строка пинилась в `top: 0`, и
на узком экране чип наезжал на названия разделов. Лечится не по месту, а
числами в словаре:

```ts
floatingTop: 10, floatingHeight: 38
stickyUnderFloating = floatingTop + floatingHeight + 8   // = 56
panelOverlap: 28
```

Второй прецедент — плашка «просмотр без номера»: панель каталога подтянута
вверх на `panelOverlap` (−28px) и накрывала её нижнюю часть. Починено `pb` +
`position/zIndex`.

**Что учесть G5 с залипающим планом:** план — это ещё одна липкая поверхность в
той же полосе. Он обязан пиниться **под** плавающей группой
(`stickyUnderFloating`), а не в `top: 0`, и оставлять снизу запас
`panelOverlap`, если под ним идёт панель со скруглением. Числа брать из словаря,
не вписывать.

### Guards, которые это ловят

**Живут только в ветке хвоста** — `e2e/tests/text-overflow.spec.ts` (30 тестов):
обрезка (`scrollHeight > clientHeight` при `overflow: hidden`) и **перекрытие**
соседом (проба пятью точками по горизонтали и четырьмя по вертикали, включая
самый низ). Покрыты витрина, заведение, инфо, корзина, заказы, CMS, трекер,
платформа, оба входа × 3 ширины × 2 темы.

⚠️ **На `g2-admin` этого guard'а нет.** Ещё один довод влить хвост до G5: иначе
новый экран строится без сторожа, который ловит ровно тот класс дефекта, к
которому липкий план предрасположен.

### i18n

* Ключей: ru 1536, en 1532, ar 1540, zh 1530.
* Расхождение — **10 ключей, и все 10 плюральные формы** (`_one`/`_few`/`_many`).
  Это не дыры: у русского три формы, у английского две, у китайского одна.
  Настоящих отсутствующих ключей — **ноль**.
* **Пустых значений — ноль** во всех четырёх.
* **Автоматического guard'а на полноту локалей НЕТ.** Проверка выше сделана
  разово скриптом для этого аудита. Добавлять новые ключи придётся
  дисциплиной либо завести сторож.
* **RTL работает**: `directionForLanguage()` в `i18n/config.ts`,
  `stylis-plugin-rtl` + отдельный emotion-кэш в `ThemeProvider.tsx`. Новый экран
  обязан использовать логические свойства (`borderInlineStart`, `ms`/`me`), как
  уже сделано в `KitToast`.

### Какие E2E придётся расширить

| Файл | Что добавить |
|---|---|
| `theme-modes.spec.ts` | новый экран в обеих темах |
| `text-overflow.spec.ts` *(из хвоста)* | маршрут `/room` в список |

Плюс backend-тесты гостевого API, которых пока нет ни одного.

## 8. Долги и открытые решения

### Блокирует G5

1. **Хвост не влит** — без него нет guard'а на перекрытие текста и трёх отелей
   для проверки white-label.
2. **Модуль `room_control` выключен у демо-отеля**, GRMS-данных нет вовсе —
   экран нечем наполнить, E2E нечего проверять.
3. **Гостевого API GRMS не существует** — весь контракт `guest-api.md` остаётся
   документом.
4. **Гостевой фронт не знает про модули отеля** — гейтить пункт нечем.

### Не блокирует, но задеть может

5. **Step-up PIN не реализован.** Контракт требует `pms_verified` для команд, а
   получить этот уровень сейчас нечем: PMS-интеграции нет. Практически это
   значит, что либо G5 разрешает команды на `room_scanned`, либо экран
   нерабочий. **Требует решения до прогона.**
6. **⛔ Feedback боевого стенда мёртв** (прозвон G0 §7, подтверждено в G1 и G2).
   Полный цикл подтверждения проверяется только на эмуляторе. Вопрос к ПНР
   открыт.
7. **⛔ Комната 506 отнесена к двум типам** в файле ПНР (G2). Вопрос к ПНР.
8. **Экранов CMS для GRMS нет** — конструктор существует только как API. Для G5
   не блокирует (конфиг можно засеять), но демонстрировать администратору
   нечего.
9. **Кит `room.tsx` не интерактивен** — три из семи компонентов только
   отображают.
10. **Рост сервисов-остатков решён наполовину** (хвост §4): 35 выключенных
    сервисов в «Кристалле» удалить нельзя, на них висят заказы. Число продолжит
    расти незаметно для оператора.
11. **Агрегатор без своей категории невидим на витрине** (хвост §7.4) — обойдено
    данными, в продукте не починено.
12. **Витрина собирается с зашитым поддоменом** `VITE_HOTEL_SUBDOMAIN` (хвост
    §7.1) — переключение отелей в браузере требует пересборки.
13. **Цвет трекера (бирюзовый/синий) и одобрение светлой темы** — в отчётах R7 и
    хвоста как открытый вопрос не зафиксированы; в найденных «СТОП-точках» обоих
    прогонов сказано, что ни одна не сработала. Если решение ожидалось, оно
    нигде не записано — **отмечаю как не найденное, а не как закрытое.**
14. **`lint:colors` ловит не всё** — именованные цвета и SVG-атрибуты проходят
    мимо.
15. **Нет guard'а на полноту локалей.**
16. **Тесты против боевого iRidi не в CI** (6 skipped) — осознанно, но значит,
    что расхождение с железом заметят только вручную.

## Что мешает начать G5

Пронумеровано по порядку выполнения. Оценка — в рабочих часах, грубо.

1. **Влить хвост в `main`, затем `main` в GRMS-стек.** Конфликтов нет, проверено
   пробным слиянием. После — прогнать backend и E2E, потому что хвост правил
   ровно те файлы гостевого шелла, куда встраивается G5. — **1–2 ч**, из них
   почти всё на прогоны.

2. **Решить вопрос уровня доверия для команд.** Контракт требует
   `pms_verified`, а взять его неоткуда: PMS нет, PIN не реализован. Варианты:
   (а) разрешить команды на `room_scanned` и записать это как временное
   послабление; (б) реализовать PIN с проверкой по произвольному коду заезда,
   заводимому в CMS. — **решение: 0 ч, реализация (б): 6–8 ч** с защитой от
   перебора и тестами.

3. **Отдать гостю признак включённого модуля.** Поле в `serialize_hotel()` +
   тип на клиенте. — **1 ч**.

4. **Построить гостевой API GRMS.** Это основной объём: резолв
   `сессия → комната → тип → опубликованный конфиг`, сериализатор снапшота **без
   технических полей**, `POST {controlId, capability, value}` с валидацией по
   диапазону, состояние `pending` (сейчас его нет — `send_command()` синхронна и
   ждёт до ~3.7 с, что для HTTP-ответа гостю недопустимо), признак
   `availability` из `node_is_online` + heartbeat. — **12–16 ч**.

5. **WS-канал комнаты.** Консьюмер + группа `room.{hotel}.{room}` + рассылка
   полного снимка во все сессии комнаты. По образцу существующих консьюмеров. —
   **4–6 ч**.

6. **Засеять демо-данные:** включить модуль, тип, переменные, элементы,
   привязки, `RoomTypeRoom` для комнаты `305`, опубликованный конфиг. Без этого
   ни экрана, ни E2E. — **3–4 ч**.

7. **Довести кит `room.tsx`:** `onChange` у `Thermostat` (и `max` до 32),
   сегменты скорости вентилятора (компонента нет вовсе). — **4–6 ч**.

8. **Решить, что делать с планом номера.** Если он входит в G5: расширить
   `payload.plan`, завести `MediaAsset.Kind.ROOM_PLAN`, добавить секцию
   `roomPlan` в `storefrontTokens.ts` для обоих режимов, продумать залипание в
   полосе с плавающей группой. — **8–12 ч**. Если не входит — 0, но это надо
   сказать явно.

9. **Продуктовое решение по режиму «просто посмотреть»:** пункт «Номер»
   скрывать или показывать с объяснением. — **решение 0 ч**, реализация внутри
   п.4.

10. **Расширить E2E и guards** под новый экран: пять файлов из §7. — **4–6 ч**.

Пункты 1–3 и 6 — подготовка, без них прогон упрётся в них же на первом часу.
Пункты 4–5 — существо работы. Пункт 8 определяет, G5 это «экран управления» или
«экран управления с планом», и объём различается вдвое.
