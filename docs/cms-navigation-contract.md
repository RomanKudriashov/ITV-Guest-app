# Контракт навигации CMS

Что отель видит в своей панели и почему именно это. Введено в R4 взамен
плоской простыни из 18 равнозначных пунктов.

Читать с [`design/guest-hub-design-map.md`](design/guest-hub-design-map.md)
(Часть 2) и [`roles-api-contract.md`](roles-api-contract.md).

---

## 1. Навигация приходит с сервера

> **Путь в `to` — КАНОНИЧЕСКИЙ (`/cms/...`), а не адресный.** На адресе отеля
> панель живёт в `/admin`, и клиент переносит путь туда сам (`toCmsRoot()`).
> Сервер про хост клиента не знает и знать не должен; см.
> [`addressing.md`](addressing.md).

`GET /api/v1/cms/navigation`

```jsonc
{
  "groups": [
    {"key": "operations", "items": [
      {"key": "dashboard", "to": "/cms/dashboard", "module": null},
      {"key": "tracker",   "to": "/tracker",       "module": null}
    ]},
    {"key": "structure", "items": [
      {"key": "services", "to": "/cms/services", "module": null},
      {"key": "rooms",    "to": "/cms/rooms",    "module": null},
      {"key": "staff",    "to": "/cms/staff",    "module": null}
    ]}
    // …appearance, analytics, settings, modules
  ]
}
```

**Почему не на клиенте.** Гейтинг решает реестр модулей отеля, а роль решает,
что человеку вообще показывать. Собери меню во фронте — и список того, за что
отель не платил, всё равно уедет к нему в бандл, а «спрятать пункт» станет
косметикой поверх открытого экрана.

Во фронте остался только реестр иконок на ключ. Второй список разделов там
означал бы два источника правды о том, что у отеля есть.

**Пустые группы не отдаются.** Заголовок без пунктов админ читает как поломку.

---

## 2. Группы

| Ключ | Что внутри |
|---|---|
| `operations` | Дашборд, Трекер |
| `structure` | Сервисы, Номерной фонд, Персонал |
| `appearance` | Бренд и витрина |
| `analytics` | Аналитика |
| `settings` | Настройки отеля, Уведомления, Справочники |
| `modules` | только включённые модульные разделы |

---

## 3. Гейтинг модулями

**Главное правило: базовое не гейтится.** Модуль — платная надстройка, а не
выключатель для того, без чего отель не работает. Привязка базового пункта к
модулю выглядит как «настройка», а на деле оставляет отель без инструмента, за
который он уже заплатил тарифом.

`module` проставлен ровно у экранов, которые БЕЗ модуля не имеют смысла:

| Пункт | Модуль |
|---|---|
| `marketing` | `marketing` |
| `roomControl` | `room_control` |
| `payments` | `payment` |
| `pms` | `pms` |
| `mobileKey` | `mobile_key` |

Всё остальное — меню, номера, персонал, бренд, аналитика, настройки — живёт
всегда. На это стоит сторож-тест поверх `ALWAYS_AVAILABLE`: он падает, если
базовый раздел когда-нибудь привяжут к модулю.

Маршрут модульного экрана существует всегда, даже когда пункта нет: прямая
ссылка не должна ломаться молча.

---

## 4. Роль

Пункты уровня отеля (`hotel_admin_only`) управляющему сервисом не показываются.
Рисовать пункт, который ответит `403 hotel_admin_only`, — это враньё
интерфейсом: человек считает, что у него что-то сломалось, хотя он просто не
администратор.

Линейному персоналу навигация не отдаётся вовсе (`403 no_cms_access`).

---

## 5. Что растворилось в R4

| Было | Стало |
|---|---|
| «Меню» отдельным разделом | вкладка внутри сервиса — «меню какого ресторана» теперь имеет ответ |
| «Отделы» | «Сервисы» (ключ — id сервиса, исполнитель внутри) |
| «Локации» | справочник в «Настройках отеля» |
| «Коммерция» | валюта/налог — в «Настройках»; коммерция заведения — на его вкладке |
| «Витрина» | вкладка в «Бренд и витрина» |
| «Бейджи», «Быстрые действия» | раздел «Маркетинг» (за модулем) |
| «Стайлгайд», три заглушки «скоро» | убраны из навигации |

Старые адреса не в 404, а редиректом на новый дом: закладки и ссылки в
переписке переживают реорг.
