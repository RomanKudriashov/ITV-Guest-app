# Гостевой сервис отеля — карта продукта и план пересборки

Документ фиксирует продуманную с нуля структуру продукта: четыре роли пользователей, их экраны и возможности, модель сервисов и план того, что переиспользуем из уже сделанного, а что переделываем.

Это источник правды. Из него дальше вырастают: (а) визуальные макеты гостевых экранов, (б) план пересборки кода.

---

## Часть 0. Модель сервиса — фундамент всего

Раньше меню было «плоским»: одна куча блюд, непонятно, к какому ресторану они относятся. Новая модель строится вокруг **сервиса**.

**Сервис — это типизированный контейнер.** Ресторан, бар, спа, такси, консьерж, хозслужба, инфо-раздел, мини-бар — всё это сервисы. У сервиса есть **тип-шаблон**, который приносит и настройки, и экраны, и вид у гостя.

**Тип собирается из 4 кирпичей** (они уже есть в системе):

- **Каталог** — список товаров/блюд с категориями (ресторан, мини-бар).
- **Форма-заявка** — гость заполняет и отправляет (такси, уборка, ремонт, будильник).
- **Слоты** — запись на время (спа-процедуры, корты, экскурсии, поздний выезд).
- **Инфо-страница** — контент с фото, без действия (о завтраке, Wi-Fi, правила, город).

Шаблон — это готовая комбинация кирпичей плюс настройки под тип. «Добавить свой сервис» = собрать из кирпичей. Ничего нового строить не нужно, всё переиспользуется.

**Полная анатомия сервиса — пять слоёв:**

1. **Тип / шаблон** — из каких кирпичей собран.
2. **Наполнение** — сам контент (блюда, процедуры, поля заявки).
3. **Доступность** — в какие локации работает + расписание + кто исполняет.
4. **Исполнение** — статусы, трекер, эскалация, уведомления.
5. **Коммерция** — цены, сборы, чаевые, минимум — у каждого сервиса свои.

Плюс **гостевая идентичность**: имя, фото-шапка, подпись — как сервис показан на витрине.

**Ключевые правила модели:**

- **Один тип — сколько угодно инстансов.** Несколько ресторанов, несколько спа, несколько бассейнов. Сервис — это экземпляр, тип — шаблон.
- **Контент делится по ссылке, а не копией.** Один источник правды. Правишь блюдо в «Панораме» один раз — оно меняется везде, где включено, стоп-лист тоже.
- **Включение несёт свой слой (overlay).** Сервис может включить чужой контент целиком или частично и поверх задать: свою наценку (+15%), скрыть часть позиций, своё расписание, своего исполнителя.
- **Исполнитель выбирается у каждого включённого блока.** По умолчанию — точка источника, либо своя собственная. Этот выбор решает и маршрутизацию, и чьё расписание в силе.
- **Заказ разъезжается по исполнителям.** Гость в рум-сервисе взял стейк + коктейль — стейк уходит в трекер кухни-исполнителя, коктейль — в трекер бара. Это решение «мультиресторанной» проблемы.
- **Доступность = пересечение.** Заимствованное блюдо доступно, только если его исполнитель работает: рум-сервис круглосуточный, но если стейк готовит кухня «Панорамы» с закрытием в 23:00 — после 23:00 стейк гаснет.

## Часть 1. Платформенный администратор

Владелец всего SaaS. При пустой базе — единственный, кто существует; заводит отели. Заходит через **/admin** с усиленным входом (2FA / IP-allowlist — это мастер-ключ ко всем отелям).

**Экраны:**

- **Сводка по платформе** — сколько отелей (активные / триал / отключённые), заказы и оборот за период по всем отелям, живые сессии, рост, здоровье системы (медиапайплайн, фоновые задачи, узлы).
- **Флот отелей** — список с поиском, фильтром и сортировкой. По каждому: название, поддомен, статус, тариф, счётчики (номера / персонал / сервисы / заказы), последняя активность.
- **Создание отеля** — поддомен, название, таймзона, валюта, языки, пресет, первый администратор. Возможен старт из шаблона онбординга («курорт», «ресторанный отель»), а не с нуля.
- **Карточка отеля** — профиль (название, TZ, валюта, языки), включение/отключение, архив, сброс/заведение админа отеля. Поддомен не редактируется (ключ тенанта, QR напечатаны).
- **Вход в отель** — платформенный админ проваливается в любой отель и настраивает что угодно, но через механизм «войти как» с логом (правки поддержки отделимы от правок самого отеля).
- **Реестр модулей** — фичи, включаемые отелю по тарифу: управление номером (GRMS), оплата, PMS, мобильный ключ, мультиресторанность, маркетинг, доп. языки, нативное приложение, уровень аналитики. С точечным исключением (дать фичу вне тарифа, например пилоту). **Этот реестр решает и то, что отель видит в своей CMS** — без модуля отель не видит ни одного его экрана.
- **Реестр он-прем узлов** (Local Connector) — как только включён GRMS или PMS: узел зарегистрирован? онлайн? последний отклик? ключ выдан / отозван.
- **Команда платформы** — несколько админов, роли (владелец / поддержка / только чтение), приглашения, аудит всех действий.
- **Оповещения админу** — отель офлайн, узел упал, триал истекает.

**Осознанно отложено:** биллинг — только шов. Тариф проставляется руками, деньги вне системы. Impersonation с таймером — каркас есть, довести. Понижение тарифа ниже использования, экспорт и офбординг данных (152-ФЗ) — учесть при реализации.

## Часть 2. Администратор отеля (CMS)

Заходит сразу в дашборд (без онбординг-мастера). Навигация **сгруппирована**, а не плоская простыня из 16 пунктов.

### Оперативный блок (сверху — «что сейчас»)

- **Дашборд** — живые заказы и заявки прямо сейчас, выручка за день, последние отзывы, что требует внимания (стоп-лист, узел офлайн). Пульт, а не список меню.
- **Заказы и заявки** — вся активность отеля, история по всем сервисам.

### Структура отеля (ядро)

- **Сервисы** — верхний уровень. Список карточек сервисов (рестораны, бар, спа, консьерж, такси…). Кнопка «добавить сервис» из шаблонов или свой. Провалился в сервис — и **только там** его наполнение (меню / форма / слоты), расписание, коммерция, локации подачи, фото-шапка, свой персонал, воркфлоу трекера. Меню вне сервиса не существует. Здесь же — включение чужого контента с overlay и выбор исполнителя.
- **Номерной фонд** — этажи, категории номеров, шаблоны типов, генерация QR. Сюда встаёт GRMS, когда модуль включён.
- **Персонал** — люди, роли, привязка к сервисам, каналы уведомлений, смены.

### Оформление (как отель выглядит гостю — всё в одном разделе)

- **Бренд и оформление** — пресет, токены, логотип, фон И раскладка плиток витрины главной. Полный предпросмотр с переключателем устройств (телефон / планшет / десктоп).

### Аналитика

- **Аналитика** — за период: тренды, разложение выручки (позиции / сбор / доставка / налог / чаевые), топ позиций, сравнение сервисов, экспорт. Отличается от дашборда: дашборд — «сейчас», аналитика — «за период».

### Настройки

- **Настройки отеля** — языки, таймзона, **валюта и налог** (единственная коммерция уровня отеля — остальная внутри сервисов), справочник **локаций подачи** (общий для всех сервисов; каждый сервис выбирает свои и ставит свою доставку), справочники аллергенов и маркеров, юридические / инфо-страницы, способы входа гостя, **Интеграции** (он-прем узел, ключи PMS).

### Модули (появляются, только если платформа включила)

Настройка управления номером (GRMS), PMS, мобильный ключ, маркетинг. Модуль выключен — экрана нет. Часть модулей встраивается прямо в профильный раздел (GRMS → в номерной фонд).

**Отдельного раздела «Коммерция» нет** — растворился: почти всё внутри сервисов, валюта и налог — в настройках. **Витрина главной не отдельный раздел** — вошла в «Бренд и оформление».

## Часть 3. Персонал

Роль решает, что человек видит и может. Три уровня внутри отеля (над ними — платформенный админ).

- **Линейный персонал сервиса** — повар, официант, бармен, горничная, диспетчер такси, спа-мастер. Видит трекер своего сервиса, двигает задачи. Меню, цены, настройки не трогает.
- **Управляющий сервисом** — всё линейного + правит меню, расписание, коммерцию **своего** сервиса, видит его аналитику, управляет своим персоналом. В чужие сервисы и настройки отеля не лезет.
- **Администратор отеля** — вся CMS (Часть 2).

**Главный экран сотрудника — трекер его сервиса**, под тип:

- **Ресторан / бар** — доска заказов: новый → готовится → готово → подано. Позиции с модификаторами, номер/локация, таймеры.
- **Хозслужба** — очередь заявок (убрать 305, полотенца): взять на себя, отметить готово.
- **Спа** — записи на сегодня лентой, отметка прихода гостя.
- **Такси / консьерж** — заявки на подачу: подтвердить, назначить время.

**Общее:** уведомление о новой заявке (звук, бейдж), эскалация, если висит без ответа. Мультисервисный сотрудник (бар + рум-сервис) — переключение или объединённая доска. Смены — кто сейчас на смене (влияет на эскалацию и автоназначение). Заимствованное блюдо падает в трекер выбранного исполнителя.

## Часть 4. Гость — детальный путь

### 4.1. Вход

- Скан QR в номере или ввод номера. QR несёт отель + номер.
- QR в лобби без номера → режим **«только просмотр»**: видит меню и сервисы, но заказать не может (или самовывоз, по решению отеля).
- Экран входа — фирменный кадр отеля (эстетика, которую утвердили): фото-фон со скримом, логотип, приветствие, поле «Номер», кнопка-стрелка, подсказка про QR, пилюли язык/тема. Тема грузится по поддомену до входа.

### 4.2. Главная — парадная отеля

- Приветственный кадр сверху, полоса активного заказа (если есть).
- **Витрина сервисов** — bento-плитки: фото на всю площадь, скрим только снизу, имя и подпись в нижнем левом углу, статус-пилюля («открыто до 23:00») в правом верхнем. Размер плитки (S / M / L) и порядок — из настроек отеля.
- Рестораны: до 3 — отдельными плитками со своими обложками; больше — одна плитка «Рестораны» с превью внутри. То же для услуг. Порог настраивается.
- Позже — плитка «Мой номер» (климат, шторы, свет).

### 4.3. Проваливание в сервис — главная починка

Тап на плитку → гость **внутри сервиса**, в его пространстве. Что именно — зависит от типа (кирпичей):

- **Ресторан / бар (каталог):** широкая фото-шапка заведения с его именем и подписью, чипы статуса (открыто, подача в номер, среднее время), строка категорий, карточки блюд (фото, состав, КБЖУ, бейджи, цена, кнопка +). Никакого «меню без ресторана».
- **Такси / уборка (форма):** шапка сервиса + форма заявки с нужными полями (куда, когда, класс / что убрать), отправка.
- **Спа / экскурсии (слоты):** шапка + выбор даты и свободных слотов, запись.
- **Инфо (страница):** шапка + контент с фото (о завтраке, бассейне, Wi-Fi, правилах).

### 4.4. Карточка позиции (в каталоге)

Фото слева (на десктопе — модалка по центру, фото сбоку; на телефоне — шторка снизу). Категория, название, цена, описание. КБЖУ одной строкой с порцией. Характеристики (способ приготовления, острота). Аллергены — янтарные пилюли «содержит», зелёные — маркеры «подходит» (без глютена, веган). Модификаторы (прожарка, молоко, допы) чипами. Комментарий, счётчик, кнопка «в заказ».

### 4.5. Корзина и оформление

- **Корзина — на сервис** (у каждого своя коммерция). Стейк в «Панораме» + коктейль в баре = два заказа. Рум-сервис-агрегатор — один заказ, разъезжается на исполнении.
- Строки: позиции → сбор → доставка → налог → чаевые → итог. **Все суммы приходят с сервера (quote), клиент ничего не считает.**
- Чаевые: пресеты + своя сумма + «без чаевых».
- Минимум: ниже порога — оформление заблокировано с подсказкой «добавьте ещё N».
- Локация подачи (номер / лобби / бассейн), время подачи (serve-by).

### 4.6. После заказа

- **Живой статус** — гостевая сторона трекера: таймлайн (принят → готовится → готово → подано), время подачи, обновление по WS без перезагрузки.
- **Полоса активного заказа** на главной.
- **История** заказов и заявок.
- **Чат** — гибрид: общий фронт-деск по умолчанию, но кнопка «написать» внутри сервиса создаёт тред этому сервису; не разобрали — падает во фронт-деск.
- **Отзыв** — карточка на экране завершённого заказа (оценка, текст, приватность).

### 4.7. Языки

Гость переключает язык; весь контент и интерфейс на 4 языках (ru / en / ar / zh), включая RTL для арабского.

## Часть 5. Что переиспользуем, что переделываем

Оценка относительно того, что уже построено (MVP + фазы A3+, B, C1–C5).

### Переиспользуем почти как есть

- **Мультитенантность + RLS** — ядро, изоляция отелей. Без изменений.
- **Медиапайплайн** (загрузка → MinIO → webp) — без изменений.
- **Коммерческий движок** (сбор, налог, чаевые, минимум, доставка, снимок сумм на заказе, /cart/quote) — логика верна, переезжает на уровень сервиса.
- **Аллергены / маркеры / характеристики** — модель готова.
- **Аналитика** с разложением выручки — готова.
- **Живой статус по WS** (реконсиляция снимком) — готов.
- **Экран входа гостя** (логин-канвас) — утверждённая эстетика, эталон.
- **4 типа предложений** (каталог / форма / слот / инфо) — это и есть кирпичи новой модели.
- **Платформенная консоль** (`/platform`, create_hotel, CRUD отелей, деактивация, аудит) — база под Часть 1.

### Адаптируем (есть, но меняем)

- **Точки исполнения → сервисы.** Сейчас venue = точка исполнения с замаршрутизированными категориями (C4.1 добавил public_name / tagline / is_guest_facing / фото). Нужно поднять сервис до полноценного типизированного контейнера с 5 слоями. Это центральная переделка модели данных.
- **Витрина главной (C4).** Плитки есть, но проваливание в сервис даёт плоское меню без идентичности заведения — чинится «пространством сервиса» (шапка + типизированный контент).
- **CMS-навигация.** Плоские 16 пунктов → сгруппированная структура (Часть 2); «Сервисы» как верхний уровень, меню внутри сервиса.
- **Локации подачи** — уже есть доставка по локации; оформить как общий справочник отеля, выбираемый в каждом сервисе.
- **Витрина + бренд** — объединить редакторы в один раздел с полным предпросмотром.
- **Платформа** — из `/platform` в `/admin`: добавить сводный дашборд, реестр модулей (с гейтингом CMS-навигации), реестр узлов, усиленный вход; вычистить тестовые отели из списка.

### Строим заново (нет)

- **Кросс-ссылочный контент с overlay** — включение чужого меню, наценка, скрытие, своё расписание, выбор исполнителя. Не существует.
- **Маршрутизация заказа по исполнителям** (fan-out) — заказ разъезжается по трекерам. Не существует.
- **Типизированные трекеры** — сейчас только кухонный. Нужны: очередь хозслужбы, записи спа, заявки такси/консьержа.
- **Роль «управляющий сервисом»** — промежуточная между линейным и админом отеля.
- **Реестр модулей** как механизм (тариф → фичи → видимость экранов).
- **Команда платформы** с ролями и аудитом.
- **Гибридный чат** с маршрутизацией по сервисам.

### Чинится по мелочи

- Белые поля на экране входа CMS (потеряли стиль темы).
- Демо-креды на экране входа (убрать с показа).
- Левый рельс десктопа — пересмотреть в пользу верхней стеклянной строки (обсуждается на макетах).
- Тёмная палитра фона + матовое стекло — отдельный стилевой проход.
