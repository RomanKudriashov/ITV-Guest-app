# План пересборки — очередь прогонов

Превращает карту продукта (`guest-hub-design-map.md`) и разбор «что переиспользуем / переделываем» в конкретную последовательность работ для Claude Code.

## Принцип

Это **рефакторинг, а не переписывание с нуля.** База переиспользуется как есть — мультитенантность и RLS, коммерческий движок, медиапайплайн, 4 кирпича (каталог / форма / слоты / инфо), аналитика, живой статус по WS, консоль платформы. Тесты держим зелёными на каждом рубеже (текущий базис — 450 backend / 35 E2E).

**Стержень — модель сервиса.** С неё начинаем: от неё зависят и трекеры, и CMS, и гость.

## Сквозные правила (в каждом прогоне)

- **Опираемся на сделанное.** Существующие модели, эндпоинты, компоненты переиспользуем и адаптируем — ничего не переписываем ради переписывания.
- **Убираем лишнее сразу.** Что новая модель делает избыточным — старые поля, эндпоинты, компоненты, транзитные заглушки — удаляем в том же прогоне, без мёртвого кода и осиротевших таблиц. Каждый прогон оставляет дерево чище, чем взял.
- **Данные — сразу реальные и обильные.** Никаких пустых экранов: каждый прогон наполняет затронутые структуры правдоподобным контентом — меню с блюдами, фото-обложки заведений и позиций, услуги, номера, персонал, расписания, коммерция, размеры плиток. Результат наглядный сразу, а не «каркас без мебели». Фото — только Unsplash/Pexels через медиапайплайн.

## Порядок и почему

Сначала **модель данных** (сервис), затем **логика** (кросс-ссылки, маршрутизация, трекеры), затем **интерфейсы** (CMS, гость, платформа), **стиль — в конце**. Стиль последним осознанно: перекрашивать движущуюся структуру — двойная работа, а визуальная цель уже зафиксирована утверждёнными прототипами. Контент наполняем с первого прогона (сквозные правила), чтобы каждый шаг был наглядным; финальную полноту всех 8 отелей доводим в C3 ближе к концу.

## Очередь прогонов

### R1 — Модель сервиса (фундамент)
ExecutionPoint → **Service** как типизированный контейнер. Пять слоёв: тип/шаблон (из 4 кирпичей), наполнение, доступность (локации + расписание + исполнитель у собственных блоков), исполнение, коммерция + гостевая идентичность. Типы-шаблоны для типовых сервисов + сборка своих. Сюда же — **модель данных реестра модулей** (флаги модулей у отеля), чтобы следующие прогоны могли на неё опираться.
Миграция существующих точек и меню в сервисы; всё продолжает работать. Заодно **удалить то, что генерализация делает лишним** (дубли полей и эндпоинтов старой модели точек). И **засеять один полностью наполненный демо-отель** («Кристалл»): меню с фото-обложками, услуги всех типов, расписания, коммерция, размеры плиток — чтобы модель сервиса была наглядной с первого прогона.
Переиспользуем: коммерция, 4 кирпича, RLS. Риск: крупный рефактор данных — контракт-first, тесты не ослаблять.

### R2 — Кросс-ссылки + overlay + маршрутизация заказа
Включение чужого контента (полностью/частично) по ссылке; overlay включения (наценка, скрытие позиций, своё расписание, выбор исполнителя); заказ **разъезжается** по трекерам исполнителей (fan-out); доступность = пересечение включающего сервиса и источника. Самая сложная логика — отдельным прогоном, изолированно.
Строим заново.

### R3 — Типизированные трекеры + роль «управляющий сервисом»
Обобщить единственный кухонный трекер в типы: доска заказов (ресторан/бар), очередь заявок (хозслужба), записи (спа), заявки (консьерж). Эскалация и уведомления на уровне сервиса. Новая роль между линейным и админом отеля. Заимствованные позиции падают в трекер выбранного исполнителя (стыкуется с R2).
Адаптируем кухонный трекер + строим недостающие типы. Ориентир — `staff-tracker-v2.html`.

### R4 — CMS отеля
Сгруппированная навигация (Оперативно / Структура / Оформление / Аналитика / Настройки) вместо плоских 16 пунктов. «Сервисы» верхним уровнем, меню — внутри сервиса на вкладках. Слияние бренда и витрины в один раздел с полным предпросмотром. Локации — общий справочник отеля. Растворить standalone «Коммерцию». **CMS-навигация гейтится реестром модулей** (из R1). Починить: белые поля на экране входа CMS, убрать демо-креды с логина.
Адаптируем существующую CMS. Ориентир — `cms-prototype.html`.

### R5 — Гость (витрина)
Главная = парадная отеля (обложка + приветствие) + витрина сервисов с **проваливанием в пространство сервиса** (шапка + типизированный контент) — главная починка. Корзина **на сервис**. Все 4 типа контента. Верхняя стеклянная строка вместо левого рельса на десктопе, модалка позиции, корзина колонкой. Оба режима группировки заведений.
Переиспуем каталог/позицию/корзину/статус, адаптируем главную и проваливание. Ориентир — `guest-prototype-v2.html`.

### R6 — Платформа /admin
Из `/platform` в `/admin` с обогащением: сводный дашборд по всем отелям; реестр отелей с фильтрами, поиском, пагинацией, массовыми действиями; карточка отеля на вкладках (Профиль / Использование и лимиты / Модули / Активность и логи / Тариф); **реестр модулей как механизм** (тариф → модули → видимость в CMS) — управляющий UI; реестр он-прем узлов; команда + роли + аудит; усиленный вход (2FA / IP-allowlist); создание отеля из шаблона онбординга; управление шаблонами и системными справочниками; экспорт и офбординг данных (152-ФЗ); тариф как запись (старт/триал/продление) — шов биллинга; чистка тестовых отелей (плюс изоляция тест-окружения, а не фильтр). «Войти в отель» — с таймером и аудитом.
Переиспуем базу консоли, достраиваем. Ориентир — `platform-admin-prototype.html`.

### R7 — Стилевой проход + светлая тема
Тёмная палитра + матовое стекло + **светлая тема во всех интерфейсах** (гость, CMS, платформа, трекеры), 1:1 с утверждёнными прототипами. Обе темы — первого класса, контраст-guard по обеим, RTL цел.

### R8 — Гибридный чат
Общий фронт-деск по умолчанию + адресный тред из сервиса; не разобрали — падает во фронт-деск. Маршрутизация как эскалация.

## Хвост (после пересборки)

1. **C3** — довести до всех 8 демо-отелей (контент уже копится с R1 — C3 достраивает остальные отели и полноту; промпт `prompt-c3-final.md`, обновить под новую модель сервисов).
2. **Перенос БД** на сервер + пересоздание платформенного админа с нормальным паролем.
3. **Домен + TLS.**
4. **Показ Кудряшову.**

## Как ведём

Каждый прогон — отдельный детальный промпт, который пишется **перед запуском** от актуального базиса (как все предыдущие фазы). Зелёный рубеж и push после каждого. Отчёт обычного формата с честными отклонениями.

Ориентиры-прототипы: `guest-prototype-v2.html`, `cms-prototype.html`, `platform-admin-prototype.html`, `staff-tracker-v2.html`; письменная карта — `guest-hub-design-map.md`.
