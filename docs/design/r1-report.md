# Отчёт R1 — Модель сервиса (фундамент)

Ветка `r1/service-model`. Базис до прогона: 450 backend / 35 E2E, `main` в синхроне.
Читать вместе с `guest-hub-design-map.md` (Часть 0) и `guest-hub-rebuild-plan.md`.

## Что сделано (по коммитам)

- **C1 — модель.** `Service` (типизированный контейнер) и `HotelModule` (реестр
  модулей) как `TenantModel`; `Category.service`; `Hotel.tariff`. Миграции:
  создание таблиц, RLS в `core` для двух новых tenant-таблиц (регистрация в
  `tenant_tables.py`), идемпотентный бэкфилл `ExecutionPoint→Service` и
  `Category.service` из `Route`. Тесты модели/RLS/реестра.
- **C2 — читатели/писатели на Service (поведение то же).** Витрина
  (`showcase.py`), hero каталога (`services.py`), редактор отделов
  (`admin_services.py`), провижининг и сид создают `Service` 1:1; коммерция
  (`charges.py`/`orders`) читает оверрайды сервиса с фолбэком на отель.
- **C3 — чистка.** С `ExecutionPoint` удалены перенесённые поля (см. «Что
  удалено»). EP стал чистым исполнителем.
- **C4 — реестр модулей: данные + API.** `module_registry.py`; платформенные
  `GET/PUT /platform/hotels/{id}/modules` + `tariff`; hotel-scoped
  `GET /cms/modules` (чтение). Контракт.
- **C5 — наглядный «Кристалл» (флаг `--with-rich-catalog`).** Доп. рестораны
  (Терраса, Сакура), рум-сервис, бар-меню, 51 позиция с фото/КБЖУ/фасетами,
  венью-часы, витринные плитки S/M/L, per-service коммерция, включённые модули.
- **C6 — контракты + i18n.** Обновлены commerce/guest-surface/hotel-admin/
  module-registry контракты; 4-язычные метки `ServiceType`/`ModuleCode`
  (`apps/hotels/vocabularies.py`), метки модулей отдаются в реестре (`title`).

## Как устроены Service / исполнитель

- **`ExecutionPoint`** — чистый исполнитель (кухня/бригада): `code`, служебный
  `title`, `kind`, `sla_minutes`, `is_active`, `realtime_group`. На него
  по-прежнему смотрят 7 FK (Order, Route, SlotConfig, StaffAssignment, ChatThread,
  NotificationChannel, EscalationRule) и весь трекер/маршрутизация/эскалации.
- **`Service`** — гостевой контейнер поверх исполнителя (**1:1 в R1**, FK +
  `unique(hotel, execution_point)`; FK, а не OneToOne, чтобы R2 ослабил связь под
  fan-out без смены типа). Несёт: тип-шаблон (`Service.Type` поверх 4 кирпичей
  `OfferingType`), гостевую идентичность (`public_name`/`tagline`/`image`/
  `is_guest_facing`), венью-часы (`schedule`), коммерч. оверрайды. `Category.service`
  = «наполнение». Маршрутизация заказа осталась на `Route` (executor-биндинг) —
  сервис читает её через `service.execution_point`.
- **Коммерция на сервисе** — nullable-оверрайды `service_fee_bp`/`tip_presets`/
  `min_order_minor`/`free_delivery_threshold_minor`/`price_round_to_minor`: `null`
  = наследовать отель. Налог/валюта/налоговый режим — только отель. Пока оверрайд
  `null`, суммы байт-в-байт те же (поведение не изменилось).

## Реестр модулей

`HotelModule(code, is_enabled, source[tariff|override], config)` — tenant-таблица
под RLS. `Hotel.tariff` — шов биллинга. API отдаёт **полный** набор кодов (дефолт
выключено/tariff) + переводимый `title`. `enabled_module_codes()` — опора гейтинга
CMS в R4. Управляющий UI — R6, гейтинг навигации — R4 (границы R1).

## Что удалено

С `ExecutionPoint` (миграция `hotels/0012`): `public_name`, `tagline`,
`is_guest_facing`, `image`, `schedule` (венью-часы), `min_order_minor`; property
`public_title`. Все читатели переключены на `Service` в C2; grep по удалённым
символам на EP — пуст. `Route` и 7 executor-FK НЕ трогали (нужны R2/R3).

## Миграция без потерь

Бэкфилл `hotels/0011`: на каждый EP — свой Service (перенос идентичности/часов/
минимума, тип из `kind`), затем `Category.service` из маршрута. Идемпотентно
(`get_or_create`, `.using(db)`). Проверено на dev-БД: `Service == ExecutionPoint`
по количеству, `Category.service` у всех замаршрутизированных категорий. На
стенде/проде бэкфилл под ролью `platform` (BYPASSRLS); в тестах таблицы пусты —
сид создаёт данные уже в новой форме.

## Честные отклонения

1. **Сид «Кристалла» — за флагом `--with-rich-catalog`, а не в дефолтной
   фикстуре.** Причина: сид гоняется на КАЖДЫЙ тест (rollback), а он генерирует
   фото позиций через медиапайплайн; 50–90 позиций × 2 отеля × 456 тестов —
   неподъёмно, плюс сломало бы тесты, завязанные на состав «Кристалла».
   Согласовано с заказчиком. Демо-витрина полного «Кристалла» — командой
   `seed_demo_hotel --with-rich-catalog`. Это совпадает с уже принятым в проекте
   приёмом (тяжёлые демо-данные за флагами: `--with-analytics-history` и др.).
   Следствие: перечисляющие тесты обновлять почти не пришлось (дефолт неизменен) —
   поправлен лишь хелпер `test_showcase` (заведение = `Service`).
2. **Реальные фото Unsplash/Pexels — не подключал.** Сид использует
   дизайнерский плейсхолдер через тот же медиапайплайн (ассет `ready`), реальное
   фото подменяется той же загрузкой. «Ноль позиций без фото, медиа ready» держится.
3. **`Service.served_locations` не выделял** — локации в R1 остаются на уровне
   категории (`ServiceLocation`), сервис их группирует. Выделенный справочник
   локаций сервиса — задел на R4 (реорг CMS).

## СТОП-точки

Ложных премис не встретил; жёстких СТОП не было. Проверял стоп-guard перед
дропом EP-полей (grep читателей `schedule`/`is_guest_facing`/… — только гость,
переключён) — дроп безопасен. Разделение Service/исполнитель однозначно
(инвариант «на каждый EP — один Service»), неоднозначности не возникло.

## Проверка

- **Backend — все 39 тест-файлов зелёные, 0 регрессий.** Прогон разбит на чанки
  (инфраструктура убивает длинные фоновые команды + общая тест-БД
  `test_guestapp`): чанк1 = 150 passed, чанк3 = 142 passed, realtime-группа = 24
  passed, чанк2 (не-realtime, вкл. `test_module_registry`) — все зелёные. Новые
  тесты: `test_service_model` (5), `test_module_registry` (4). Все «мигающие»
  ошибки первых прогонов — висящие сессии от убитых прогонов (не логика), на
  чистом ре-ране исчезали. RLS-сторож зелёный, missing-migration чист,
  `manage.py check` чист.
- Идемпотентность бэкфилла/сида проверена (повторный `migrate`/сид не дублирует);
  счётчики `Service == ExecutionPoint`, `Category.service` у всех замаршрутизированных
  категорий; потерь нет.
- Наглядность: `seed_demo_hotel --with-rich-catalog` → 51 товарная позиция с фото,
  7 venue-плиток с обложками и статусом («открыто до 23:00», бар «откроется в
  16:00», спа «до 20:00»), витрина (`build_showcase`/`build_menu`) рендерит полный
  «Кристалл» на 390/1440; вся медиа `ready`, ноль позиций/точек без фото.
- **E2E: 36/36 зелёные.** Два первичных падения — окружение, НЕ регрессии кода:
  (1) `platform-console` — неверный e-mail платформенного админа в ручном ресете
  (нужен `platform@itv.local`); (2) `analytics` экспорт — **worker-контейнер
  (Celery) не перезагружает код автоматически** и гонял до-C3 модель против
  БД с уже удалённой колонкой (`execution_point.schedule_id`). Веб-бэкенд
  перезагрузился сам (потому 34/36 прошли). После рестарта worker — зелено.

## Эксплуатационная заметка

После миграции C3 (дроп колонок EP) **worker (Celery) нужно перезапустить** —
он не подхватывает изменения модели на лету, в отличие от dev-сервера бэкенда. В
обычном деплое все контейнеры перезапускаются, здесь — вручную
(`docker compose restart worker`).
