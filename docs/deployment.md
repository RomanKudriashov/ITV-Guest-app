# Развёртывание: что ломается молча

Документ про три вещи, каждая из которых уже стоила разбирательства. Общее у
них одно: приложение при этом НЕ падает. Гость видит «Управление номером
временно недоступно» или пустой экран, в логах — ничего похожего на ошибку
развёртывания, и причину приходится искать от симптома.

Всё три всплыли при пересеве стенда с нуля (снесли том Postgres). На сервере
объекта тот же путь проходят при первой установке и при восстановлении из
бэкапа, поэтому повторятся там же.

## 1. Демо-конфигурация GRMS сеется только с `--with-room-control`

`manage.py seed_demo_hotel` **по умолчанию GRMS-демо не создаёт**: ни типа
номера с планом, ни опубликованной конфигурации. Флаг выключен намеренно —
базовый сид это то, от чего отсчитывают ожидания все остальные тесты, и тип
номера с четырнадцатью элементами сдвигал чужие проверки.

```
python manage.py seed_demo_hotel --with-room-control
```

Dev-стенд получает флаг сам: он лежит в умолчании `SEED_ARGS` в
`backend/entrypoint.sh`. В проде `SEED_ARGS` **задана и пуста** — флаг туда не
попадает, и это правильно: боевому отелю чужой демо-номер не нужен.

**Симптом, если забыть:** экран номера открывается, но контролов на нём нет
вовсе — `room-control-*` не находится ни один. Выглядит как поломка фронта.

Отдельной командой то же самое: `manage.py seed_grms_demo --subdomain <sub>`.

## 2. Ключ он-прем узла умирает вместе с базой

Локальный коннектор аутентифицируется ключом, от которого в базе лежит только
**хэш** (`OnPremNode.key_hash`) — сам ключ показывается один раз при выдаче в
админке платформы. Снесли базу — узла больше нет, а в `.env` коннектора остался
ключ от несуществующей записи.

**Симптом:** коннектор в бесконечном цикле переподключения, в его логе
`server rejected WebSocket connection: HTTP 403`, в логе backend —
`управление номером недоступно: причина=CONNECTOR_OFFLINE`. Ни одного слова про
ключ ни там, ни там: разница между «нет такого ключа» и «ключ отозван» не
раскрывается намеренно, чтобы не помогать перебору.

**Лечение:** выпустить узлу новый ключ в админке платформы и положить его в
`ITV_CONNECTOR_KEY` окружения коннектора, затем перезапустить коннектор.

Ключ **не хранится в конфиге узла** (`connector/config.dev.json`) сознательно:
конфиг попадает в бэкапы и в логи развёртывания, ключ — не должен.

## 3. Профиль `grms` не поднимается обычным `up -d`

Эмулятор iRidi и коннектор стоят под профилем `grms`:

```yaml
iridi-emulator:
  profiles: ["grms"]
connector:
  profiles: ["grms"]
```

Обычный `docker compose up -d` их **не запускает**. Так и задумано: эмулятор
изображает оборудование, и молча поднимать его вместе со стендом значило бы
однажды перепутать его с настоящим объектом.

```
docker compose --profile grms up -d
```

**Симптом, если забыть эмулятор:** коннектор подключён (в логе backend
`коннектор подключён: узел=… отель=…`), а состояние номера приходит с
`availability: unavailable` и причиной `ENDPOINT_UNREACHABLE`. От пункта 2
отличается именно причиной: `CONNECTOR_OFFLINE` — не дошли до коннектора,
`ENDPOINT_UNREACHABLE` — коннектор есть, оборудования за ним нет.

На боевом объекте эмулятор не нужен вовсе: за коннектором стоит настоящий
сервер iRidi, и профиль `grms` там поднимает только коннектор.

## Проверка после развёртывания

Один запрос отвечает сразу на все три вопроса:

```
TOKEN=$(curl -s -X POST $API/api/v1/guest/session \
  -H 'Content-Type: application/json' -H "X-Hotel-Subdomain: $HOTEL" \
  -d '{"room_number":"305","language":"ru"}' | jq -r .token)

curl -s $API/api/v1/guest/room/state \
  -H "Authorization: Bearer $TOKEN" -H "X-Hotel-Subdomain: $HOTEL" | jq '.availability, (.zones|length)'
```

Ожидается `"online"` и число зон больше нуля. `"unavailable"` — смотреть
причину в логе backend, она разводит пункты 2 и 3; ноль зон при `online`
означает пункт 1.
