# Подключение отеля

От пустого поддомена до гостя, который отсканировал код в номере и оформил
заказ. Глава для того, кто ведёт подключение: часть шагов делается в консоли,
часть — на сервере, часть — руками отеля, и путать, кто что делает, дороже
всего.

Термины — в [глоссарии](../../glossary.md).

---

## Что должно быть до начала

| | Кто даёт | Без чего не начать |
|---|---|---|
| Поддомен | мы | латиница, не из зарезервированных (`GUEST_APP_RESERVED_SUBDOMAINS`) |
| Название, часовой пояс, валюта, языки | отель | первый язык становится языком по умолчанию |
| Почта администратора | отель | пароль уходит **только** туда |
| Тариф | мы | от него зависят модули и лимиты |
| Список номеров | отель | без них некуда вести гостя |
| Есть ли управление номером | отель | если да — дальше [коннектор](connector.md) |

Почта — не формальность. Пароль администратора отеля показывается **один раз**
и уходит письмом; в интерфейсе его потом не посмотреть. Адрес, к которому у
отеля нет доступа, запирает отель насмерть — это чинится отдельной командой
смены адреса, и лучше туда не попадать.

---

## 1. Завести тенанта

Из консоли: **Флот → Новый отель**. То же самое командой, если консоль
недоступна:

```bash
docker compose -f docker-compose.prod.yml --env-file .env.prod \
  exec -T backend python manage.py create_hotel \
  --subdomain=grand --name="Grand Hotel" --admin-email=admin@grand.example \
  --tz=Europe/Moscow --currency=RUB --languages=ru,en
```

Заведение идёт **одной транзакцией**: либо отель есть целиком, либо его нет
вовсе. Занятый поддомен даёт чистый отказ, а не полусозданный отель — это
важно, потому что полусозданный тенант выглядит рабочим ровно до первого
гостя.

Пароль администратора выводится один раз. Если не задан — генерируется.

---

## 2. Сертификат на новый поддомен

**Шаг, который забывают, и отель узнаёт об этом первым.** Отель адресуется
поддоменом, а сертификат выписан на перечисленные имена. Новый поддомен в
списке не появится сам:

```bash
APP_DOMAIN=example.com ./infra/nginx/enable-tls.sh admin@example.com
docker compose -f docker-compose.prod.yml --env-file .env.prod restart nginx
```

Проверка — именем, а не «сайт открылся у меня»:

```bash
echo | openssl s_client -connect grand.example.com:443 -servername grand.example.com 2>/dev/null \
  | openssl x509 -noout -checkend 0 -subject
```

На настоящем домене это снимается wildcard-сертификатом по DNS-01, и тогда шаг
исчезает совсем. Пока домена нет, шаг обязателен на каждом подключении.

---

## 3. Тариф и модули

В консоли: карточка отеля → **Тариф**. Тариф задаёт модули и лимиты; поверх
него живёт **намерение**: выключенный руками модуль не зажигается новым
тарифом.

Смена тарифа вниз гасит модули, которых в новом нет. Гаснущие показываются
**поимённо до нажатия** — это единственный момент, когда их видно; после
нажатия отель просто обнаружит пропажу.

Если у отеля есть управление номером, модуль `room_control` включается здесь,
до всего остального: без него экран номера гостю не покажется, сколько бы
оборудования ни было настроено.

---

## 4. Что отель делает сам

Дальше администратор отеля входит на `<поддомен>/admin` и наполняет:

1. **Номера** — иначе гостю некуда войти.
2. **Заведения** (ресторан, бар, спа, консьерж) и их часы.
3. **Точки исполнения** и сотрудников: доска работает на точке, а не на
   заведении. Заявка, у которой нет точки, не появится ни у кого.
4. **Каталог** — меню, услуги, слоты, информационные страницы.
5. **Бренд** — цвета, логотип, фотографии.

Наше дело здесь — не наполнять за отель, а проверить, что не осталось
заведения без точки исполнения: это самая частая дыра, и обнаруживается она
первым заказом, который никому не пришёл.

---

## 5. Управление номером

Только если оборудование есть. Порядок — в [connector.md](connector.md);
коротко: тип номера → элементы → публикация конфигурации → узел и ключ →
проверка на живой комнате.

**Тип номера, а не комната.** Настройка делается один раз на тип; комнаты
наследуют. Настраивать покомнатно — способ получить сто расхождений там, где
должно быть одно решение.

---

## 6. Коды в номера

Печатный QR кодирует `/r/:roomNumber` — например `/r/401`. Форма ссылки
**заморожена**, и сторож книги следит за ней вместе с маршрутизатором: коды наклеены
на стены, и смена схемы означает перепечатку по всему отелю.

Перед печатью тиража проверяется один код на одном номере, целиком: скан →
витрина → номер узнан → заказ оформляется. Тираж печатается после этого, а не
до.

---

## 7. Приёмка

Проходится целиком, в этом порядке, до того как отель пустит гостей.

| Проверка | Что доказывает |
|---|---|
| `https://<поддомен>/` открывает витрину | тенант резолвится по поддомену |
| Скан кода из номера → номер узнан | deep-link и комнаты на месте |
| Заказ доходит до доски исполнителя | точка исполнения назначена |
| Смена статуса видна гостю без перезагрузки | живой канал работает |
| Просрочка и эскалация срабатывают | пороги заданы, старший назначен |
| `https://<поддомен>/admin` пускает администратора | учётка и почта дошли |
| Консоль **не** открывается на адресе отеля | изоляция платформы цела |
| Управление номером на живой комнате | если модуль включён |

Последняя строка в таблице проверок — не формальность:

```bash
curl -sS -X POST https://grand.example.com/api/v1/platform/auth/login \
     -H 'Content-Type: application/json' -d '{"email":"…","password":"…"}'
```

Обязан вернуть **404 `platform_wrong_host`**. Токен здесь означает, что
мастер-ключ платформы доступен с адреса клиента.

---

## 8. Чего мы отелю не обещаем

Сказать это стоит до подключения, а не после первого вопроса:

* **PMS не подключён** — заселение и выезд в систему не приезжают. Выезд
  отмечается кнопкой в панели, PIN проживания имеет срок.
* **Оплаты нет** — заказ оформляется без списания.
* **Push закрытому приложению не приходит** — уведомление живёт, пока
  приложение открыто или свёрнуто.
