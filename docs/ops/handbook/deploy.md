# Выкатка обновления

Эта глава собрана не из замысла, а из пяти выкаток и одного разбора. Каждый
абзац, помеченный **«стоило нам»**, стоял денег или ночи; остальное — обычный
порядок.

Главная мысль одна и стоит того, чтобы её назвать до команд:

> **Успешно выполненная команда — не доказательство, что новый код поехал.**
> Доказательство — файл, прочитанный **внутри** контейнера, и действие,
> выполненное **после** выкатки.

Установка с нуля — в [install.md](install.md). Здесь — обновление системы, в
которой уже живут отели.

---

## 0. До того, как трогать сервер

Прогоны идут **последовательно, а не параллельно**: и pytest, и Playwright
работают против одного контейнера бэкенда, и одновременный запуск даёт ложные
падения по таймаутам — их потом полдня читают как настоящие.

```bash
docker compose exec -T backend python -m pytest -q          # сначала это
cd e2e && npx playwright test                               # и только потом это
```

Красный прогон означает «выкатки нет». Не «выкатим и посмотрим на стенде»:
стенд — это то, что показывают клиенту.

---

## 1. Код на сервер

```bash
ssh deploy@<сервер>
cd ~/itv-guest
git fetch --all && git log --oneline HEAD..origin/main   # что именно едет
git pull --ff-only
```

`--ff-only` не даст молча создать merge-коммит на сервере. Сервер — не место,
где разрешаются расхождения истории.

---

## 2. Сборка: **все шесть образов, поимённо**

> **Стоило нам 39 часов.** Воркер и планировщик собираются из того же каталога
> `./backend`, но это **отдельные образы** с отдельными именами. `up -d --build
> backend` пересобирает **только** бэкенд; воркер и планировщик остаются на
> предыдущем слое. Внешне всё зелено: контейнеры подняты, API отвечает новым
> кодом. А фоновые задачи полтора суток исполнял старый код — и заметили это не
> по логам, а по тому, что публикация вела себя не так, как её только что
> переписали.

Образы:

| Образ | Что внутри |
|---|---|
| `itv-guest-prod-backend` | API и WebSocket |
| `itv-guest-prod-worker` | фоновые задачи (публикация, уведомления) |
| `itv-guest-prod-beat` | расписание |
| `itv-guest-prod-nginx` | **собранный фронт** плюс сам nginx |
| `itv-guest-prod-connector` | коннектор (только стенд) |
| `itv-guest-prod-iridi-emulator` | эмулятор оборудования (только стенд) |

Собирать явно и всё сразу:

```bash
docker compose -f docker-compose.prod.yml --env-file .env.prod build \
  backend worker beat nginx connector iridi-emulator
docker compose -f docker-compose.prod.yml --env-file .env.prod up -d
```

Правило простое: **перечисляйте сервисы, а не полагайтесь на `--build` при
`up`.** Список из шести имён скучен, зато не зависит от того, вспомнил ли
человек про воркер.

## 3. Проверка сборки — чтением **внутри** контейнера

Не `docker images`, не «команда прошла», не дата создания образа. Берём файл,
который в этом коммите изменился, и читаем его там, где он теперь исполняется:

```bash
for s in backend worker beat; do
  echo "== $s"
  docker compose -f docker-compose.prod.yml --env-file .env.prod \
    exec -T $s sh -c 'grep -c "<строка из нового кода>" /app/<путь/к/файлу.py> || echo НЕТ'
done
```

Три контейнера — три ответа. Если воркер отвечает «НЕТ», значит он на старом
образе, и вся выкатка недействительна, как бы ни выглядел `ps`.

Быстрая версия того же — сравнить идентификаторы образов и убедиться, что они
различаются с прошлым разом:

```bash
docker compose -f docker-compose.prod.yml --env-file .env.prod \
  images backend worker beat nginx
```

Она короче, но слабее: совпадение идентификаторов доказывает, что образ один и
тот же, а несовпадение не доказывает, что внутри новый код. Чтение файла —
доказательство, идентификатор — намёк.

### Почему сверка бандла по контрольной сумме больше не работает

Раньше фронт проверялся так: собрать локально, взять `sha256` бандла, сравнить
с тем, что лежит в контейнере nginx. Сходится — фронт новый.

Это сломалось, когда домен стал **аргументом сборки**. `APP_DOMAIN` попадает в
образ nginx через `build.args` и запекается в бандл: по нему фронт отличает
корень платформы от адреса отеля. Локальная сборка идёт с другим доменом, то
есть даёт другой байт — и **другую сумму при том же коде**. Сумма перестала
отвечать на вопрос «тот ли это код» и стала отвечать «тот ли это домен».

Сверять надо **по содержимому**, и именно тем, что должно было измениться:

```bash
# 1. Домен зашит правильный — иначе корень покажет витрину вместо лендинга.
docker compose -f docker-compose.prod.yml --env-file .env.prod \
  exec -T nginx sh -c 'grep -ro "app\.[0-9.]*\.sslip\.io" /usr/share/nginx/html/assets | head -1'

# 2. Новый код доехал: строка, которой в прошлой сборке не было.
docker compose -f docker-compose.prod.yml --env-file .env.prod \
  exec -T nginx sh -c 'grep -rc "<новая строка интерфейса>" /usr/share/nginx/html/assets | grep -v ":0"'
```

Первый запрос — самая частая тихая поломка фронта: домен не передался, бандл
собрался, всё зелено, а корень платформы показывает гостевую витрину. Перезапуск
не лечит: это **сборочный** аргумент, нужна пересборка nginx.

## 4. Миграции

При старте бэкенд сам гоняет `migrate --database=platform`. Обычно этого
достаточно, и отдельного шага нет.

> **Почему платформенной ролью.** У неё `BYPASSRLS`. Роль приложения видит
> только строки своего тенанта, а вне тенанта — **ноль строк, а не ошибку**.
> Data-миграция под ней отработает «успешно» и не тронет ни одной строки:
> ни исключения, ни предупреждения, ни следа в логе. Это самый дорогой класс
> отказов в системе, и он выглядит как зелёный прогон.

Что посмотреть после старта:

```bash
docker compose -f docker-compose.prod.yml --env-file .env.prod \
  exec -T backend python manage.py showmigrations | grep -v '\[X\]'
```

Пусто — все применены. Если миграцию приходится гонять руками (перезапуск после
сбоя, доливка данных), ключ обязателен:

```bash
… exec -T backend python manage.py migrate --database=platform
```

**Data-миграция, которая ходит по тенантным таблицам, обязана либо идти
платформенной ролью, либо открывать тенанта явно** (`tenant_context`). Третьего
нет; «просто ORM» здесь тихо ничего не делает.

## 5. Что проверяется **исполнением** после выкатки

Проверка, которую можно пройти, ничего не запустив, ничего не значит. После
каждой выкатки исполняется следующее:

| Проверка | Команда | Что доказывает |
|---|---|---|
| Живость | `curl -sS https://<домен>/api/v1/health` | база, Redis, MinIO отвечают |
| Фоновая очередь | запустить публикацию на один отель из консоли | воркер **исполняет новый код**, а не просто поднят |
| Расписание | `docker compose … logs beat --since 5m` | планировщик тикает после перезапуска |
| Целостность стенда | `manage.py check_demo_stand` | демо-отель не потерял то, что показывают клиенту |
| Адресная схема | `e2e/tests/address-scheme.spec.ts` | консоль недоступна с адреса отеля, редиректы живы |
| Обход глазами | `PLATFORM_PASSWORD=… node e2e/stand-sweep.mjs` | ошибки в консоли браузера, упавшие запросы, пустые экраны |

Фоновая очередь стоит в списке не для полноты: **это единственная проверка,
которая ловит невыкаченный воркер.** Всё остальное зелено и при старом образе.

Пароли обходных скриптов берутся из окружения (`PLATFORM_PASSWORD`), а лежат в
`.env.prod` на сервере. В репозитории их нет и быть не должно — однажды они там
были, и это исправлено вместе с этой книгой.

## 6. Убрать за собой

Прогоны оставляют следы на общем стенде: тестовые отели, заказы, узлы.

```bash
docker compose -f docker-compose.prod.yml --env-file .env.prod \
  exec -T backend python manage.py clean_test_residue
docker system prune -f            # слои от предыдущих сборок
```

Второе — не гигиена, а место на диске. Стенд уже падал целиком, и первым, что
надо было смотреть, оказался `df -h`: диск кончился после серии сборок, и
Postgres перестал писать. С той стороны это выглядело как «сервер не отвечает»,
и полчаса ушло на поиск причины в приложении.

## 7. Если что-то пошло не так

Порядок разбора — снизу вверх, и **состояние снимается до того, как что-либо
перезапускается**: перезапуск стирает улику, и тогда причину не узнают вовсе.

Полный порядок — в [triage.md](triage.md). Кратко:

1. `df -h` и `docker ps` — диск и живость контейнеров.
2. Логи упавшего, не пересказ, а текст: `docker compose … logs --tail=200 <сервис>`.
3. nginx **изнутри** (`curl` из его контейнера в бэкенд) и снаружи — это разные
   отказы, и лечатся они разным.
4. Только потом перезапуск, и после него — те же проверки исполнением из §5.

Откат — это выкатка предыдущего коммита по тому же порядку, **включая все шесть
образов**. Откатить один бэкенд означает оставить воркер на новом коде: ровно
та же ошибка, что стоила 39 часов, только зеркальная.
