## Управление стендом

Все команды выполняются на сервере, в каталоге проекта:

    ssh root@147.45.245.172
    cd /home/deploy/ITV-Guest-app

Дальше везде используется один и тот же префикс — вынесен ради краткости:

    dc() { docker compose -f docker-compose.prod.yml --env-file .env.prod "$@"; }

### Состояние и логи

    dc ps                         # что поднято
    dc logs -f backend            # логи одной службы
    dc logs --tail 100 connector  # коннектор управления номером

### Перезапуск и обновление кода

    dc restart backend

    sudo -u deploy git fetch origin main
    sudo -u deploy git reset --hard origin/main
    dc build backend worker beat nginx iridi-emulator connector
    dc up -d

Стенд живёт на ветке `main` (раньше был на `deploy/stand-full`). Сливать
руками нечего и незачем: у пользователя `deploy` нет git-identity, поэтому
только `reset --hard`.

ОБРАЗЫ ПЕРЕСОБИРАТЬ ОБЯЗАТЕЛЬНО. Один `up -d` после `git reset` поднимает
старые образы: код в них запечён, а не смонтирован, и стенд молча работает
по вчерашнему коду — на этом уже обжигались. Отдельно про `nginx`: в нём
собран бандл интерфейса, без его пересборки правки консоли и CMS на стенд
не попадают. Неизменившиеся службы пересборка не трогает — слои берутся из
кэша, это быстро.

Обновляться надо ИМЕННО от пользователя `deploy`: ключ доступа к репозиторию
лежит у него, у `root` его нет.

### Наполнение

    dc exec backend python manage.py seed_demo_hotel --force \
        --with-rich-catalog --with-room-control --with-marketing-badges
    dc exec backend python manage.py seed_demo_fleet

Обе команды идемпотентны: повторный прогон досоздаёт недостающее и не
дублирует существующее.

### Проверка наполнения — ПОСЛЕ КАЖДОГО ДЕПЛОЯ

    dc exec backend python manage.py check_demo_stand

Ненулевой код возврата означает «стенд обеднел», и в выводе сказано, чего
именно не хватает: номеров, заказов, сессий по каждому из трёх отелей, а у
«Кристалла» ещё тип GRMS, публикация, привязка комнаты, PIN, зоны и элементы.

Гнать её после каждого деплоя, а не только перед показом. Проверка ничего не
чинит — это осознанно: команда, которая молча дочиняет стенд, скрывает сам
факт деградации.

Считает она ЧЕРЕЗ приложение, а не запросом в базу. Причина в RLS: `psql` под
ролью `guestapp` без выставленного тенанта возвращает ноль строк, и полный
стенд выглядит пустым. Если проверяете руками — либо этой командой, либо
`select set_config('app.current_hotel','<id отеля>',false);` перед запросом.

## Демо-активность: заказы, чаты, отзывы

История заказов на стенде создана **генератором**, а не руками:

    dc exec backend python manage.py seed_activity --orders 300 --days 60

Что он делает: гости в разных номерах и в разное время суток, заказы всех
типов (корзина с модификаторами, заявка-услуга, бронь слота, агрегат
рум-сервиса с разъездом по нескольким заведениям), полный жизненный цикл —
принят, в работе, готов, завершён, часть отменена, часть брошена до
эскалации, — плюс переписки и отзывы. Всё растянуто на два месяца назад,
иначе аналитике нечего показывать.

**Как отличить его записи от настоящих.** Все сессии генератора помечены:

    GuestSession.guest_ref = "actgen:v1"

Остальное привязано к сессии ссылками — заказ знает сессию, отзыв знает
заказ, ветка чата знает сессию. Поле служебное (ссылка на гостя в PMS),
гостю не показывается.

**Как убрать за собой:**

    dc exec backend python manage.py seed_activity --clean            # показать
    dc exec backend python manage.py seed_activity --clean --apply    # убрать

Без `--apply` не удаляется ничего. После уборки журнал аналитики
пересобирается из оставшихся заказов, поэтому цифры на дашборде сходятся и
после отката.

Объём задаётся `--orders` и означает «сколько должно быть ВСЕГО»: повторный
прогон с тем же числом не создаёт ничего, с бо́льшим — досоздаёт хвост.

## Почта: где смотреть письма

Пароль администратора отеля **не показывается оператору** — он уходит
администратору письмом. Оператор видит только адрес доставки. Поэтому без
работающей почты консоль не заводит отели и не сбрасывает пароли: она
отвечает отказом, а не делает вид, что получилось.

Письма ловит **Mailpit** — служба `mailpit` в компоузе. Настоящие письма
наружу не уходят: всё, что отправлено, оседает в ней.

**В письмах лежат НАСТОЯЩИЕ пароли от панелей отелей.** Ящик — это связка
ключей от всех отелей стенда, и относиться к нему надо так же.

Поэтому порт наружу **не опубликован**. Смотреть письма — через SSH-туннель
со своей машины:

    ssh -L 8025:localhost:8025 root@147.45.245.172 \
        -N -o ExitOnForwardFailure=yes

Пока команда висит, откройте http://localhost:8025 — спросит логин и пароль,
они лежат в `MAILPIT_UI_AUTH` в `/home/deploy/ITV-Guest-app/.env.prod`.

Посмотреть последние письма без браузера:

    dc exec mailpit sh -c 'wget -qO- \
        "http://ЛОГИН:ПАРОЛЬ@127.0.0.1:8025/api/v1/messages?limit=5"'

Логин и пароль идут В АДРЕСЕ, а не отдельными ключами: внутри образа Mailpit
лежит busybox-wget, и `--user`/`--password` он не понимает — прежний рецепт
отвечал «unrecognized option» и ничего не показывал.

Если консоль отвечает «Письмо с паролем не ушло» или «Почта не настроена» —
проверьте службу: `dc ps mailpit` и `dc logs mailpit`.

## Фотографии

Снимки демо-каталога скачиваются **на хосте**, а не из контейнера: у хоста
есть IPv6 до CDN, у docker-сети его нет, и из контейнера TLS-рукопожатие с
`images.unsplash.com` не проходит.

Кэш лежит на хосте и примонтирован в контейнер:

    /home/deploy/ITV-Guest-app/backend/apps/.seed_photos

Если каталог опустеет (например, после `git clean`), снимки надо докачать
на хосте — список кодов и адресов отдаёт манифест
`backend/apps/media/services/seed_photos.py`. Изнутри контейнера
`manage.py fetch_seed_photos` на этом сервере не сработает.

## Резервные копии

Снимаются каждую ночь в 4:00 в `/var/backups/itv`, хранятся последние семь.
Задание: `/etc/cron.d/itv-backup`, скрипт `/opt/itv-backup/bin/backup.sh`,
лог `/var/log/itv-backup.log`.

Снять прямо сейчас:

    /opt/itv-backup/bin/backup.sh

Копия — это дамп Postgres (`db-<дата>.dump`) и архив хранилища
(`minio-<дата>.tgz`). Восстановление проверялось 11.08.2026.

Скрипта восстановления в комплекте НЕТ — разворачивать надо руками:

    dc stop backend worker beat
    dc exec -T postgres pg_restore -U "$POSTGRES_SUPERUSER" -d "$POSTGRES_DB" \
        --clean --if-exists < /var/backups/itv/db-<дата>.dump
    dc start backend worker beat

## Управление номером: если коннектор потерял ключ

Самая частая причина «Управление номером временно недоступно» —
пересоздание базы: узел остаётся в конфиге, а ключа в базе уже нет.

1. Платформенная консоль → Узлы → у узла `stand-connector` кнопка
   «Перевыпустить». Ключ показывается ОДИН раз — скопируйте сразу.
2. Впишите его в `.env.prod` в строку `ITV_CONNECTOR_KEY=`.
3. `dc up -d connector`
4. Проверьте: `dc ps connector` — должно быть `Up`, а не `Restarting`,
   и в `dc logs connector` последней строкой «подключились к backend».

## Если что-то не поднимается

* **`dependency failed to start` у postgres** — почти всегда пустая
  переменная в `.env.prod`. Healthcheck идёт с пустым `-U`, и падает вся
  сборка. Сверьте `.env.prod` со списком `${...}` из `docker-compose.prod.yml`.
* **Гостевая главная отдаёт 500** — проверьте `CACHE_URL` в `.env.prod`:
  погода читает кэш первой.
* **Пропали все фотографии** — проверьте `GUEST_APP_PUBLIC_SCHEME=https`:
  на HTTPS-странице `http`-картинка блокируется браузером.
* **«Управление номером недоступно»** — `dc logs connector`. Если там
  `403` в петле, коннектор не проходит проверку источника на сокете; если
  ошибка про ключ — см. раздел выше.
* **Кончилось место** — `df -h`. Съедают обычно копии (`/var/backups/itv`)
  и хранилище. Логи Docker ограничены 50 МБ на службу и сами не разрастутся.

## Чего на стенде НЕТ

* **Живого iRidi.** Оборудование изображает эмулятор в соседнем контейнере.
  Команды доходят и подтверждаются по-настоящему, но лампы горят понарошку.
* **PMS.** Заселение и выезд не подключены: комнаты и гости заведены сидом.
* **Настоящих push-уведомлений.** Уведомление о смене статуса заказа
  приходит, пока приложение открыто (можно свернуть). Закрытому приложению
  не придёт — для этого нужен отдельный механизм, его пока нет.
* **Оплаты.** Заказ оформляется без списания денег.
