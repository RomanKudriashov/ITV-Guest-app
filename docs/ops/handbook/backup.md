# Резервные копии и восстановление

Копия, из которой ни разу не поднимались, — это не копия, а надежда. Поэтому
глава состоит из трёх частей, и вторая с третьей важнее первой:

1. как снимается,
2. **как из неё подняться**,
3. **как убедиться, что она рабочая** — не открыв её в проде.

---

## Что вообще нужно сохранить

| Что | Где живёт | В копии |
|---|---|---|
| База | том `postgres_data` | дамп `db-<дата>.dump` |
| Картинки и файлы | том `minio_data` | архив `minio-<дата>.tgz` |
| Конфигурация | `.env.prod` на сервере | **нет — сохраняется отдельно** |
| Сертификаты | `/etc/letsencrypt` | нет, перевыпускаются |
| Роли Postgres | кластер, не база | **нет — см. ниже** |
| Ключ узла коннектора | хэш в базе | восстановлению не подлежит |

Две строки со словом «нет» — это то, обо что спотыкается восстановление, и обе
разобраны дальше по тексту.

---

## 1. Снятие

> **В репозитории средств снятия копий НЕТ.** Ни скрипта, ни задания cron:
> всё это заведено руками на нашем стенде и в поставку не входит. Новая
> установка резервных копий не имеет вообще, и узнать об этом лучше сейчас,
> чем в день, когда они понадобятся. Раздел 1.1 — что делать на новом сервере;
> раздел 1.2 — как это устроено у нас.

### 1.1. На новой установке — двумя командами

```bash
D=/var/backups/itv && mkdir -p $D && T=$(date +%F)
docker compose -f docker-compose.prod.yml --env-file .env.prod \
  exec -T postgres pg_dump -U "$POSTGRES_SUPERUSER" -Fc "$POSTGRES_DB" > $D/db-$T.dump
docker run --rm -v <проект>_minio_data:/data -v $D:/backup alpine \
  tar czf /backup/minio-$T.tgz -C /data .
```

`<проект>` — имя проекта compose, то есть имя каталога: `docker volume ls`
покажет точное имя тома. Формат `-Fc` (custom) обязателен — из него умеет
`pg_restore` с `--clean`, а из простого SQL-дампа нет.

Обе команды повесить в cron и **проверить, что копия рабочая** (§3). Задание,
которое пишет нулевой файл, выглядит точно так же, как задание, которое
работает.

### 1.2. Как это устроено на нашем стенде

Копии снимаются каждую ночь в 4:00 в `/var/backups/itv`, хранятся последние
семь. Задание — `/etc/cron.d/itv-backup`, скрипт
`/opt/itv-backup/bin/backup.sh`, лог `/var/log/itv-backup.log`.

Снять прямо сейчас (перед выкаткой, перед миграцией данных, перед любой
необратимой операцией):

```bash
/opt/itv-backup/bin/backup.sh
ls -lh /var/backups/itv | tail -5
```

Смотреть надо на **размер**. Дамп, который вдруг стал в десять раз меньше
вчерашнего, — это не «сжался лучше», это упавший посреди работы `pg_dump`,
который вернул нулевой код и оставил обрезанный файл.

## 2. Восстановление

Скрипта восстановления в комплекте нет намеренно: восстановление — операция,
которую делают руками, глядя на то, что делают.

### 2.1. Остановить тех, кто пишет

```bash
cd ~/ITV-Guest-app
docker compose -f docker-compose.prod.yml --env-file .env.prod stop backend worker beat
```

**Воркер и планировщик — обязательно.** Забытый воркер продолжит исполнять
задачи поверх восстанавливаемой базы, и получится смесь двух состояний, худшая,
чем любое из них.

### 2.2. База

```bash
docker compose -f docker-compose.prod.yml --env-file .env.prod \
  exec -T postgres pg_restore -U "$POSTGRES_SUPERUSER" -d "$POSTGRES_DB" \
  --clean --if-exists < /var/backups/itv/db-<дата>.dump
```

`--clean --if-exists` сносит существующие объекты перед заливкой. Это значит,
что **команда необратима**: она сначала удаляет, потом восстанавливает, и
прерванная посередине оставляет базу без обеих версий. Перед восстановлением в
живой системе снимите свежую копию того, что есть сейчас, даже если оно
сломано.

`pg_restore` печатает предупреждения на несуществующие объекты — при
`--if-exists` это норма. Ошибки, на которые надо смотреть, содержат `ERROR:` и
не содержат `does not exist`.

### 2.3. Роли — если кластер новый

**Здесь ломается восстановление на чистый сервер.** `pg_dump` одной базы **не
содержит ролей**: роли живут в кластере. У нас их три, и на них держится вся
изоляция — роль приложения без `BYPASSRLS`, платформенная с ним, и
суперпользователь для обслуживания.

Роли создаёт `infra/postgres/init/01-roles.sh`, и он исполняется **один раз при
инициализации пустого кластера**. Если вы поднимаете новый сервер из
`docker-compose.prod.yml` с теми же переменными — роли создадутся сами, и шага
нет. Если заливаете дамп в чужой или уже существующий кластер — роли надо
завести руками до восстановления, иначе политики RLS сошлются на
несуществующие роли и заливка упадёт.

Проверить, что они на месте:

```bash
docker compose … exec -T postgres psql -U "$POSTGRES_SUPERUSER" -d "$POSTGRES_DB" \
  -c "\du" | grep -E "guestapp|platform"
```

Платформенная обязана иметь `Bypass RLS`, роль приложения — **не иметь**.
Перепутанные местами роли не сломают ничего заметного: система будет работать,
а изоляция отелей исчезнет.

### 2.4. Хранилище

```bash
docker compose … stop minio
docker run --rm -v <проект>_minio_data:/data -v /var/backups/itv:/backup alpine \
  sh -c 'rm -rf /data/* && tar xzf /backup/minio-<дата>.tgz -C /data'
docker compose … start minio
```

База и хранилище — **две копии одного момента**. Восстановленные из разных
дат, они дают каталог, где половина картинок не открывается: строки о файлах
есть, файлов нет. Даты берите парой.

### 2.5. Поднять и проверить

```bash
docker compose -f docker-compose.prod.yml --env-file .env.prod start backend worker beat
docker compose … exec -T backend python manage.py migrate --database=platform
docker compose … exec -T backend python manage.py showmigrations | grep '\[ \]'
```

Миграция после восстановления обязательна, если код новее копии: дамп несёт
схему на момент снятия. И **платформенной ролью** — под ролью приложения
data-миграции по тенантным таблицам молча не сделают ничего.

### 2.6. Ключ узла

Ключ коннектора в базе лежит **хэшем**. Восстановление базы вернёт узел, но не
ключ; если ключ на объекте потерян вместе с сервером — его надо перевыпустить
в консоли и положить на объект заново. Иначе коннектор уйдёт в рестарт-петлю,
а гость увидит «управление номером недоступно» без внятной причины.

## 3. Как убедиться, что копия рабочая

Проверка обязана идти **мимо прода**. Разворачиваем копию во временную базу
того же кластера и задаём ей вопросы.

```bash
D=/var/backups/itv/db-$(date +%F).dump
docker compose … exec -T postgres createdb -U "$POSTGRES_SUPERUSER" restore_check
docker compose … exec -T postgres pg_restore -U "$POSTGRES_SUPERUSER" \
  -d restore_check < "$D" 2>&1 | grep -c "ERROR:"
```

Ноль ошибок — необходимое условие, но не достаточное. Дальше три вопроса,
каждый из которых ловит свой класс негодной копии:

```sql
-- 1. Данные на месте, а не только схема.
SELECT (SELECT count(*) FROM hotels_hotel)      AS отели,
       (SELECT count(*) FROM accounts_user)     AS учётки,
       (SELECT count(*) FROM orders_order)      AS заказы;

-- 2. Копия свежая, а не позавчерашняя, переложенная под сегодняшним именем.
SELECT max(created_at) FROM core_audit_log;

-- 3. Изоляция цела: политики RLS приехали вместе с таблицами.
SELECT count(*) FROM pg_policies WHERE schemaname = 'public';
```

Третий вопрос — тот, ради которого всё и затевается. Дамп со схемой и данными,
но без политик, восстановится **без единой ошибки** и даст систему, в которой
отели видят друг друга. Политик у нас 65; число должно совпадать с продовым:

```bash
docker compose … exec -T postgres psql -U "$POSTGRES_SUPERUSER" -d "$POSTGRES_DB" \
  -c "SELECT count(*) FROM pg_policies WHERE schemaname='public'"
```

Самая честная проверка — **под ролью приложения, без тенанта**:

```bash
docker compose … exec -T postgres psql -U guestapp -d restore_check \
  -c "SELECT count(*) FROM orders_order"
```

Обязан вернуть **ноль**. Не ошибку — ноль: вне тенанта роль приложения не
падает, она не видит ничего. Ненулевое число здесь означает, что изоляции в
восстановленной базе нет, и узнать об этом лучше сейчас, чем на живом отеле.

Убрать за собой:

```bash
docker compose … exec -T postgres dropdb -U "$POSTGRES_SUPERUSER" restore_check
```

## Чего эта копия не спасёт

* **Конфигурацию.** `.env.prod` в копию не входит. Потеряв сервер вместе с ним,
  вы теряете секреты подписи — все выданные токены станут недействительны, а
  MinIO не отдаст файлы. Храните `.env.prod` отдельно, в менеджере секретов.
* **Удаление, замеченное поздно.** Хранятся семь ночей. Ошибка, обнаруженная на
  восьмой день, уже не откатывается.
* **Момент между копиями.** Всё, что произошло после 4:00, теряется. Перед
  необратимой операцией копия снимается руками, а не «ночная же есть».
