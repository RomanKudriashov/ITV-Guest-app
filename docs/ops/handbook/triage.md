# Разбор отказа

Глава о том, как искать причину, а не как чинить. Чинить — дело простое, когда
известно что; девяносто процентов времени уходит на «что».

Три правила, каждое куплено дорого:

> **1. Снимите состояние до того, как что-нибудь перезапустите.** Перезапуск —
> самый быстрый способ вылечить симптом и потерять причину навсегда. Отказ,
> вылеченный перезапуском без снимка, вернётся, и разбор начнётся с нуля.
>
> **2. Показывайте логи, а не пересказ.** «Там ошибка подключения» и `FATAL:
> password authentication failed for user "guestapp"` — разные объёмы
> информации, и второй короче.
>
> **3. Сначала докажите, что сломались мы.** Половина «система лежит» — это не
> система.

## Порядок: снизу вверх

Слои проверяются от самых немых к самым разговорчивым. Верхний слой всегда
жалуется громче, но причина почти всегда ниже.

```bash
# 0. Снимок — ПЕРВЫМ ДЕЛОМ, до любых действий
mkdir -p /tmp/incident && cd /tmp/incident
df -h > disk.txt
docker compose -f docker-compose.prod.yml --env-file .env.prod ps > ps.txt
for s in backend worker beat nginx postgres redis connector; do
  docker compose -f docker-compose.prod.yml --env-file .env.prod \
    logs --tail=300 $s > log-$s.txt 2>&1
done

# 1. Диск — первым, всегда
df -h

# 2. Контейнеры: кто не Up, кто в Restarting
docker compose … ps

# 3. База и Redis отвечают?
docker compose … exec -T postgres pg_isready
docker compose … exec -T redis redis-cli ping

# 4. Бэкенд отвечает ИЗНУТРИ (минуя nginx и всю сеть)
docker compose … exec -T backend curl -fsS http://localhost:8000/api/v1/health

# 5. Бэкенд отвечает ИЗ NGINX (сеть compose жива)
docker compose … exec -T nginx curl -fsS http://backend:8000/api/v1/health

# 6. И только теперь — снаружи
curl -sS -o /dev/null -w '%{http_code} %{time_total}\n' https://<домен>/api/v1/health
```

**Диск первым не по алфавиту.** Стенд уже падал целиком после серии сборок:
место кончилось, Postgres перестал писать, и снаружи это выглядело как «сервер
не отвечает». Полчаса ушло на поиск причины в приложении.

**Шаги 4, 5 и 6 — три разных отказа.** Отвечает изнутри, но не из nginx —
сеть compose. Отвечает из nginx, но не снаружи — TLS, порты или путь до нас.
Не отвечает изнутри — это наконец приложение.

## Случай 1. «Стенд не отвечает», а он жив

**Как выглядело.** Стенд перестал открываться сразу после выкатки. Естественная
версия — выкатка и сломала.

**Что показал разбор.** Все слои изнутри — зелёные: контейнеры `Up`, база
отвечает, бэкенд отвечает и себе, и из nginx. Снаружи — то ответ за 200 мс, то
обрыв. Ключевой замер:

```
$ for i in $(seq 1 20); do curl -sS -o /dev/null -w '%{http_code} %{time_total}\n' https://<домен>/api/v1/health || true; done
200 0.21
200 0.19
curl: (56) OpenSSL SSL_read: Connection reset by peer
200 0.22
curl: (35) error:0A000126:SSL routines::unexpected eof while reading   # после 5.03 с
200 0.20
```

Обрывы **на TLS**, не на HTTP: соединение рвётся до того, как приложение
что-либо увидит. Доля — от десяти до тридцати процентов, время до обрыва
подозрительно ровное. Приложение о таких запросах не знает вовсе: в логах
nginx их нет, потому что рукопожатие не закончилось.

**Вывод: обрывается сетевой путь, а не стенд.** Причина была на нашей стороне
пути — туннель между наблюдателем и сервером. Ничего не перезапускали.

**Как отличить за минуту.** Три признака, любые два из которых означают «это
путь»:

* изнутри контейнера всё зелено, а снаружи мигает;
* обрывы **не в логах** приложения (их там и не может быть);
* тот же адрес с другой точки — с телефона по мобильной сети, с чужого
  сервера — отвечает стабильно.

**Чего не делать.** Не перезапускать nginx «на всякий случай». Перезапуск
уберёт симптом на несколько минут — ровно настолько, чтобы поверить в него и
потерять день.

Отдельно: на объекте с корпоративной сетью такое же мигание даёт **конфликт
маршрутов** — VPN-клиент или прокси перехватывает подсеть стенда. Проверяется
`ip route get <адрес>` и сравнением того, чей это интерфейс.

## Случай 2. Узел онлайн, сигналы идут вверх и не идут вниз

**Как выглядело.** Управление номером «умерло» на работающем стенде. Узел в
консоли — `Online`. Эмулятор отвечает. Коннектор в логах бодр: heartbeat каждую
минуту, ошибок нет. А гость видит, что состояние не читается, и команды не
доходят. Лечилось пересозданием контейнеров — и через сутки повторялось.

**Что показал разбор.** Асимметрия — вот вся улика: **вверх доходит, вниз
нет**. Значит сокет жив (иначе не было бы heartbeat), а адресация вниз
сломана.

Внизу лежит группа Channels в Redis. Членство в группе живёт с TTL
(`group_expiry`, по умолчанию **сутки**) и продлевается только новым
`group_add`. Коннектор держит сокет неделями и переподписаться не пытается —
незачем, соединение же не рвалось. Через сутки рассылка вниз уходит в никуда:
группа пуста, отправлять некому, ошибки нет.

Снаружи: узел «онлайн», оборудование отвечает, а бэкенд считает связь мёртвой
и отдаёт «состояние нечитаемо». Пересоздание контейнеров лечило потому, что
переподключение заново добавляло канал в группу — то есть лечило симптом ровно
на следующие сутки.

**Как чинится.** Переподписка на каждом heartbeat: `group_add` идемпотентен и
стоит одну команду Redis, а heartbeat идёт раз в минуту. Поднять `group_expiry`
было бы половиной решения — большой TTL всё равно однажды истечёт на
долгоживущем соединении. Срок, который просто больше, — это не решение, а
отложенный тот же отказ.

**Общий признак, ради которого случай здесь.** Долгоживущее соединение и
подписка с конечным сроком — вечный источник таких отказов. Ищите его всякий
раз, когда:

* отказ приходит **по расписанию**, а не по нагрузке (через сутки, через час);
* поток **односторонний**: одно направление живо, другое молчит;
* перезапуск лечит **ровно на длину срока**.

## Случай 3. Тест мигает, а изменились данные, а не код

**Как выглядело.** Прогон доски исполнителя стал падать через раз. Код доски
никто не трогал. Версия напрашивалась сама: потерянное сообщение живого канала
— гонка, которая и должна мигать.

**Что я сделал не так.** Поверил версии и начал чинить: добавил на доску
периодический опрос как страховку от потерянного сообщения. Тест позеленел.
Это и было ошибкой — позеленел он потому, что опрос маскировал **любую**
причину, включая настоящую.

**Что оказалось.** На дев-стенде накопилось **119 активных заказов**. Доска
рисует все, старые первыми. Тест искал свою заявку на экране, а она уезжала за
пределы видимой части — тем вероятнее, чем больше мусора накопилось за день.
Мигание было не гонкой, а функцией количества строк.

**Чем кончилось.** Продуктовую правку я откатил: доска не должна опрашивать
сервер ради теста, а страховка от несуществующей гонки — это лишний трафик у
каждого исполнителя навсегда. Старые заказы закрыл, прогон повторил трижды
подряд — зелено.

**Правило, которое из этого следует.**

> Мигающий тест при неизменном коде — сначала подозревайте **состояние**, а не
> код. Данные стенда меняются каждый день, код — по коммиту.

Проверяется быстро и до всякой отладки:

```bash
git log --oneline -5 -- <файл, который «сломался»>     # код правда не менялся?
docker compose … exec -T backend python manage.py clean_test_residue
```

И красный флаг для себя: **если правка продукта чинит тест, а объяснение
причины так и не найдено — правка маскирует, а не чинит.** Зелёный прогон
здесь не доказательство, а именно то, что мешает найти причину.

## Быстрый определитель

| Симптом | Смотреть первым |
|---|---|
| Всё лежит после выкатки | `df -h`, потом логи упавшего контейнера |
| Мигает снаружи, изнутри зелено | сетевой путь (случай 1), не трогать сервер |
| `dependency failed to start` у postgres | пустая переменная в `.env.prod` |
| Гостевая главная отдаёт 500 | `CACHE_URL` — погода читает кэш первой |
| Пропали все фотографии | `GUEST_APP_PUBLIC_SCHEME=https` |
| Управление номером недоступно | три звена порознь, потом логи коннектора |
| Узел онлайн, команды не доходят | случай 2, срок подписки |
| Фоновые задачи ведут себя «как раньше» | воркер на старом образе — [выкатка](deploy.md) §3 |
| Платформенная выдача пуста, ошибок нет | забыт тенант или платформенная роль |
| Тест мигает при неизменном коде | случай 3, состояние стенда |

Последние две строки — один и тот же класс: **ноль строк вместо ошибки**. Вне
тенанта роль приложения не падает, она отдаёт пустоту. Ищите не исключение, а
несделанную работу.
