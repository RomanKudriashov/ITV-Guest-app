# Погода на главной: лицензия, свой экземпляр, настройки

## Коротко

Погоду показывает главная витрины гостя. Данные берёт **сервер** фоновой
задачей и держит в кэше; гостевое приложение к провайдеру не обращается
никогда. Блок появляется, только если у отеля заданы координаты и погода
включена в CMS.

## ЛИЦЕНЗИЯ — это не опция

Провайдер по умолчанию — [Open-Meteo](https://open-meteo.com). Ключ и
регистрация не нужны, но **публичный `api.open-meteo.com` бесплатен только для
некоммерческого использования и до 10 000 запросов в сутки**.

Наш продукт коммерческий. Значит, для боевой эксплуатации нужно одно из двух:

1. **платный план** провайдера — тогда в `WEATHER_API_URL` уходит выданный
   адрес (у Open-Meteo это `https://customer-api.open-meteo.com` с ключом);
2. **свой экземпляр** — сервер Open-Meteo открытый и ставится в Docker. Тогда
   лимитов и лицензионных условий публичного доступа нет вовсе, а данные не
   уезжают за периметр. Это же снимает вопрос доступности: сервис соседний, а
   не чужой.

**Атрибуция обязательна в любом случае.** Рядом с погодой на витрине стоит
ссылка на open-meteo.com — она часть условий, а не украшение, и убирать её
нельзя. Ссылка живёт в компоненте `HomeWeather`; если провайдер меняется,
меняется и подпись.

### Свой экземпляр в двух словах

```bash
docker run -d --name open-meteo -p 8080:8080 \
    -v open-meteo-data:/app/data ghcr.io/open-meteo/open-meteo
# и один раз — скачать нужный набор данных (пример: ECMWF IFS 0.25°)
docker exec open-meteo /app/openmeteo-api sync ecmwf_ifs025 temperature_2m,weather_code
```

После этого в окружении бэкенда:

```
WEATHER_API_URL=http://open-meteo:8080
```

Кода это не касается: провайдер спрятан за интерфейсом
(`apps/integrations/weather/base.py`), адрес приходит настройкой.

## Настройки окружения

| Переменная | По умолчанию | Смысл |
|---|---|---|
| `WEATHER_PROVIDER` | `open-meteo` | Какой провайдер. Сменяемый: интерфейс одноместный, реализация выбирается здесь |
| `WEATHER_API_URL` | `https://api.open-meteo.com` | Адрес провайдера. В проде — платный план или свой экземпляр |
| `WEATHER_REFRESH_SECONDS` | `1200` (20 мин) | Как часто ходим за погодой одного отеля |
| `WEATHER_FRESH_SECONDS` | `2700` (45 мин) | Докуда значение остаётся правдой. Позже — блок исчезает |

`WEATHER_FRESH_SECONDS` заметно больше `WEATHER_REFRESH_SECONDS` намеренно: одна
пропущенная попытка не должна гасить блок.

## Как это работает

* координаты отеля — поля профиля (CMS → Настройки главной). Нет координат —
  нет ни блока у гостя, ни раздела погоды у оператора;
* обновление ставит **первый гость, увидевший протухший кэш**, и ровно один:
  рядом с данными лежит ключ-кулдаун на `WEATHER_REFRESH_SECONDS`. Сто
  одновременных открытий главной дают один вызов провайдера. Отель, на главную
  которого никто не заходит, не опрашивается вовсе;
* провайдер не ответил, ответил непонятно, значение протухло, координат нет,
  отель погоду не включал — для витрины это **один и тот же случай**: блока
  нет. Ни прочерков, ни заглушек, ни старых значений под видом текущих;
* состояние («ясно», «дождь») локализуется **нашими** строками по коду WMO из
  ответа, на всех четырёх языках. Текст провайдера гостю не показывается: он не
  на всех наших языках.

## Если погоды нет у гостя

По порядку: заданы ли координаты (CMS), включена ли погода (CMS), отвечает ли
`WEATHER_API_URL` из контейнера бэкенда, жив ли воркер Celery (обновление —
фоновая задача). В логах бэкенда ищите `Погода:`.
