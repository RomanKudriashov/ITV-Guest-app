# E2E (Playwright)

Тесты гоняются поверх **уже поднятого** стенда — они не поднимают своё
окружение. Смысл именно в этом: проверяется та сборка, которую видит
разработчик, вместе с настоящими бэкендом, Postgres и MinIO.

```bash
docker compose up -d          # из корня репозитория
cd e2e
npm install
npm run install-browsers      # один раз: скачает chromium
npm test
```

Полезное:

```bash
npm run test:headed           # с видимым браузером
npx playwright test --debug   # пошаговая отладка
npm run report                # HTML-отчёт после запуска
E2E_BASE_URL=http://localhost:5183 npm test
```

Тесты последовательны (`workers: 1`) намеренно: они пишут в каталог общего
демо-отеля, и параллельный запуск устроил бы гонку за порядок сортировки.
Каждый тест создаёт позиции с уникальным суффиксом и убирает их за собой.

## Стенд: снимок, уборка и проверка после прогона

Прогон убирает за собой по правилу «чего не было в снимке до прогона — создано
прогоном». Правило одностороннее и обязано таким остаться:

* **снимок не прочитался — прогон не начинается.** `globalSetup` падает громко,
  а не записывает пустой список. Пустой снимок раньше означал «ничего не было»,
  и уборка сносила по нему весь отель: три заведения без заказов удалялись,
  остальные выключались вместе с точками исполнения — то есть отель переставал
  принимать заказы;
* **вид не прочитался — по нему не убирается ничего.** Решение живёт в чистой
  функции `plannedRemovals`, её и проверяет `tests/stand-guard.spec.ts` — без
  сети и без последствий: сторож, который зовёт настоящую уборку, ломал бы
  стенд ровно в тот прогон, когда защита отвалилась.

### Серийные файлы: читать «did not run», а не только «passed»

`room-control-cms.spec.ts` объявлен `mode: 'serial'` — шаги зависят друг от
друга. При падении шага остальные НЕ выполняются, и Playwright честно пишет
это отдельной строкой сводки:

```
  1 failed
  8 did not run
  1 passed
```

Строка «did not run» — часть результата, а не шум. Отфильтровав её грепом по
`passed|failed`, легко прочитать «1 failed, 1 passed» как «упал один тест,
остальное в порядке», хотя проверено было два теста из десяти.

После прогона (и перед любым показом клиенту) стоит спросить стенд, цел ли он:

```bash
docker compose exec backend python manage.py check_demo_stand
```

Команда называет, что именно исчезло — вплоть до выключенной точки исполнения,
которую на витрине не видно, а заказ по ней уже не проходит. Смотрит она
теперь весь стенд: номера, заказы и сессии по каждому из трёх отелей, а у
«Кристалла» ещё управление номером (тип, публикация, привязка, PIN, зоны,
элементы). Раньше контракт был только про каталог демо-отеля — и «стенд цел»
могло уживаться с «номеров нет», потому что про номера проверка не знала.
Ненулевой код возврата означает деградацию. Чинит не она, а идемпотентный
сид:

```bash
docker compose exec backend python manage.py seed_demo_hotel \
    --subdomain crystal --force --with-rich-catalog
```
